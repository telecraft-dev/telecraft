# Findings: can one collector report to two OpAMP servers?

Resolves `issues/01-opamp-extension-supervisor-coexistence.md`.

Researched 2026-08-04. All citations are to upstream source read directly, not to
blog posts or summaries. Sources pinned at:

- `open-telemetry/opamp-spec` @ `c55ef2474d37` (2026-08-03), `specification.md`,
  document status Beta.
- `open-telemetry/opentelemetry-collector-contrib` @ `dbd6ad84f39c` (2026-08-03),
  latest release `v0.157.0` (2026-07-21), also checked at `v0.120.0`, `v0.130.0`,
  `v0.140.0`, `v0.150.0`, `v0.157.0`.
- `open-telemetry/opamp-go` @ `258e6d4cb261` (2026-08-03).

Line numbers are against those commits. `main` moves, so treat line numbers as
locators, not as stable identifiers. Note: the ticket asks five numbered
questions. Section 6 below is not from the ticket, it is the explicit ADR-0003
verdict the ticket's closing paragraph asks for.

Throughout, "MANDATES" means normative RFC 2119 language in the OpAMP
specification. Everything else is one implementation's behaviour at a point in
time and can change.

---

## 1. Does the spec forbid, permit, or not address two OpAMP servers per agent?

**Verdict: not addressed. No prohibition and no explicit permission. The spec's
unit of description is a single Client-to-Server pair, and it is silent on an
Agent holding two.**

Evidence.

The only cardinality statement in the Communication Model is non-normative and
describes the reverse direction (`specification.md` L325-328):

> Typically a single Server accepts connections from many Clients.

The spec then collapses the Agent/Supervisor distinction and defines its subject
as the client-implementing entity, singular (L361-364):

> In the rest of the OpAMP specification the term _Agent_ is used to refer to the
> entity which implements the client portion of the OpAMP, regardless of whether
> or not a Supervisor is part of that entity.

The only normative constraint on connection count is in
[Duplicate WebSocket Connections](https://github.com/open-telemetry/opamp-spec/blob/main/specification.md#duplicate-websocket-connections)
(L3429-3436), and it is scoped to a single Server:

> Each Client instance SHOULD connect no more than once to the Server. [...]
> The Server MAY disconnect or deny serving requests if it detects that the same
> Client instance has more than one simultaneous connection or if multiple Agent
> instances are using the same instance_uid.

That is a SHOULD about duplicate connections to the same Server, plus a MAY about
`instance_uid` collision within one Server's view. Neither reaches two distinct
Servers.

The closest the spec comes to contemplating a change of Server is redirection of
the one connection, not a second concurrent one (L1650-1653, Connection Settings
Management):

> The **OpAMP Server** itself. This is typically used to manage credentials [...]
> The Server MAY also offer a different destination endpoint to direct the OpAMP
> Client to connect to a different OpAMP Server.

Searches of the full specification for "multiple server", "more than one server",
"two server", "several server" and "multiple OpAMP" return only the L325 line
above. There is no text defining behaviour when two Servers both offer remote
config, both assign `instance_uid`, or disagree.

Consequences worth carrying forward, stated as consequences rather than as spec
text:

- Two OpAMP Clients inside one collector process are, to the spec, two Agents.
  Each carries its own `instance_uid` unless configured otherwise.
- Because the spec is silent, nothing upstream guarantees interoperability of the
  arrangement. It is not forbidden, but it is also not a supported shape with
  defined semantics. Any guarantee has to come from the implementations, which is
  what questions 2 and 3 test.

## 2. Does the collector's `opamp` extension support one server endpoint or many?

**Verdict: exactly one server per extension instance, and the two transports are
mutually exclusive. Running two named instances of the extension is permitted by
the collector's component model, but is not documented, tested or discussed
anywhere upstream that I could find, so multi-instance support is NOT
established.**

Evidence for "exactly one".

`extension/opampextension/config.go`:

- L31-32: a single field, `Server *OpAMPServer \`mapstructure:"server"\``. There is
  no list type anywhere in the config struct.
- L135-138: `OpAMPServer` holds `WS *commonFields` and `HTTP *httpFields`, one
  endpoint each.
- L217-220, `Validate()`:

```go
case cfg.Server.WS == nil && cfg.Server.HTTP == nil:
    return errors.New("opamp server must have at least ws or http set")
case cfg.Server.WS != nil && cfg.Server.HTTP != nil:
    return errors.New("opamp server must have only ws or http set")
```

- L182-189: `GetEndpoint()` returns a single string.

`extension/opampextension/opamp_agent.go` L132-154 builds one
`types.StartSettings` with one `OpAMPServerURL` and starts one client (L184).

The README documents the same single-server shape (`README.md` L20-39, example at
L59-65).

Evidence bearing directly on ADR-0003's premise about what the extension can do.

`config.go` L74-92, `toAgentCapabilities()`, is the complete set the extension can
advertise:

```go
agentCapabilities := protobufs.AgentCapabilities_AgentCapabilities_ReportsStatus
if caps.ReportsEffectiveConfig { ... ReportsEffectiveConfig }
if caps.ReportsHealth { ... ReportsHealth }
if caps.ReportsAvailableComponents { ... ReportsAvailableComponents }
if caps.AcceptsRestartCommand { ... AcceptsRestartCommand }
```

`AcceptsRemoteConfig` is absent, and there is no config key that could add it.
The extension therefore cannot be offered remote config at all: per spec L2509-2511,
"The OpAMP Client MUST set the AcceptsRemoteConfig bit [...] If the bit is not set
the Server MUST not offer a remote configuration to the Agent." The supervisor's
own design document states the same subset
(`cmd/opampsupervisor/specification/README.md` L685-703).

One correction to the ADR's framing, though. The extension is not purely a
reporter. `accepts_restart_command` (default `false`, gated behind the alpha
feature gate `extension.opampextension.RemoteRestarts`) lets its OpAMP server send
a restart command, on which the extension SIGHUPs the collector, which re-reads
its `--config` sources (`README.md` L73-82, `config.go` L70-71 and L213-216).
Pointed at a third party, that is a remote actuation path, not just telemetry. It
is off by default and would have to be deliberately enabled.

Evidence on multiple instances, and its limit.

The collector addresses components by a `type[/name]` composite key
(`go.opentelemetry.io/collector/component/identifiable.go`, `typeAndNameSeparator`),
so `opamp` and `opamp/fleet` are two distinct component IDs, and the factory
(`extension/opampextension/factory.go`) creates a fresh instance per ID with no
package-level or global state. Components that want to talk to a specific opamp
extension look it up by explicit component ID rather than by type
(`extension/opampcustommessages/README.md`, usage example), so two instances are
individually addressable rather than ambiguous.

What I could NOT establish: any upstream statement, test, example or issue that
two `opamp` extension instances in one collector is a supported configuration. GitHub
issue searches on the contrib repo for "opampextension multiple instances", "opamp
extension multiple servers" and "two OpAMP servers" returned nothing. Absence of a
prohibition in code is not the same as upstream support. This is the weakest link
in the chain and is cheap to settle empirically in the testbed.

## 3. Does the Supervisor inject or manage the collector's `opamp` extension block?

**Verdict: yes, it injects it, and it also injects `service.extensions: [opamp]`.
But the specific failure mode the ticket fears, a hand-added second extension
being silently overwritten on the next config push, does NOT occur: the Supervisor
merges `service::extensions` by concatenation plus de-duplication rather than by
replacement. A different hazard exists in the opposite direction, described below.**

Evidence that it injects.

`cmd/opampsupervisor/supervisor/templates/opampextension.yaml`, verbatim and
complete:

```yaml
extensions:
  opamp:
    instance_uid: "{{.InstanceUid}}"
    server:
      ws:
        endpoint: "ws://127.0.0.1:{{.SupervisorPort}}/v1/opamp"
        tls:
          insecure: true
    ppid: {{.PID}}
    ppid_poll_interval: {{.PPIDPollInterval}}
    capabilities:
      reports_available_components: {{.ReportsAvailableComponents}}
{{- if .IncludeResourceAttributes}}
    agent_description:
      include_resource_attributes: true
{{- end}}

service:
  extensions: [opamp]
  telemetry:
    resource:
      attributes:
        - name: service.instance.id
          value: "{{.InstanceUid}}"
```

Rendered by `supervisor.go` L1328-1353 (`composeOpAMPExtensionConfig`). The design
document states it plainly (`cmd/opampsupervisor/specification/README.md` L685-686):
"The Supervisor automatically injects the opamp extension in the Collector's
configuration." The merged result is written to disk and the collector is launched
against it (`supervisor.go` L2220, `os.WriteFile(s.agentConfigFilePath(), ...)`).

Evidence on merge order.

`supervisor.go` L1144-1172 (`addSpecialConfigFiles`) inserts `$OWN_TELEMETRY_CONFIG`
at the front, then appends `$OPAMP_EXTENSION_CONFIG`, then appends `$REMOTE_CONFIG`.
The design document documents the same default order
(`specification/README.md` L286-292):

> - `$OWN_TELEMETRY_CONFIG`
> - <USER_PROVIDED_CONFIG_FILES>
> - `$OPAMP_EXTENSION_CONFIG`
> - `$REMOTE_CONFIG`

and states that later files win (L255-258): "configuration files are merged from the
top of the list to the bottom. Configuration added by files at the top of the list
may be overwritten by the later ones." Files are merged in that order by
`composeAgentConfigFiles` (L1362-1416), consumed by `composeMergedConfig`
(L1750-1782). So the remote config from the OpAMP server merges LAST, on top of the
injected extension block.

Evidence that the extension list is concatenated, not replaced. This is the load-
bearing finding.

`cmd/opampsupervisor/supervisor/config/confmap.go` L157-186:

```go
// MergeConf merges incoming into base while preserving Supervisor-specific
// merge semantics that collector confmap does not provide by default.
// service extension lists are concatenated and resource attributes are
// merged by name.
func MergeConf(base, incoming *confmap.Conf) error {
	baseExtensions := getExtensions(base)
	incomingExtensions := getExtensions(incoming)
	...
	if err := base.Merge(incoming); err != nil { return err }
	...
	if len(baseExtensions) > 0 || len(incomingExtensions) > 0 {
		setExtensions(base, deduplicateExtensions(baseExtensions, incomingExtensions))
	}
```

with `deduplicateExtensions` (L211-225) appending base then incoming and dropping
repeats. A remote config carrying `service.extensions: [opamp/fleet]` therefore
yields `[opamp, opamp/fleet]`, not `[opamp/fleet]`. Separately, `extensions:` is a
map, so an `extensions.opamp/fleet` block and the injected `extensions.opamp` block
are different keys and coexist under ordinary map merge.

This is not new or `main`-only behaviour. The same semantics are present in the
released `v0.157.0` under the older koanf implementation
(`supervisor.go`, `configMergeFunc`, which does `slices.Concat(destExt, srcExt)` and
de-duplicates), and the extension-list append exists as far back as `v0.120.0`
(append without de-duplication there, de-duplication added by `v0.130.0`).

The hazard that DOES exist, in the other direction.

Because `$REMOTE_CONFIG` merges last and ordinary map keys are overridden by the
later source, a remote config that writes under the key `extensions.opamp` will
override the Supervisor's injected values, including the endpoint pointing at the
Supervisor's local server. That would break the Supervisor-to-collector link
rather than "defeat ADR-0003 quietly". The design document asserts the opposite
(`specification/README.md` L735-736): "The extension's configuration cannot be
overridden by the remote configuration." I found no code enforcing that assertion.
The design document carries a softer, accurate warning instead (L271): overriding these
snippets "may result in the Supervisor failing to properly start the Collector and
should be done with caution."

Practical consequence: a second extension must be given a distinct name such as
`opamp/fleet`. Reusing the bare name `opamp` would clobber the Supervisor link.

Two further details.

- The Supervisor's local OpAMP server accepts only one agent connection at a time,
  returning 409 Conflict to a second (`supervisor.go` L859-870). This constrains
  connections to the Supervisor. It does not constrain a second extension instance
  connecting outward to a different server.
- Not established: I found no upstream test exercising a remote config that adds a
  second `opamp` extension instance. The merge semantics are tested
  (`config/confmap_test.go` exists), but the specific end-to-end case is not
  something I could evidence.

## 4. Does the Supervisor report `EffectiveConfig` and health to its own server?

**Verdict: yes to both, and both are enabled by default. The Supervisor also
forwards the collector's own reported effective config and health upward, so what
its server sees is the collector's declared state, not merely the Supervisor's
intention.**

Evidence, effective config.

`supervisor.go` L723-725, in `startOpAMPClient`, registers the callback opamp-go
uses to populate `AgentToServer.effective_config`:

```go
GetEffectiveConfig: func(context.Context) (*protobufs.EffectiveConfig, error) {
    return s.createEffectiveConfigMsg(), nil
},
```

`createEffectiveConfigMsg` (L1687-1707) prefers `s.effectiveConfig`, falling back to
the Supervisor's own merged config:

```go
cfgStr, ok := s.effectiveConfig.Load().(string)
if !ok {
    cfgState, ok := s.cfgState.Load().(*configState)
    if !ok { cfgStr = "" } else { cfgStr = cfgState.mergedConfig }
}
```

`s.effectiveConfig` is populated from the collector, via the collector's own opamp
extension, in `handleAgentOpAMPMessage` (L896-911):

```go
if message.EffectiveConfig != nil {
    if cfg, ok := message.EffectiveConfig.GetConfigMap().GetConfigMap()[""]; ok {
        s.effectiveConfig.Store(string(cfg.Body))
        err := s.opampClient.UpdateEffectiveConfig(ctx)
```

So the chain is: collector extension reports effective config to the Supervisor's
local server, the Supervisor stores it and pushes it up to its own OpAMP server. The
Supervisor also re-reports on any config change of its own (L2514-2520). The message
is a single-entry config map keyed with the empty string (L1698-1704).

Evidence, health.

`handleAgentOpAMPMessage` L936-951 relays the agent's health upward:

```go
if message.Health != nil {
    s.lastHealthFromClient.Store(message.Health)
    err := s.SetHealth(message.Health)
```

`SetHealth` (L2478-2491) calls `s.opampClient.SetHealth`. The Supervisor also sets
health itself: unhealthy before the collector starts (L747), unhealthy on start
failure (L1952) and on crash paths (L640, L2061), healthy once running (L2028).

Evidence, defaults.

`cmd/opampsupervisor/supervisor/config/config.go` L446-457 (default capabilities):

```go
AcceptsRemoteConfig:            false,
AcceptsRestartCommand:          false,
AcceptsOpAMPConnectionSettings: false,
ReportsEffectiveConfig:         true,
ReportsOwnMetrics:              true,
ReportsHealth:                  true,
ReportsRemoteConfig:            false,
ReportsAvailableComponents:     false,
ReportsHeartbeat:               true,
AcceptsPackages:                false,
```

`SupportedCapabilities()` (L105-158) maps those onto `protobufs.AgentCapabilities`,
and `startOpAMPClient` sets them on the client (L757-760). The design document
agrees (`specification/README.md` L46-50, L99).

Note for Interchange's own configuration: `AcceptsRemoteConfig` is `false` by
default, so a deployment that wants the control plane to push config must enable it
explicitly. `ReportsEffectiveConfig` and `ReportsHealth` cost nothing extra, they
are already on.

Bearing on `testbed/control-plane/main.go`.

The claim in the ticket's context note checks out. At L139-140 the control plane
advertises only `AcceptsStatus | OffersRemoteConfig`, and `onMessage` (L136-210)
reads `msg.AgentDescription`, `msg.RemoteConfigStatus` and `msg.Health` but never
`msg.EffectiveConfig`. It is already receiving the collector's effective config on
the connection it owns and discarding it. Making use of it is: add
`ServerCapabilities_AcceptsEffectiveConfig` at L139-140, and read
`msg.EffectiveConfig.ConfigMap.ConfigMap[""]` in `onMessage`. See question 5 for why
the capability bit matters even though the data arrives without it.

## 5. Which capability flags govern effective config, and which side advertises what?

**Verdict: the Agent advertises `ReportsEffectiveConfig` (0x00000004) and MUST do so
if capable. The Server advertises `AcceptsEffectiveConfig` (0x00000004 in the
separate ServerCapabilities space). The spec MANDATES that an Agent stop using a
capability the Server does not advertise, so a conforming client would stop sending
effective config to a server that omits `AcceptsEffectiveConfig`. opamp-go's client
does NOT implement that check, so in practice the data flows either way today.
Health has no paired server capability, it is covered by mandatory `AcceptsStatus`.**

Agent side, `specification.md` L671-712:

```protobuf
ReportsStatus                   = 0x00000001;  // MUST be set, all Agents report status
AcceptsRemoteConfig             = 0x00000002;
ReportsEffectiveConfig          = 0x00000004;
...
ReportsHealth                   = 0x00000800;
ReportsRemoteConfig             = 0x00001000;
```

and the normative rule (L2526-2529):

> The Client MUST set the ReportsEffectiveConfig bit of AgentToServer.capabilities
> if the Agent is capable of reporting effective configuration. If the bit is not
> set the Server should not expect the AgentToServer.effective_config field to be
> set.

Server side, `specification.md` L963-987:

```protobuf
AcceptsStatus                  = 0x00000001;  // MUST be set, all Servers accept status
OffersRemoteConfig             = 0x00000002;
AcceptsEffectiveConfig         = 0x00000004;
```

with (L955-961) "This field MUST be set in the first ServerToAgent sent by the
Server and MAY be omitted in subsequent ServerToAgent messages."

The binding rule that ties the two together is in Interoperability of Partial
Implementations (L3665-3669):

> After the Server learns about the capabilities of the particular Agent the
> Server MUST stop using the capabilities that the Agent does not support.
>
> Similarly, after the Agent learns about the capabilities of the Server the Agent
> MUST stop using the capabilities that the Server does not support.

Read strictly, a conforming Client that sees a Server without
`AcceptsEffectiveConfig` MUST stop sending `effective_config`.

Implementation reality, which differs.

opamp-go's client never inspects `ServerCapabilities`. Grepping the whole non-test
client for the symbol returns zero hits in `client/internal/receivedprocessor.go`,
`client/internal/clientcommon.go`, `client/internal/httpsender.go`,
`client/internal/wssender.go` and `client/internal/sender.go`. The client gates
outbound and inbound handling on its OWN `AgentCapabilities` only
(`receivedprocessor.go` L68-129, `clientcommon.go` L75-93). So a control plane that
omits `AcceptsEffectiveConfig` still receives effective config from opamp-go-based
agents, including both the Supervisor and the collector's extension.

Practical guidance for Interchange: relying on that is relying on a client not
implementing a MUST. Advertise `AcceptsEffectiveConfig` and the behaviour is correct
by the spec as well as working in practice.

Related flags for completeness:

- Health: `AgentCapabilities_ReportsHealth` = 0x00000800 (`specification.md` L708-709).
  There is no `AcceptsHealth` server capability, health arrives under the mandatory
  `AcceptsStatus`.
- Remote config status: `AgentCapabilities_ReportsRemoteConfig` = 0x00001000. The
  Supervisor defaults this to `false` (`config.go` L454), and gates its
  `SetRemoteConfigStatus` calls on it (`supervisor.go` L2423, L2453). Worth knowing
  if Interchange's control plane wants to see apply/failure outcomes rather than
  infer them from the config hash echoed in `RemoteConfigStatus`.

## 6. Verdict on ADR-0003's central claim

ADR-0003 claims that pointing the collector's in-process `opamp` extension at
Elastic Fleet costs nothing architecturally, because the extension only reports
while the Supervisor keeps applying config from Interchange.

**The central claim HOLDS on the evidence, with two qualifications and one
unestablished dependency.**

Holds:

1. The extension genuinely cannot accept remote config. `AcceptsRemoteConfig` is
   not in its capability set and there is no config key to add it
   (`config.go` L74-92), and the spec forbids a Server offering config to an Agent
   that has not set the bit (`specification.md` L2509-2511). Config authority
   cannot leak to Fleet through this path.
2. The Supervisor does inject and own an `opamp` extension block, so the ADR was
   right to worry (question 3). But the feared silent overwrite does not happen:
   `service::extensions` is merged by concatenation plus de-duplication, in `main`,
   in released `v0.157.0`, and back to at least `v0.120.0`
   (`config/confmap.go` L157-225; `v0.157.0` `configMergeFunc`). A remote config
   adding `opamp/fleet` survives the next push.

Qualification A, naming is load-bearing. The second extension must NOT be called
`opamp`. `$REMOTE_CONFIG` merges after `$OPAMP_EXTENSION_CONFIG`, so values written
under `extensions.opamp` override the Supervisor's injected endpoint and break the
Supervisor-to-collector link. The Supervisor design document claims this cannot
happen (`specification/README.md` L735-736); no code enforces that claim. So the
cost is not literally zero, it is one naming constraint plus a documented reason for
it.

Qualification B, "only reports" is imprecise. With `accepts_restart_command` plus
the `extension.opampextension.RemoteRestarts` feature gate, the extension's server
can trigger a collector restart via SIGHUP, which re-reads `--config` sources
(`extension/opampextension/README.md` L73-82). Both are off by default. The ADR
should say the extension cannot accept remote config, which is exact, rather than
that it only reports, which is not.

Not established: whether two concurrent `opamp` extension instances in one collector
are supported upstream. The collector's `type/name` component model permits it, the
factory holds no shared state, and custom-message consumers resolve extensions by
explicit component ID. But no upstream documentation, test, example or issue
addresses the case. This is an assumption the ADR rests on and it should be settled
by running it in the testbed, not by reading more code.

Separately, question 4 changes the shape of the problem rather than just validating
the ADR. The Supervisor already reports `EffectiveConfig` and health to its own
OpAMP server by default, and forwards the collector's own reported effective config
upward. Interchange therefore does not need the extension in order to obtain
declared state: it already has it on the connection it owns, and
`testbed/control-plane/main.go` is discarding it. That weakens the argument that the
extension must be spent on Fleet to get visibility, and correspondingly weakens the
premise the ADR was defending against.
