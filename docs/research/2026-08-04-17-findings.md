# 17: What does the Kubernetes OTel ecosystem already give us for free?

Research findings. Source of truth for the OTel Operator claims is the repository at
commit `936faf56a92dce743afd4ef7be60f6719dd2b534` (main, 2026-08-04), release line
v0.156.0. Paths below are relative to `github.com/open-telemetry/opentelemetry-operator`
unless marked otherwise.

---

## Bottom line: adopt, build, reconsider

**The OpAMP bridge does not remove the need to write an OpAMP server. It is an OpAMP
client that requires one.** The bridge's entire purpose is to connect *outbound* to a
server you supply and translate what that server sends into Kubernetes writes. There is no
OpAMP server in the OpenTelemetry org: only the spec (Beta), `opamp-go` (which does ship
a reusable Apache-2.0 `server` package), and an archived Java client. The operator's README
points at two personal repositories of a maintainer as example servers. Writing the server
stays in scope; `opamp-go` means you write policy and state, not wire protocol.

**Adopt:**
- `OpenTelemetryCollector` CRD + operator for in-cluster collector lifecycle and version
  management. Mature enough, Apache-2.0, CNCF.
- The OpAMP bridge as a **northbound reporting adaptor**: one OpAMP connection per cluster
  reporting effective config and health for every collector in it, including a read-only
  OpAMP proxy that harvests real pipeline health from collectors running the `opamp`
  extension. This is a genuine saving and the strongest part of the component.
- `opamp-go`'s `server` package as the protocol layer of your own server.
- Target Allocator, if and only if Prometheus scrape distribution is in scope.
- Two proven tier-boundary designs as **designs to copy**: kube-logging's `LoggingRoute`
  (selector + resolved status + failure reporting, Apache-2.0) and ECK's
  `Agent`/`fleetServerRef` association controller (resolved endpoint + propagated CA/mTLS;
  design only, Elastic License).

**Build:**
- The OpAMP server itself: rendering, policy, state, and the fleet model.
- Everything for collectors outside Kubernetes. The counterpart there is the OpAMP
  Supervisor (alpha), which is a different agent-side component with a different lifecycle
  from the in-cluster path. The two halves share only the protocol.
- The tier-boundary object. Nothing in OpenTelemetry has one (it has been requested four
  times since 2023 and never built), and the OTel Operator's own RFC explicitly places the
  gateway tier outside its model. But do not design it from scratch: copy kube-logging's
  `LoggingRoute` (Apache-2.0, CNCF Sandbox), which is the closest existing match, and steal
  Odigos's trick of having the consumer advertise accepted signals in `status`.
- Config history / audit of rendered configs. Etcd retains ~5 minutes.
- Graphical surface and a query API. The Kubernetes API's label selectors are the only
  query model, and the operator ships no UI.

**Reconsider:**
- One custom resource per collector at 5,000+. Not because etcd cannot hold them (it can,
  easily) but because Kubernetes' own CRD documentation disqualifies the shape in writing,
  because external objects cannot be watched so must be polled at rates the tooling cannot
  sustain, and because Kubernetes offers no scalability guarantee for custom resources at
  all. If Kubernetes-native semantics (RBAC, admission, audit, `kubectl`, watch) are the
  actual requirement, an aggregated API server with its own storage keeps all of them while
  moving the data off cluster etcd. That is the compromise worth costing.

## 1. The OTel Operator: what exists today

**Verdict: substantial and adoptable for in-cluster collector lifecycle. It is a
config-to-workload renderer, not a fleet control plane. Pre-1.0 on every API, with a
release cadence tied to the Collector's roughly-weekly-to-fortnightly train, which means
a continuous upgrade tax rather than a stable dependency.**

### The `OpenTelemetryCollector` CRD

Two served versions. `v1beta1` is the storage version; `v1alpha1` is served but
`storage: false` (`config/crd/bases/opentelemetry.io_opentelemetrycollectors.yaml`,
lines 4713-4714 and 9929-9930). Conversion between them is handled by a webhook, which
is why cert-manager is a hard install dependency (`README.md` line 34).

Four deployment modes, enum-validated (`apis/v1beta1/mode.go`):

| Mode | Renders |
|---|---|
| `deployment` | Deployment + Service |
| `daemonset` | DaemonSet |
| `statefulset` | StatefulSet |
| `sidecar` | Injected container via pod mutating webhook |

The CRD carries the entire collector config inline under `spec.config` as structured
YAML (`apis/v1beta1/config.go`, `opentelemetrycollector_types.go`), plus the usual
workload knobs: resources, tolerations, affinity, volumes, env, ports, autoscaler,
ingress, PDB, service account.

### Target Allocator

Now has its own CRD, `TargetAllocator.opentelemetry.io/v1alpha1`, split out of the
collector CR's `spec.targetAllocator` sub-resource because embedding it made the
collector CR unwieldy (`docs/reference/crd-changelog.md`). Two functions: even
distribution of Prometheus scrape targets across a collector pool, and discovery of
prometheus-operator CRs (ServiceMonitor, PodMonitor)
(`docs/target-allocator/README.md`). Default allocation strategy
`consistent-hashing`. **Only supports `statefulset` and `daemonset` collector modes**,
stated as a warning at the top of its README. This is a Prometheus-scrape scaling
mechanism, not a general fleet-partitioning mechanism.

### `Instrumentation` CRD

Injects language auto-instrumentation into workloads via pod annotations. Language
support is gated by operator CLI flags, not by the CR
(`docs/reference/feature-gates.md`): Java, NodeJS, Python, DotNet, ApacheHttpD default
on; **Go and Nginx default off**. Multi-container multi-language instrumentation is
behind `enable-multi-instrumentation`, default `false`. Instrumentation has a
`v1alpha1` and `v1beta1` (`apis/v1beta1/instrumentation_types.go`), with an RFC for the
v1beta1 migration at `docs/rfcs/instrumentation-v1beta1.md`.

### Lifecycle management

The operator version-locks the operand. "if the OpenTelemetry Operator is based on
version `0.40.0`, it will create resources with an underlying OpenTelemetry Collector at
version `0.40.0`" (`docs/getting-started/compatibility.md`). Config migration between
Collector versions is done by an upgrade routine in `pkg/collector/upgrade`, run against
managed CRs. Opt-out is per-resource: `spec.upgradeStrategy: none`
(`docs/getting-started/upgrading.md`), and the only other legal value is `automatic`.
Setting a custom `spec.image` also takes the resource out of managed versioning.

### Stability and cadence

- **Version**: 0.156.0 (`versions.txt`). Never cut a 1.0. Served CRD versions, parsed from
  the installed manifests: **only the Collector CRD has reached beta**:

  | CRD | Served versions |
  |---|---|
  | `OpenTelemetryCollector` | `v1alpha1` (served, deprecated), **`v1beta1`** (served, storage) |
  | `Instrumentation` | `v1alpha1` only |
  | `OpAMPBridge` | `v1alpha1` only |
  | `TargetAllocator` | `v1alpha1` only |
  | `ClusterObservability` | `v1alpha1` only |

  Note the gap between *project* maturity and *component* maturity: OpenTelemetry graduated
  CNCF in May 2026, but four of the operator's five APIs are still alpha. And
  `docs/rfcs/crd-version-graduation-strategies.md` records that the v1alpha1→v1beta1
  conversion webhook caused enough Helm and OLM pain that the team now recommends an
  "Identical Schemas" graduation strategy instead, directly relevant if you plan to depend
  on API stability.
- **Cadence**: "The operator should be released within a week after the OpenTelemetry
  collector release" (`RELEASE.md`). The release-manager rota in `RELEASE.md` is
  scheduled out to v0.164.0, one named maintainer per release. Versioning tracks the
  Collector's minor version exactly.
- **Kubernetes support**: v1.25 to v1.35 for v0.156.0, with at least one month's notice
  before dropping a version (`docs/getting-started/compatibility.md`).
- **Governance**: CNCF / OpenTelemetry project. Four maintainers, employed by Red Hat
  (x2), Omlet and Elastic; approvers from Splunk, Coralogix, Honeycomb, OllyGarden
  (`README.md`). Not vendor-captured, but a thin maintainer bench.
- **Hard dependency**: cert-manager, for the conversion and admission webhooks.

### Newly relevant: `ClusterObservability`

An `v1alpha1` cluster-scoped **singleton** CR behind the `operator.clusterobservability`
feature gate (`docs/collector/cluster-observability.md`). Its entire spec is one OTLP
HTTP exporter destination (`apis/v1alpha1/clusterobservability_types.go` line 150-155).
From it the controller generates, controller-of-controllers style, an agent DaemonSet
collector CR, a cluster StatefulSet collector CR, and one Instrumentation CR. Only the
oldest such CR in the cluster is active; others get a `Conflicted` condition. See Q4:
this is the closest thing in the ecosystem to a topology object, and it deliberately
stops short.

## 2. The OpAMP bridge: the load-bearing question

**Verdict: it does NOT remove the need for an OpAMP server. The bridge is an OpAMP
*client*. It connects outbound to an OpAMP server that you must supply, and its whole
purpose is to translate what that server sends into Kubernetes API writes. If the
design's egress is OpAMP, the bridge is a *consumer* of that egress, not the egress
itself. Writing the OpAMP server remains in scope.**

Three secondary verdicts, all of which matter:

- **It can serve arbitrary rendered config, in standalone mode only, and only into a
  pre-existing ConfigMap.** In its default operator mode it can only accept a full
  `OpenTelemetryCollector` CR manifest, so config still has to go through the CRD.
- **Yes, it reports effective config and health back.** Including, in operator mode, a
  read-only OpAMP proxy that harvests effective config and health directly from
  collectors that speak OpAMP.
- **No, it does not reach collectors outside the cluster.** Every applier writes through
  the Kubernetes API. The embedded proxy could in principle accept an inbound connection
  from anywhere, but it cannot configure what connects to it.

### Server, client, or translator? All three, in different directions.

**Outbound (northbound) it is a client.** `cmd/operator-opamp-bridge/README.md` line 3:
"It implements the agent-side of the OpAMP protocol and communicates with an OpAMP
server." In code, `internal/agent/agent.go` constructs an `opamp-go`
`client.OpAMPClient` and calls `opampClient.Start(ctx, types.StartSettings{OpAMPServerURL:
agent.config.Endpoint, ...})` (lines 201-260). It declares capabilities via
`SetCapabilities`, sets an agent description, and heartbeats health on a ticker
(`runHeartbeat`, default interval 30s per
`cmd/operator-opamp-bridge/internal/config/flags.go` line 30).

The README is explicit about what it expects on the other end, and it is not something
that ships with the operator. Line 12: "Examples of OpAMP server implementations that the
OpAMP Bridge can interact with include jaronoff97/opamp-elixir and
jaronoff97/opamp-operator-server": two personal repositories of one of the operator's
maintainers. There is no production OpAMP server in the OpenTelemetry org.

**Southbound it is a translator into the Kubernetes API.** The
`operator.ConfigApplier` interface (`internal/operator/client.go` lines 35-55) is
`Apply(key, *protobufs.AgentConfigFile)`, `Delete(key)`, `Restart(ctx)`,
`ListInstances()`, `GetHealth()`. Every implementation writes via a
`sigs.k8s.io/controller-runtime` client.

**Southbound it ALSO runs a real OpAMP server, but read-only.**
`internal/proxy/server.go` embeds `opamp-go`'s `server.OpAMPServer` and listens on
`:8080` by default (`flags.go` line 23), exposed by the operator as a Service on port 80
(`internal/manifests/opampbridge/service.go`). This was added deliberately as a read-only
proxy, CHANGELOG line 1279: "`opamp`: Enables the OpAMP Bridge to act as a read-only
proxy for effective configuration and health reporting. (#3823)", later correlated with
the bridge's own data (#3837, CHANGELOG line 1010).

Read-only is verifiable, not just claimed. In `internal/proxy/server.go` the `onMessage`
callback builds `response := &protobufs.ServerToAgent{}` and returns it having set only
an error or a `ReportFullState` flag; it never populates `RemoteConfig`. The only other
field ever set is connection settings, and `internal/proxy/agent.go`
`calcConnectionSettings` sets every member of `ConnectionSettingsOffers` to `nil` with
TODOs. Grepping `RemoteConfig` across `internal/proxy/` returns exactly two hits, both in
`agent.go` lines 100-101, and both are checks on whether the *agent* omitted its
`RemoteConfigStatus`. **The proxy cannot push config to a collector.**

### Can it deliver config the operator did not author from a CRD?

Two modes, selected by `mode:` in the bridge config file, default `operator`
(`internal/config/config.go` lines 41-42, `flags.go` line 31).

**Operator mode: no.** `internal/operator/client.go` `Apply()` does:

```go
var collector v1beta1.OpenTelemetryCollector
err = yaml.Unmarshal(configmap.Body, &collector)
```

The remote config body must be a complete `OpenTelemetryCollector` v1beta1 manifest. The
OpAMP config-map *key* is parsed as `namespace/name` (`kubeResourceFromKey`). It then
enforces three gates before writing:

1. `validateComponents` rejects any receiver/processor/exporter not in the bridge's
   `componentsAllowed` allow-list.
2. `validateLabels` refuses to modify a collector labelled
   `opentelemetry.io/opamp-reporting: "true"`, and refuses any collector that does not
   carry `opentelemetry.io/opamp-managed: "true"` or `= <bridge-name>`. Both the existing
   object *and* the incoming one are checked.
3. It then `Create`s or `Update`s the CR.

So the config does not have to be authored by the operator, but it must be *shaped as* a
CRD instance, and the CR is then rendered to a workload by the operator's own collector
controller. You cannot hand it a rendered `otelcol` YAML in operator mode.

**Standalone mode: yes, with real constraints.** Added in response to issue #4913
("there is no supported way to use OpAMP remote configuration to update a collector's
ConfigMap directly"), landed via #4986, CHANGELOG line 94. In this mode the bridge takes
a static list of `standalone.agents`, each pinned to a `workloadRef` (apps/v1
Deployment, DaemonSet or StatefulSet) and a set of named config entries, each mapping an
OpAMP config file name to a specific ConfigMap name and key
(`cmd/operator-opamp-bridge/README.md` lines 23-86). On remote config, it validates the
body as collector config, writes it into that exact ConfigMap key, and triggers a rollout
by patching `kubectl.kubernetes.io/restartedAt`
(`internal/standalone/client.go` `applyConfigMapFile`).

The constraints:

- **It will not create or delete ConfigMaps.** `applyConfigMapFile` returns "standalone
  mode does not support creating ConfigMap %s/%s" on NotFound, and
  `scopedApplier.Delete` unconditionally returns an error. The set of managed collectors
  is fixed at bridge start-up by its config file.
- **One OpAMP client connection per configured agent**: `main.go`
  `standaloneManagerOptions` loops over `cfg.Standalone.Agents` creating a client each.
  So N collectors means N OpAMP connections from one pod.
- **The proxy is disabled in standalone mode.** `main.go` line 87 passes
  `proxy.NoopServer{}`. No health or effective-config harvesting from live collectors.
- **Standalone mode is not reachable via the `OpAMPBridge` CRD.**
  `internal/manifests/opampbridge/configmap.go` renders only `endpoint`, `tls`,
  `headers`, `capabilities`, `componentsAllowed`, `description` into
  `remoteconfiguration.yaml`. It never emits `mode` or `standalone`. To use standalone
  mode you deploy the binary yourself and manage its config file and RBAC (the repo ships
  a starter at `cmd/operator-opamp-bridge/manifests/standalone/rbac.yaml`).

### Does it report effective config and health back?

Yes, and this is the strongest part of the component.

Capabilities are declared, not assumed: `AcceptsRemoteConfig`,
`ReportsEffectiveConfig`, `ReportsRemoteConfig`, `ReportsHealth`
(`apis/v1alpha1/opampbridge_capabilities.go`, exposed as `spec.capabilities`).

- **Effective config** (`agent.go` `getEffectiveConfig`, lines 336-373): lists every
  managed instance, emits one `AgentConfigFile` per instance keyed by `namespace/name`,
  then merges in whatever the read-only proxy has collected from directly connected
  collectors, keyed by OpAMP instance UID.
- **Health** (`agent.go` `getHealth` + `addProxyHealth`, lines 81-172): builds a
  recursive `ComponentHealth` tree: bridge root, then one node per collector CR
  (using `status.scale.statusReplicas`), then one node per collector Pod (healthy iff
  `status.phase == "Running"` and a start time exists). `addProxyHealth` then grafts
  proxy-reported health onto the matching Pod node by correlating OpAMP
  `host.name` against the Pod name; unmatched proxy agents are attached at the root.
- **Restart command**: `onCommand` handles `CommandType_Restart` by triggering a rollout
  restart of managed workloads; every other command type is rejected with an error
  (`agent.go` lines 458-472). Sidecar-mode collectors are skipped.

Note what "health" means here in operator mode without the proxy: it is *Kubernetes
workload health*, not collector-internal pipeline health. Real pipeline health only
arrives if the collectors themselves run the `opamp` extension pointed at the bridge's
proxy endpoint.

### Does it reach collectors outside the cluster?

**No, for configuration.** Both appliers are Kubernetes clients. Operator mode writes
`OpenTelemetryCollector` CRs; standalone mode writes ConfigMaps and patches apps/v1
workloads. There is no code path that delivers config to anything that is not a
Kubernetes object.

**Partially, for telemetry-about-agents.** The proxy is a plain OpAMP server on a TCP
listener. If you exposed it outside the cluster, an external collector running the
`opamp` extension could connect and its health and effective config would be forwarded
northbound. It would receive nothing back. Also note `internal/proxy/server.go` lines
85-94: TLS configuration for the proxy is commented out with "TODO: In the future we will
probably want some TLS configuration." The proxy listener has no TLS and no
authentication.

### Scaling ceilings on the bridge itself

Two hard ones, both relevant to a 5,000-collector fleet:

- **`OpAMPBridge` replicas are capped at 1.** The admission webhook rejects anything
  higher: `if r.Spec.Replicas != nil && *r.Spec.Replicas > 1 { return warnings,
  errors.New("replica count must not be greater than 1") }`
  (`internal/webhook/opampbridge_webhook.go` line 106; default set to 1 at line 63). No
  HA, no horizontal scale, no leader election needed because there is only ever one.
- **Proxy state is in-memory only.** `OpAMPProxy` holds `agentsById`, `agentsByHostName`
  and `connections` as plain maps guarded by a mutex (`internal/proxy/server.go` lines
  44-52). Restart the bridge and every agent's reported state is gone until each
  reconnects and re-reports.

### Dependency versions

`go.mod`: `github.com/open-telemetry/opamp-go v0.23.0`,
`sigs.k8s.io/controller-runtime v0.24.1`.

The OpAMP specification itself is **Status: Beta**
(`open-telemetry/opamp-spec/specification.md`, line following the title). Apache-2.0.

### What this means for the plan

The bridge is worth adopting as a *northbound reporting adaptor* for in-cluster
collectors: it gives effective-config and health aggregation for a whole cluster behind
one OpAMP connection, which is a genuine saving. It is not the egress. The OpAMP server
that renders and serves per-collector config still has to be built, and for collectors
outside Kubernetes the counterpart is the OpAMP Supervisor
(`opentelemetry-collector-contrib/cmd/opampsupervisor`, alpha, no Kubernetes required),
talking to that same server. See Q5.

## 3. Kubernetes as a control plane substrate, and where the wall is

**Verdict: the wall is much closer than 5,000 objects suggests, and it is not etcd
capacity. Three findings, in force order. (1) Kubernetes' own CRD documentation
disqualifies this design in writing, on two independent published criteria: ">1000s of
objects" and ">10s of requests per second sustained", plus a standalone "avoid using a
Custom Resource as data storage for... monitoring data". (2) Collectors outside the
cluster cannot be watched, so they must be polled, and the arithmetic is decisive: 5,000
external objects on Crossplane's default 1-minute poll needs ~83 reconciles/sec against a
documented global limit of 10/sec, an 8x miss, with horizontal scaling of providers closed
`not_planned` twice, most recently April 2026. (3) Kubernetes makes NO scalability promise
about custom resources at all: the official SLOs and the official thresholds both
explicitly exclude them. Locally, the OTel Operator makes it worse: reconcile concurrency
1, a cluster-wide cache over 14 resource types, and a 10-hour full-resync herd.**

The framing that matters: the question is not "can etcd hold 5,000 objects" (yes, easily)
but "what does the reconcile loop cost, and what is guaranteed". The answers are "far more
than you think" and "nothing".

### Kubernetes explicitly excludes custom resources from its scalability guarantees

The official API call latency SLO reads, verbatim: "In default Kubernetes installation,
for every (resource, verb) pair, **excluding virtual and aggregated resources and Custom
Resource Definitions**, 99th percentile per cluster-day <= 1s"
(https://github.com/kubernetes/community/blob/master/sig-scalability/slos/api_call_latency.md
lines 7-8). The read-only SLO carries the same exclusion.

The thresholds document is headed "Thresholds related to API server and etcd storage for
**builtin resource types**"
(https://github.com/kubernetes/community/blob/master/sig-scalability/configs-and-limits/thresholds.md):

| Quantity | scope=resource type | scope=cluster |
|---|---|---|
| Number of objects (non-Event) | 150,000 | TBD |
| Size per object | 1.5 MB | 1.5 MB |
| Total size | 1.5 GB | TBD |

Per-resource, per-namespace: 3,000 Pods, 5,000 Services (10,000 cluster-wide), 2,000
Deployments, 10,000 Namespaces, 5,000 Nodes. ConfigMaps and Secrets are literally "TBD".
The document is candid that these are soft ("crossing the limit results in degraded
performance and doesn't mean cluster immediately fails over") and that "**Many of the
thresholds (for cluster scope) are given for the largest possible cluster. For smaller
clusters, the limits are proportionally lower.**"

A request to add CRD/CR limits to this document
(https://github.com/kubernetes/community/issues/798, opened by KubeVirt in 2017) was
closed in 2020 unanswered, with a maintainer confirming cluster-wide CR quota "is not
supported today."

So 5,000 custom resources sits inside the *builtin* envelope. But Kubernetes has not
promised anything about custom resources, has not measured them, and the numbers it does
publish are for a 5,000-node cluster, not the small cluster a control plane actually runs
on. Any capacity claim here is yours to prove.

### Etcd is not the wall, and saying it is will lose the argument

Documented limits (https://etcd.io/docs/v3.5/dev-guide/limit/): max request size **1.5
MiB** (`--max-request-bytes`); storage quota **2 GiB** default (`--quota-backend-bytes`),
"8 GiB is a suggested maximum size for normal environments and etcd warns at startup if
the configured value exceeds it"; **no documented limit on number of keys**. kube-apiserver
adds a 3 MiB max request body, and 400 non-mutating / 200 mutating inflight requests.

A realistic `OpenTelemetryCollector` CR with inline pipeline config is single-digit
kilobytes; 5,000 at 20 KB is ~100 MB, about 5% of the default quota. Etcd holds this
without complaint. The naive "etcd will explode from 5,000 objects" objection is simply
wrong.

Two etcd-adjacent things do matter. A single object cannot exceed ~1.5 MiB, and the
`OpenTelemetryCollector` CRD embeds the full collector config inline: the CRD *schema
itself* is 408 KB of YAML
(`config/crd/bases/opentelemetry.io_opentelemetrycollectors.yaml`). And etcd retains no
history worth having: compaction runs on a 5-minute default timer (see Q5).

### The controller side is the wall, and the OTel Operator's own numbers are bad

Verified from source, not inferred.

**Reconcile concurrency is 1.** controller-runtime defaults `MaxConcurrentReconciles` to 1
when unset (https://github.com/kubernetes-sigs/controller-runtime/blob/main/pkg/controller/controller.go:
`if options.MaxConcurrentReconciles <= 0 { options.MaxConcurrentReconciles = 1 }`), and it
is literally the worker-goroutine count. The OTel Operator **never sets it**: grepping
`MaxConcurrentReconciles` across the whole non-test tree returns zero hits, and
`internal/operator/setup.go` builds `ctrl.Options` without it. Every collector CR is
reconciled one at a time, in one goroutine.

Drain time for 5,000 queued items at concurrency 1: ~8 min 20 s at a 100 ms reconcile,
**~1 h 23 min at a 1 s reconcile**.

**Full resync every ~10 hours, over everything.** `defaultSyncPeriod = 10 * time.Hour`
(https://github.com/kubernetes-sigs/controller-runtime/blob/main/pkg/cache/cache.go), with
±10% jitter. Its own doc comment: "SyncPeriod will locally trigger an artificial Update
event with the same object in both ObjectOld and ObjectNew for **everything that is in the
cache**." The operator does not override it. So every ~10 hours all 5,000 CRs land in a
queue drained by one worker. That is the thundering herd, and at a 1s reconcile it takes
83 minutes to clear before any error tail.

**Per-item backoff caps at 1000s (~16.7 minutes)** (client-go
`util/workqueue/default_rate_limiters.go`). Collectors outside the cluster sit behind
flaky networks; after ~12 consecutive failures a collector is retried at most once per 17
minutes. That is an operationally significant blind window for a fleet product.

**The cache holds far more than the CRs.** `SetupWithManager` calls `Owns()` for every
owned resource type (`internal/controllers/opentelemetrycollector_controller.go` lines
349-364), and `GetOwnedResourceTypes` returns ConfigMap, ServiceAccount, Service,
Deployment, DaemonSet, StatefulSet, Ingress, NetworkPolicy, HorizontalPodAutoscaler,
PodDisruptionBudget, plus ClusterRole and ClusterRoleBinding when RBAC creation is
available, plus PodMonitor and ServiceMonitor when prometheus-operator CRDs are present,
up to 14 types.

`Owns()` is not a cheap filter. Its own doc comment: "By default, this is the equivalent of
calling `Watches(source.Kind(cache, &Type{}, handler.EnqueueRequestForOwner(...)))`"
(https://github.com/kubernetes-sigs/controller-runtime/blob/main/pkg/builder/controller.go
lines 121-122): a full informer, LIST then WATCH, every object of that type held in
memory. And controller-runtime's cache starts "a new informer for every new requested
resource" by default (`ReaderFailOnMissingInformer` "Defaults to false"), listing
cluster-wide unless a namespace is set.

The operator's cache **is** cluster-wide by default. `internal/operator/setup.go` sets
`Cache: cache.Options{DefaultNamespaces: namespaces}` where `parseWatchNamespaces` returns
`nil` when `WatchNamespace` is unset, logging "watching all namespaces" (lines 222-233).
**Out of the box the OTel Operator caches every ConfigMap, Service, Deployment, DaemonSet
and StatefulSet in the entire cluster.** In a busy cluster the ConfigMap informer alone
dwarfs the CRs you care about. This is the classic operator OOM, and it is unrelated to
how many collectors you have. Mitigations exist (`--watch-namespace`, `cache.Options.ByObject`
selectors, `TransformStripManagedFields`) but the operator exposes only the first, and it
narrows what the operator can manage.

**Leader election means no horizontal scale.** `internal/operator/setup.go` configures
leader election with lease 137s / renew 107s / retry 26s. Extra replicas are standby, not
extra reconcile capacity.

### If you also render the collectors as workloads, workload thresholds bite first

Each `deployment`-mode collector CR renders a Deployment **and** a Service. 5,000
collectors in one namespace is 5,000 Deployments against a documented threshold of 2,000
per namespace, and 5,000 Services against a threshold of 5,000 per namespace / 10,000 per
cluster. You blow the Deployment threshold by 2.5x before etcd notices.

In this design most collectors are *outside* the cluster, so the CRs would be intent-only
with no rendered workload, which sidesteps this wall, but only by conceding that the
operator's actual job (rendering workloads) is not what you are using it for. Worth saying
out loud: **if the CR does not produce a Deployment, you are using CRDs as a database with
a watch API, not as an operator.**

### Kubernetes' own CRD documentation disqualifies this design, in writing

This is the cheapest and hardest argument available, and it is normative, not folklore.
https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/
lists criteria a declarative API should meet ("Your API consists of a **relatively small
number of relatively small objects**", "The objects are updated **relatively
infrequently**") and then lists explicit disqualifiers, "signs that your API might not be
declarative":

> - "Directly storing large amounts of data; for example, > a few kB per object, or **>
>   1000s of objects**"
> - "**High bandwidth access (10s of requests per second sustained) needed**"

and, standalone:

> "**Avoid using a Custom Resource as data storage for application, end user, or
> monitoring data**: architecture designs that store application data within the
> Kubernetes API typically represent a design that is too closely coupled."

A 5,000-collector fleet trips the first on count alone (5x over), and trips the second the
moment liveness is persisted (below). This is Kubernetes telling you, in its own extension
documentation, that this is not what custom resources are for.

### Write churn is the etcd failure mode, not storage

The OpAMP specification's own defaults set the load. Heartbeat interval "SHOULD be 30
seconds", and "The default polling interval when the Agent does not have anything to
deliver is 30 seconds"
(https://github.com/open-telemetry/opamp-spec/blob/main/specification.md).

5,000 collectors at one heartbeat per 30s is **~167 inbound status events per second**. If
any meaningful fraction of those writes to a CR `.status` (last-seen, health, effective-
config hash, which is the obvious design), that is ~167 etcd writes/sec from one
controller. Against that:

- The CRD-docs disqualifier is ">10s of requests per second sustained": ~17x over.
- The SIG-Scalability SLO prerequisite is cluster-wide churn <= 20/sec: ~8x over.
- Etcd is MVCC. Every write is a new revision, retained until compaction. At the default
  5-minute compaction interval that is ~50,000 accumulated revisions per window from
  collectors alone.

Exceeding the etcd quota is not graceful: per https://etcd.io/docs/v3.5/op-guide/maintenance/
it "raises a cluster-wide alarm that puts the cluster into a maintenance mode which only
accepts key reads and deletes." Cluster-wide. Recovery is manual: compact, defragment,
disarm.

**This is the design question to put to the team**, because it is the one that decides
whether the pattern survives: is per-heartbeat liveness persisted into CR status? If yes,
this breaks. If the answer is "no, we debounce, we write only on change, liveness lives
outside etcd", then the follow-up is whether the CR is still carrying enough to justify
its existence.

*Flagged as inference: the 167/sec figure assumes status is persisted per heartbeat. That
assumption has to be checked against the actual design, not assumed.*

### Reconciling external objects: the Crossplane numbers make it arithmetic, not opinion

Objects outside the cluster **cannot be watched**. They must be polled. That removes the
entire event-driven efficiency argument for using custom resources at all: you get
polling, with none of the benefits, plus etcd.

Crossplane's documented defaults (https://docs.crossplane.io/latest/guides/pods/):
`--max-reconcile-rate` **10/sec**, `--poll-interval` **1 minute**, `--sync-interval`
1 hour. And from Crossplane's own rate-limiting design one-pager
(https://github.com/crossplane/crossplane/blob/main/design/one-pager-rate-limiting.md),
verbatim:

> "A global token bucket rate limiter limits all controllers within a provider to
> `--max-reconcile-rate` reconciles per second... **All reconciles are subject to the
> global rate limiter, even those triggered by a previous reconcile returning
> `reconcile.Result{RequeueAfter: t}`.**"

The `RequeueAfter` path *is* the polling path. So:

- 5,000 external objects on a 1-minute poll needs **~83 reconciles/sec**.
- The default global limiter allows **10/sec**.
- A full pass takes 5,000 / 10 = **500 seconds ≈ 8.3 minutes**. The default poll interval
  is unachievable by ~8x.
- To actually hit it you need `--max-reconcile-rate ≈ 84`, which Crossplane's own docs
  warn "will potentially cause the provider to use up to the same number of CPUs", and
  which by the same one-pager produces an apiserver client at
  `--max-reconcile-rate * 5` qps bursting to `* 10`: **~420 qps bursting to 840**, from a
  single controller, against a cluster-wide default budget of ~600 inflight seats
  (`--max-requests-inflight` 400 + `--max-mutating-requests-inflight` 200).

**This is the clearest quantified breakdown in the whole question: the default
configuration cannot meet its own default poll interval at this fleet size, and the
configuration that could would consume the cluster's entire request budget.**

And you cannot scale out of it. Horizontal scaling of Crossplane providers has been closed
`not_planned` twice: https://github.com/crossplane/crossplane/issues/4269 (Oct 2023) and
https://github.com/crossplane/crossplane-runtime/issues/739 (**April 2026**). The only
lever is a bigger pod.

### Honest correction: the usual anti-Crossplane evidence does not apply here

Crossplane's famous scaling problems are about **CRD count (types)**: provider-aws
shipping 900+ CRDs, ~3-13 MiB of apiserver memory per CRD, O(n^2) OpenAPI merging
(https://github.com/kubernetes/kubernetes/issues/105932, fixed in v1.23). This proposal is
**one CRD with 5,000 instances**. That entire body of evidence is about the wrong axis. If
someone cites "Crossplane melts clusters" against this design they will be rebutted, and
deservedly.

The instance-count evidence is thinner but real:

- Crossplane's own benchmark, in a *good-news* post
  (https://blog.crossplane.io/new-providers-for-crossplane-donated-by-upbound-bring-up-to-4x-cost-savings/):
  1,000 `RolePolicyAttachment` managed resources on an 8-core node, **pre-2024
  architecture**: average time to Ready **19.55 minutes**, peak **95.45 minutes**, average
  CPU **95.77%**, recommended instance c4.4xlarge. The post-rewrite figures (1.012s
  average) are a vendor benchmark on a synthetic, cheap resource type; treat as
  best-case.
- User reports, anecdotal but numeric: >4,000 MRs OOMKilled, limit raised 900 MB → 2 GB
  (https://github.com/crossplane/crossplane/issues/5272, closed *not_planned*); ~400 GCP
  PubSub objects growing to **~20 GB** RSS per day with zero resource changes
  (https://github.com/crossplane-contrib/provider-upjet-gcp/issues/489); ~1,000 XRs
  showing "slower and slower sync times", mitigated only by moving poll from 1 min to 15
  min (https://github.com/crossplane/crossplane/issues/2477).

### The best real-world analogue is Argo CD, and it is sobering

Argo CD is genuinely one-CR-per-external-object at instance scale, mature, and public.

- CNOE's benchmark (https://cnoe.io/blog/argo-cd-application-scalability): at **15,000
  Applications** on one m5.2xlarge (8 vCPU, 30 GB), "CPU and Memory Usage is near 100%
  utilization of 8 vCPUs and 30 GB". A single shard managing 10k apps **deadlocked** and
  needed a controller restart.
- Production report at ~20,000 Application CRs
  (https://github.com/argoproj/argo-cd/discussions/16212): "high CPU usage is observed on
  the Kube apiserver going above **30 CPU constantly**". Mitigation was raising the sync
  interval from 3 minutes to 30 minutes. Unresolved.
- Argo CD's `Application.status` routinely approaches the **1.5 MB per-object limit**, a
  direct, lived warning about putting per-object observed state in CR status. Which is
  exactly what "report effective config back into the CR" would do.

Scaled down, 5,000 is roughly a third of the 15k figure: order-of ~3 vCPU and ~10 GB for
the controller alone, plus real apiserver load, plus sharding infrastructure. Not fatal.
But a cost to budget, not to discover.

Cluster API gives the same shape from a different angle
(https://github.com/kubernetes-sigs/cluster-api/issues/8052): 100 clusters ~15 min, **300
clusters ~135 min**, after which adding one more took >8 minutes, and critically, "For a
single workload cluster with **1000 Machines**, this was no issue at all, but when trying
to create **hundreds of single node clusters** things get very slow." Sharding by namespace
made it *worse*. **5,000 independent external collectors is the "hundreds of independent
object graphs" shape, not the "1,000 machines in one graph" shape.**

### LIST amplification, and why API Priority and Fairness will not save you

From KEP-3157 (watch-list),
https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/3157-watch-list/README.md,
verbatim:

> "The kube-apiserver is vulnerable to memory explosion. The issue is apparent in larger
> clusters, where only a few LIST requests might cause serious disruption."

> "The bottom line is around **O(5\*the_response_from_etcd)** of temporary memory
> consumption. **Neither priority and fairness nor Golang garbage collection is able to
> protect the system from exhausting memory.**"

Its reproducer: 400 Secrets of 1 MB each, and "**16 informers were able to take down the
test cluster**". The official blog corroborates: with API streaming on, memory "stabilized
at approximately 2 GB"; off, "approximately 20GB, a 10x increase"
(https://kubernetes.io/blog/2024/12/17/kube-apiserver-api-streaming/). KEP-3157 is **beta
in v1.32 and not GA**; its own post-GA item is "Increase LIST request costs in admission
flow prioritization", i.e. APF knowingly under-prices LISTs today.

APF (https://kubernetes.io/docs/concepts/cluster-administration/flow-control/) gates
concurrency, not allocation. Seats are estimated at `objectsPerSeat = 100.0` but clamped
by `MaximumListSeatsLimit: 10`, so a 150,000-object LIST estimating 1,500 seats is charged
10. By the time throttling engages, the memory is already allocated. Excess requests get
**HTTP 429**, which your controller then retries.

One piece of good news: KEP-1904 (efficient watch resumption) is **stable since v1.24**, so
watchers resume via bookmarks rather than relisting on apiserver rolling upgrade.

### Corrections to commonly-cited numbers

Worth recording, because several are stale and citing them would undermine the argument:

- **controller-runtime does not use client-go's 5 QPS / 10 burst, and no longer uses
  20/30.** It sets `cfg.QPS = -1`, disabling client-side limiting entirely, from v0.21.0
  onwards. Verified in source (above). Which behaviour you get depends on how the
  `rest.Config` was constructed; client-go's own `DefaultQPS = 5.0` still applies if you
  build it yourself. An easy trap in a project mixing both.
- **The 10 qps workqueue token bucket is not on the default path** since controller-runtime
  v0.23.0, where the priority queue became default and selects a bare exponential limiter
  with no bucket. And even when present it only gated *requeues*, never fresh informer
  events (`pkg/handler/enqueue.go` calls plain `q.Add`).
- **`--default-watch-cache-size` is a documented no-op**: "Watch caches are sized
  automatically. This flag is no-op and it will be removed in a future version."
- **Memory per cached object is not documented anywhere.** Anyone quoting "~1-2 KB per
  cached object" is guessing. Measure it on your own cluster; do not cite a number.
- **"SIG API Machinery recommends max 500 CRDs" has no locatable primary source.** Folklore.
- **The kubernetes.io blog on the controller-runtime cache (2026-07-29) carries an official
  banner**: "Some of the technical detail in this article is not accurate." Prefer source.

### The documented alternative, if Kubernetes semantics are the actual requirement

An **aggregated API server with its own storage** keeps `kubectl`, RBAC, admission, audit
and watch semantics while moving high-cardinality, high-churn data off the cluster's etcd.
The design proposal is explicit: "Each API server is responsible for storing their
resources. **They can have their own etcd** or can use kubernetes server's etcd"
(https://github.com/kubernetes/design-proposals-archive/blob/main/api-machinery/aggregated-api-servers.md).
`kubernetes/sample-apiserver` is the reference; Kine (https://github.com/k3s-io/kine)
plumbs the same storage interface over SQL; Cozystack is a worked example written up on
kubernetes.io (https://kubernetes.io/blog/2024/11/21/dynamic-kubernetes-api-server-for-cozystack/).

The trade, per the CRD docs: CRDs need no programming, aggregation "requires programming"
but gives "more control over API behaviors [including] how data is stored." An aggregated
apiserver is a database you now operate. That is a real cost, but it is the honest version
of what "5,000 collectors as custom resources" is asking for.

### Where the proposal is fine, and should be conceded

Arguing this badly loses the room. The following are true and should be said first:

- 5,000 objects is ~3% of the documented 150,000-per-resource-type threshold. Object count
  is not the problem.
- ~100 MB of config data against a 2 GiB default etcd quota is trivial.
- One CRD means none of Crossplane's CRD-count pain applies.
- RBAC, admission, audit, `kubectl` and the watch API are genuine benefits, and an
  aggregated apiserver preserves all of them while moving the storage.

The wall is not capacity. It is: no scalability guarantee for custom resources at all; a
reconcile loop with concurrency 1 and a 10-hour herd; polling arithmetic that misses its
own default interval by 8x with no horizontal scale available; and the documented advice,
from Kubernetes itself, not to use custom resources as a datastore for monitoring data.

## 4. Does anything model a multi-stage topology as CRDs?

**Verdict: nothing in OpenTelemetry does, but the negative is NOT universal, and ticket
04's finding needs restating. Four projects outside OpenTelemetry hold the tier boundary
as a real object: Elastic ECK (`Agent.spec.fleetServerRef`), kube-logging's
`LoggingRoute` (the closest match to what this product needs, Apache-2.0, CNCF Sandbox),
Splunk's shared `Queue` + `queueRef`, and Odigos's `CollectorsGroup` with a negotiated
status handshake. Two distinct proven shapes exist to copy (selector-with-resolved-status,
and shared-immutable-boundary-object), plus one idea worth stealing regardless: the
consumer advertising its accepted signals in `status` so the producer derives config from
declared capability rather than asserting it. Meanwhile in the OTel Operator the boundary
is a string in an opaque `AnyConfig` blob, and a topology CRD has been proposed four times
since 2023 and never built.**

### The OTel Operator has no object for a link between collectors

The `OpenTelemetryCollector` v1beta1 spec has no reference field pointing at another
collector. Grepping the type for reference-shaped fields
(`apis/v1beta1/opentelemetrycollector_types.go`, `apis/v1beta1/common.go`) turns up
`nodeSelector` and a Prometheus-exporter `selector` string, and nothing else. Agent-to-
gateway routing exists only as text inside `spec.config.exporters`, where it is opaque to
the API: the operator does not parse it into a relationship, and no controller knows the
two CRs are connected.

The closest thing to a cross-object relationship in the whole operator is the
TargetAllocator's binding to a collector pool, and it is not a data-flow boundary: it is
scrape-target distribution, and the binding is by config-file `collector_selector` and
naming convention rather than a typed reference in the CRD
(`apis/v1alpha1/targetallocator_types.go` has no `collectorSelector` field;
`docs/target-allocator/README.md` documents `collector_selector` as a TA config-file key).

### The near-miss: `ClusterObservability`

`ClusterObservability` (Q1) is the only CR in the ecosystem that generates a two-tier
deployment from a single object: an agent DaemonSet collector plus a cluster StatefulSet
collector plus an Instrumentation CR
(`docs/collector/cluster-observability.md`). It even holds *one* boundary, the terminal
egress, as structured, typed fields rather than a string: `spec.exporter` is a full
`OTLPHTTPExporter` with endpoint, per-signal endpoint overrides, TLS, timeout, sending
queue, retry, compression and headers (`apis/v1alpha1/clusterobservability_types.go`).

But the boundary it models is cluster-to-backend, not tier-to-tier. Both generated
collectors export to the same destination; neither exports to the other. And the agent-tier
endpoint that instrumented applications use is derived by convention, not modelled:
"instrumented applications... send telemetry to their local node's collector using
`$(OTEL_NODE_IP):4317` or `$(OTEL_NODE_IP):4318`".

### The refusal is explicit, and it is in writing

The design RFC for this CR, `docs/rfcs/managed.md` (Antoine Toulme, 2025-03-20), has a
goals section headed **"OTLP, single endpoint support"** which states:

> "The solution exports data to a single endpoint using the OTLP protocol. **Users may
> choose to deploy a gateway to transform, filter, redact data before sending it to
> storage.**"

That is the gateway tier being named and then placed outside the model, by design. The
same RFC's next non-goal is "Do not offer a way to turn on and off specific features."

So the operator's own answer to "does anything hold the tier boundary" is: no, and we
chose not to. This corroborates ticket 04's finding rather than contradicting it, and it
does so from the horse's mouth rather than by absence of evidence.

### It has been proposed in the OTel Operator four times and never built

This matters more than the absence itself: the gap is known, requested, and unaddressed.

- [#1906 "Distributed collector configuration"](https://github.com/open-telemetry/opentelemetry-operator/issues/1906):
  **still open**, opened 2023-07-11, last comment 2025-09-01. Contains a maintainer
  sketch of `OpenTelemetryGateway` / `OpenTelemetryExporter` / `OpenTelemetryAgent` CRDs,
  and a later `CollectorGroup` CRD proposal from pavolloffay.
- [#2128 "Add a Gateway and Exporter CRD"](https://github.com/open-telemetry/opentelemetry-operator/issues/2128):
  closed as duplicate of #1906.
- [#3956](https://github.com/open-telemetry/opentelemetry-operator/issues/3956)
  (fluent-operator-style modular pipelines): closed as duplicate of #1906.
- [#1477 "Proposal: Opinionated Operator CRDs"](https://github.com/open-telemetry/opentelemetry-operator/issues/1477):
  open since Feb 2023.

There is **no RFC on topology** in `docs/rfcs/`; the seven RFCs there cover CRD
graduation, docs, instrumentation v1beta1, managed state and webhook HA.

Also worth noting: in v1beta1 the config is typed only one level deep. `spec.config` has
`receivers`/`exporters`/`service` required and `processors`/`connectors`/`extensions`
optional, but **each is an `AnyConfig`**: "AnyConfig represent parts of the config". The
exporter endpoint that *is* the tier boundary sits inside a blob the operator cannot type,
validate or reference.

And the operator already has the exact mechanism, applied to the wrong relationship. Per
`docs/target-allocator/README.md`: you set `opentelemetry.io/target-allocator: <name>` on
the collector CR, and the operator **derives** the endpoint and rewrites the config to
`target_allocator: endpoint: http://<name>-targetallocator:80`. Object-reference-plus-
derived-endpoint, exactly the pattern; it just binds collector to target-allocator, never
tier to tier.

### The four projects that DO hold the boundary as an object

None is OpenTelemetry. Two distinct shapes emerge, plus one idea worth stealing.

#### `LoggingRoute` (kube-logging/logging-operator). The closest match, and Apache-2.0.

The type doc-comment reads, verbatim: "**LoggingRoute: Connects a log collector with log
aggregators from other logging domains and routes relevant logs based on watch
namespaces**"
([`loggingroute_types.go`](https://github.com/kube-logging/logging-operator/blob/master/pkg/sdk/logging/api/v1beta1/loggingroute_types.go)).

```go
type LoggingRouteSpec struct {
    Source  string               `json:"source"`   // the Logging whose collector this applies to
    Targets metav1.LabelSelector `json:"targets"`  // aggregator-tier Logging resources
}
type LoggingRouteStatus struct {
    Tenants  []Tenant `json:"tenants,omitempty"`   // resolved bindings, namespaces expanded
    Problems []string `json:"problems,omitempty"`  // boundaries that failed to bind
    Notices  []string `json:"notices,omitempty"`
}
```

Cluster-scoped, shortName `lr`, status subresource. Three properties make it the real
thing:

1. **The endpoint is never written down.** Targets are selected by label over `Logging`
   objects; the operator resolves each target's aggregator service itself.
2. **The routing predicate is derived from the target's own declaration**: the target
   `Logging`'s `watchNamespaces` determines what it receives. The consumer declares what it
   accepts; the producer does not guess.
3. **Status reports whether the boundary bound.** `status.problems` names boundaries that
   block a tenant from receiving anything.

Apache-2.0, [CNCF Sandbox since 2023-09-19](https://www.cncf.io/projects/logging-operator/).
Note its OpenTelemetry successor,
[telemetry-controller](https://github.com/kube-logging/telemetry-controller), **regressed**:
its `Bridge` connects two logical tenants inside one collector, the collector is
DaemonSet-only with no aggregator tier, and `Output` bottoms out in
`GRPCClientConfig.Endpoint *string`.

#### `Queue` + `queueRef` (splunk/splunk-operator). The shared-boundary-object shape.

`docs/IndexIngestionSeparation.md`: "Queue is introduced to store message queue information
to be **shared among** IngestorCluster and IndexerCluster." Both
[`IngestorClusterSpec`](https://github.com/splunk/splunk-operator/blob/main/api/v4/ingestorcluster_types.go)
and [`IndexerClusterSpec`](https://github.com/splunk/splunk-operator/blob/main/api/v4/indexercluster_types.go)
carry `QueueRef corev1.ObjectReference`, required and **CEL-immutable** on the ingestor
(`rule="self.queueRef == oldSelf.queueRef"`). `QueueSpec` holds the contract itself
(provider, SQS name, auth region, DLQ, endpoint).

One object, referenced from both the producing and consuming tier, immutable after
creation. Caveats: Splunk-proprietary (GitHub reports `NOASSERTION`), requires Splunk
Enterprise 10.2+, and the boundary is a durable SQS queue rather than a collector protocol
endpoint.

#### `Agent.spec.fleetServerRef` (Elastic ECK). Verified directly.

`pkg/apis/agent/v1alpha1/agent_types.go`:

```go
Mode               AgentMode                    `json:"mode,omitempty"`               // "standalone" | "fleet"
FleetServerEnabled bool                         `json:"fleetServerEnabled,omitempty"`
FleetServerRef     commonv1.FleetServerSelector `json:"fleetServerRef,omitempty"`
KibanaRef          commonv1.ObjectSelector      `json:"kibanaRef,omitempty"`
ElasticsearchRefs  []Output                     `json:"elasticsearchRefs,omitempty"`
PolicyID           string                       `json:"policyID,omitempty"`
```

Doc-comment on the load-bearing field: "**FleetServerRef is a reference to Fleet Server
that this Agent should connect to obtain its configuration.**" The gateway tier is itself
an `Agent` CR with `fleetServerEnabled: true`.

The reference is *resolved*, not decorative. ECK runs a dedicated association controller
for exactly this edge, `pkg/controller/association/controller/agent_fleetserver.go`, with
its own `commonv1.FleetServerAssociationType`. It derives the upstream endpoint from the
referenced CR (`ExternalServiceURL: getFleetServerExternalURL`, resolving the Service URL
rather than taking a user string) and copies the CA secret into the downstream namespace.
`FleetServerSelector` additionally carries `ClientCertificateSecretName`, with ECK
auto-generating a client cert if the upstream requires mTLS.

So ECK covers endpoint + transport + auth. **But the data half escapes Kubernetes**:
`PolicyID` is an opaque pointer into Fleet/Kibana, and agent policies and integrations are
not CRs. It models who-talks-to-whom and how they authenticate, not what flows. Elastic
License 2.0 (Q6).

#### `CollectorsGroup` (Odigos). The idea worth stealing.

[`collectorsgroup_types.go`](https://github.com/odigos-io/odigos/blob/main/api/odigos/v1alpha1/collectorsgroup_types.go):
`Role` is a kubebuilder enum **`CLUSTER_GATEWAY;NODE_COLLECTOR`**: the tier is a typed
field. `OtlpExporterConfiguration` is doc-commented as "the configuration for the OTLP
exporter from node collector to cluster gateway collector".

The interesting artefact is in status: `CollectorsGroupStatus.ReceiverSignals`: "the
signals (trace, metrics, logs) that the collector has setup an otlp receiver for, thus it
can accept data from an upstream component. **this is used to determine if a workload
should export each signal or not**." The downstream tier publishes what it will accept;
the upstream tier reads it to decide what to send. That is a **negotiated** boundary
contract expressed through the API server, and there is no equivalent anywhere in
OpenTelemetry.

Caveat: it is not user-facing. The CRD is labelled `odigos.io/system-object: "true"` and
instances are constructed by the operator's own scheduler, a materialised intermediate,
not a contract users author. Apache-2.0, vendor-controlled, not CNCF.

### Everywhere else: the boundary is a string

- **prometheus-operator.** `RemoteWriteSpec.URL` is a bare `URL` string, `+required`
  (`pkg/apis/monitoring/v1/prometheus_types.go`). No object reference, no
  `RemoteWriteConfig` CRD, no federation CRD. `PrometheusAgent` inherits the same shape.
  Important distinction: the famous selector pattern (`Prometheus` selects
  `ServiceMonitor`s) is **configuration-to-instance binding within one tier**, often cited
  as prior art for distributed config, and not the thing being asked about.
- **fluent/fluent-operator: the most instructive negative.** The two-tier topology is real
  and first-class in the *deployment* model (Fluent Bit DaemonSet → Fluentd StatefulSet
  "log forward layer") and objects exist on both sides:
  `ClusterOutput.spec.forward` with `Host`/`Port`/`SharedKey`, and
  `Fluentd.spec.globalInputs[].forward` with `port`/`bind`/`security`. **Neither references
  the other.** The join happens in Helm at template time, string-building
  `host: {{ printf "%s.%s.svc.cluster.local" ... }}`. Nothing validates that the sending
  `sharedKey` matches the receiving `security` block. Objects on both sides of the wire, a
  shared-secret handshake, and still mutually unaware.
- **Grafana.** `grafana/alloy-operator` is one CR (`Alloy`, `collectors.grafana.com/v1alpha1`)
  wrapping the Helm chart; the destination lives inside an unparsed River string. The
  deprecated Grafana Agent Operator's `GrafanaAgent`→`MetricsInstance` link is a **label
  selector** borrowed from prometheus-operator, and its destination is
  `RemoteWriteSpec.URL string`. Archived, [EOL 2025-11-01](https://github.com/grafana/agent).
  `grafana/grafana-operator` manages Grafana itself, not collector topology.
- **Vector.** No official operator exists; the `vectordotdev` org has only `k8s-openapi`
  (archived fork) and `vector-k8s-examples`. Agent vs Aggregator is a Helm `role` value.
- **Dash0.** Ten CRDs; the boundary is an `Export` one-of over `dash0`/`http`/`grpc`, each
  bottoming out in `Endpoint string`. No tiering.
- **Bindplane.** The distinction is decisive: `observIQ/bindplane-operator` defines **one**
  CRD (`Bindplane`) which deploys the *server*. The Configuration / Source / Destination /
  Processor / Connector / **Fleet** model (the richest routing model in this survey) lives
  in Bindplane's **proprietary server API**, surfaced via Terraform. It is not a Kubernetes
  object.
- **Datadog.** `DatadogAgent` collapses both tiers into one CR via
  `override: {nodeAgent, clusterAgent, clusterChecksRunner, otelAgentGateway}`. The only
  surfaced boundary artefact is `global.clusterAgentToken`. Most collapsed model of the set.
- **Gateway API for telemetry.** Used only for ingress *into* a collector, never tier-to-
  tier. `OpenTelemetryCollectorSpec.httpRoute` attaches to an ingress Gateway by name. **No
  `TelemetryRoute` exists anywhere.**

### What this means

The consistent industry pattern: operators model **tiers as workloads** and **config as
selectable fragments**, but the **wire between tiers as a bare string**. fluent-operator has
objects on both sides of the wire and still leaves them mutually unaware. Datadog hides the
boundary inside one CR. OpenTelemetry's newest opinionated CRD deploys two tiers and routes
both straight past each other to the backend.

Ticket 04's finding should be restated: it is not that *nothing* holds the tier boundary,
it is that **nothing in the OpenTelemetry ecosystem does**, and the four projects that do
are split between a proprietary licence (ECK, Splunk), an operator-internal object
(Odigos), and one genuinely adoptable open-source design (kube-logging's `LoggingRoute`,
Apache-2.0, CNCF Sandbox).

That is a stronger position for the product, not weaker. Two proven shapes exist to copy:

1. **Selector with resolved status** (`LoggingRoute`): the producer names consumers by
   label, the operator derives endpoints, and status reports what bound and what failed.
2. **Shared immutable boundary object** (Splunk `Queue`): both tiers objectRef a third
   object that holds the contract.

Plus one idea worth stealing regardless of shape: **the consumer advertising its accepted
signals in `status`** (Odigos `ReceiverSignals`), so the producer's config is derived from
the consumer's declared capability rather than asserted independently. The request for any
of this in OpenTelemetry ([#1906](https://github.com/open-telemetry/opentelemetry-operator/issues/1906))
has been open for three years.

## 5. What an operator does NOT give you

**Verdict: everything the ticket suspected, and one more. There is no graphical surface,
no query API beyond the Kubernetes API's own label and field selectors, no config history
at all (etcd retains roughly five minutes), and nothing whatsoever for collectors with no
Kubernetes near them. The extra one: the in-process OpAMP extension in the Collector
cannot apply remote config, so non-Kubernetes collectors require the OpAMP Supervisor,
which is alpha.**

### No graphical surface

There is no UI in the repository. No `ui/`, `web/`, `frontend/` or `console/` directory
exists; the only `package.json` in the tree is an end-to-end test fixture
(`tests/test-e2e-apps/nodejs/package.json`). The closest thing to an operator-side
diagnostic tool is `cmd/gather`, a must-gather that dumps cluster state to disk for
support tickets (`cmd/gather/README.md`). Operator status surfaces are CR
`status` blocks and Kubernetes Events, read with `kubectl describe`
(`docs/collector/cluster-observability.md`, Troubleshooting).

### No query API for a console

The Kubernetes API server is the only query surface. Its query model is: get by
namespace/name, or list a single kind filtered by label selector or a small set of
indexed field selectors. There is no join, no aggregation, no full-text search, no
"which collectors export to endpoint X" without listing every object and filtering
client-side, which is exactly the access pattern that hurts most at 5,000 objects (Q3).
The bridge already demonstrates the pattern: `listOpenTelemetryCollectors`
(`internal/operator/client.go`) does two full cluster-wide `List` calls per invocation,
one per label selector, and is called on every health tick and every effective-config
request.

### No audit trail of rendered configs

etcd is not a history store. The kube-apiserver compacts etcd revisions on a timer:
`--etcd-compaction-interval` defaults to `5m0s`
(https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/,
implementation at
https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/storage/etcd3/compact.go).
Once compacted, superseded revisions are unrecoverable; this is a storage-reclamation
mechanism, not retention. A CR carries `metadata.generation` and `metadata.resourceVersion`,
but neither is a pointer to retrievable prior content.

Kubernetes audit logging is also not this. It records *API requests* against a policy, to
a log sink, with configurable retention; it answers "who changed this and when", not
"what was the rendered collector config on 3 June". And the object stored in etcd is the
CR, not the rendered `otelcol` YAML; the rendering happens in the operator's manifest
generation at reconcile time. Nothing persists the render.

For a product that has to answer "what config was this collector running when it dropped
data", config history is net-new build.

### Nothing for collectors with no Kubernetes near them

This is the largest gap and it is total. Both of the bridge's config appliers write
through the Kubernetes API (Q2). The `OpenTelemetryCollector` CRD renders Kubernetes
workloads. The Target Allocator distributes targets to collectors it discovers via the
Kubernetes API. The `Instrumentation` CRD works by pod admission webhook. Every component
in the operator assumes a cluster.

The OpenTelemetry answer for non-Kubernetes collectors lives elsewhere, and is
immature on the piece that matters:

- **`opampextension`** (`opentelemetry-collector-contrib/extension/opampextension`):
  **alpha**. Reports effective config, health and available components by default;
  accepts a restart command behind a feature gate. It **cannot apply remote
  configuration to the collector**. Config must arrive through the Collector's own
  `--config` sources; the extension only sends SIGHUP to trigger a reload, and an invalid
  config leaves the Collector down requiring manual intervention.
- **`opampsupervisor`** (`opentelemetry-collector-contrib/cmd/opampsupervisor`):
  **alpha**. This is the component that actually accepts remote config, writes it, and
  manages the Collector process. Reports effective config, own telemetry and health;
  accepts restart. Package/agent updates and full status reporting are still under
  development. Runs as a standalone binary on Linux, macOS and Windows; Kubernetes not
  required.

So the non-Kubernetes path is: your OpAMP server → Supervisor → Collector. That is a
different agent-side component, a different lifecycle, a different failure model and a
different install story from the in-cluster path, and the load-bearing piece is alpha.
Any claim of "one control plane for in-cluster and remote alike" has to survive the fact
that the two halves share only the protocol.

### Also absent, worth naming

- **Multi-cluster.** One operator governs one cluster. Nothing aggregates across clusters;
  you would run one bridge per cluster, each a single non-HA pod (Q2).
- **Authorisation beyond RBAC.** The bridge's only policy control is
  `componentsAllowed`, a flat allow-list of receiver/processor/exporter names, and two
  labels (`opamp-managed`, `opamp-reporting`). There is no notion of who may change what.
- **Reconciliation of anything that isn't a Kubernetes object.** See Q3.

### The one that needs care: Elastic License 2.0

ECK is not open source. ELv2 (https://www.elastic.co/licensing/elastic-license) imposes
three limitations, the first of which is the live one:

> "You may not provide the software to third parties as a hosted or managed service, where
> the service provides users with access to any substantial set of the features or
> functionality of the software."

Plus: no circumventing licence-key functionality, and no removing notices. If this product
is ever offered as a hosted or managed service, embedding or redistributing ECK is a
licence problem. Depending on it for reference or interop is not.

### Grafana's AGPL relicensing did NOT hit the agent line

Worth checking explicitly because the assumption usually runs the other way. Grafana core
is AGPL-3.0, and the 2021 relicensing covered Grafana, Loki, Tempo and Mimir. It did **not**
cover the agent line: `grafana/alloy`'s LICENSE is the Apache License 2.0 verbatim, as are
`grafana-operator`, `alloy-operator` and the archived `grafana/agent`. Verified by reading
each `LICENSE` file.

### Governance notes that matter more than the licences

- **OpenTelemetry graduated CNCF on 11 May 2026**
  (https://www.cncf.io/announcements/2026/05/21/cloud-native-computing-foundation-announces-opentelemetrys-graduation-solidifying-status-as-the-de-facto-observability-standard/).
  Read this correctly: graduation is a statement about project governance, adoption and
  process maturity. It says nothing about per-component API stability. The operator is
  still v0.156.0 with `v1alpha1` APIs on four of its five CRDs, and the OpAMP spec is
  still Beta.
- **The OpAMP bridge is a peripheral component even within its own project.** The official
  OpenTelemetry operator page at
  https://opentelemetry.io/docs/platforms/kubernetes/operator/ does not mention the OpAMP
  bridge or the `OpAMPBridge` CRD at all. The operator's own README describes the operator
  as managing "the OpenTelemetry Collector" and "auto-instrumentation"; the bridge is not
  in that sentence.
- **There is no OpAMP server in the OpenTelemetry org.** A search of the org returns
  exactly three OpAMP repositories: `opamp-spec`, `opamp-go`, and `opamp-java`
  (**archived**). `opamp-go` does ship a `server` package
  (https://github.com/open-telemetry/opamp-go/tree/main/server, HTTP and WebSocket
  connection handling, Apache-2.0), which is what the operator's bridge proxy is built
  on. So building an OpAMP server means implementing policy and state on top of a
  maintained Apache-2.0 protocol library, not implementing the wire protocol.
- **Maintainer bench.** The OTel Operator has four maintainers (Red Hat x2, Omlet,
  Elastic) and four approvers (Splunk, Coralogix, Honeycomb, OllyGarden). Broad enough to
  not be vendor-captured, thin enough that a single maintainer's departure is felt. Release
  management rotates one-per-release through that same list (`RELEASE.md`).
- **cert-manager is a transitive hard dependency** of the OTel Operator (conversion and
  admission webhooks). It is Apache-2.0 and CNCF Graduated, so this is benign, but it is a
  second operator you must run and upgrade.
