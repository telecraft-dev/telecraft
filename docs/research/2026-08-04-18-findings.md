# Findings: Can Backstage be the surface and the register?

Ticket: `issues/18-backstage-as-surface-and-register.md`
Researched: 4 August 2026
Method: primary sources first (backstage.io docs, backstage/backstage source and
schemas, kubernetes.io, headlamp.dev, kubernetes-sigs/headlamp), with vendor and
secondary material used only for cost figures and labelled as such.

## Summary verdict

**Backstage should not be the primary surface.** It fails on the one requirement
the design cannot compromise on, which is authoring, and it fails structurally
rather than incidentally: the Backstage catalogue has no write API for entities
by deliberate design, its source of truth is YAML in Git, and its relation model
cannot carry a first-class Hop. A Backstage plugin *can* host a real editor,
because a plugin is an arbitrary React application with an arbitrary backend, but
that editor would be writing to our own store through our own API, so it buys
nothing except the shell, and it charges the full Backstage adoption cost for it.

The cost, stated plainly and in the direction that matters: **the plugin is one
to three engineer-weeks, and the Backstage it needs is 3 engineers for 6 to 12
months to stand up and 2 engineers permanently to keep running.** That cost lands
on the adopter, not on us, which makes it worse than an internal cost, because we
would be imposing it on every user who wants the product.

Recommendation: **optional surface over an API, later, and only on request.**
Build the authoring surface as a small purpose-built console. If a second,
Kubernetes-native surface is wanted, price a Headlamp plugin before a Backstage
plugin: Headlamp costs days, supports genuine writes to custom resources, needs
no fork and no rebuild, and is now the Kubernetes project's own recommended UI.

## 1. The catalogue as the register

**Verdict: it can carry the two axes, and it cannot carry the Hop. As a register
it would be a read-only mirror of the custom resources, never the register
itself.**

### What the model provides

Nine built-in kinds: Component, Template, API, Group, User, Resource, System,
Domain, Location.
<https://backstage.io/docs/features/software-catalog/descriptor-format/>

Every entity carries `metadata.labels`, `metadata.annotations`, `metadata.tags`,
`metadata.links`, plus a kind-specific `spec`. Relations and status are
explicitly **output-only**.

### The two axes fit, cheaply

Criticality Tier and Classification can both be carried. Three viable placements,
in increasing order of risk:

1. **Annotations.** Docs state annotations are "arbitrary metadata for external
   systems", keys take an optional lowercase-domain prefix plus a name, the
   `backstage.io/` prefix is reserved, and values are unconstrained strings. So
   `ampup.io/criticality-tier: "1"` and `ampup.io/classification: pii` are
   entirely within the sanctioned model.
2. **Labels.** Same namespacing rules, but values are constrained to the same
   character set as `metadata.name`, so a free-form user-chosen Classification
   value could collide with that constraint. Ticket 07 made the values the
   user's, which argues for annotations over labels.
3. **Custom `spec` fields.** The Component JSON schema in
   `packages/catalog-model/src/schema/kinds/Component.v1alpha1.schema.json`
   requires `type`, `lifecycle`, `owner` and does **not** set
   `additionalProperties: false` anywhere in `spec` or `metadata`. Extra fields
   therefore validate. The docs warn that "general plugins and tools may not be
   able to understand their semantics".
   <https://backstage.io/docs/features/software-catalog/extending-the-model/>

The extension guide ranks these itself: new `type` values and annotations/labels
are low risk, custom relation types are emittable from a processor without
backend changes, and **new kinds are high risk**, because "most plugins will be
compiled against the builtin `@backstage/catalog-model` package and have
expectations that kinds align with that".

### Where it breaks: the Hop

Ticket 07's central bet is that the **edge** is first-class and carries its own
properties: trust (derived, overridable), and the delivery expectation derived
from a Path.

Backstage relations are `{ type, targetRef }` and nothing else. They are
read-only, they are computed during stitching from `spec` fields by processors,
and there is no place on a relation to hang trust, a derived expectation, or any
other attribute. Relations are also not addressable, so nothing can reference "a
Hop" as an object.

That leaves two options, both bad:

- Model a Hop as an entity of a **custom kind**, which is the extension the
  Backstage docs themselves flag as the high-risk one, and which strands the Hop
  outside every catalogue UI, search result and graph view that assumes the nine
  built-in kinds.
- Model a Hop as a `Resource` with annotations, which type-launders the design's
  central object into a kind that means "infrastructure a component needs", and
  still leaves the Hop's endpoints expressed as ordinary relations with no
  guarantee that only two exist or that they are directed as intended.

Similarly, Path is "an application's route through the Stage graph" and an
application may have several. A set of ordered edges per application has no
representation in a model whose only edge type is an unordered, unattributed,
derived relation.

### Ingestion, and whether a processor can own a field

Yes, and the split is clean.
<https://backstage.io/docs/features/software-catalog/life-of-an-entity/>

- **EntityProvider**: owns a private bucket of entities sourced from an external
  authoritative system, and manages the full add/update/delete lifecycle. "No two
  providers can output the same entity."
- **CatalogProcessor**: runs in the processing loop, validates and **mutates**
  entities, emits relations, reports errors. Processors cannot delete.
- **Stitching**: merges the processed entity with incoming and outgoing relations
  into the object served by the API.

So a custom processor can absolutely own a field, and a custom provider can make
Kubernetes custom resources the authoritative source of catalogue entities. There
is a working precedent: TeraSky's `kubernetes-ingestor` is a backend catalogue
entity provider that ingests standard workloads plus arbitrary user-supplied
GVKs, auto-ingests Crossplane claims as Components, and keeps the catalogue in
sync as cluster state changes.
<https://github.com/TeraSky-OSS/backstage-plugins/tree/main/plugins/kubernetes-ingestor>

But note what that precedent actually is: **the cluster is the register and the
catalogue is a downstream projection of it.** That is the correct architecture,
and it is also an admission that the catalogue is not the register.

### The decisive quote

> "The source of truth for the components in your software catalog are metadata
> YAML files stored in source control (GitHub, GitHub Enterprise, GitLab, ...)."
> "Teams owning the components are responsible for maintaining the metadata about
> them, and do so using their normal Git workflow."

<https://backstage.io/docs/features/software-catalog/>

## 2. What a plugin costs, and whether it can ship standalone

**Verdict: the plugin ships standalone as an npm package; Backstage does not. The
plugin is small. The application it requires is the entire cost, and the adopter
owns it.**

### The plugin itself

- **Language and framework**: TypeScript and React, Material UI, built with the
  Backstage CLI. Plugins are yarn workspace packages with their own
  `package.json` and `src/`, and the docs describe this as "enabling distribution
  as separate npm packages".
  <https://backstage.io/docs/plugins/structure-of-a-plugin/>
- **Generated scaffolding**: `plugin.ts` (`createPlugin` /
  `createRoutableExtension`, or `createFrontendPlugin` / `PageBlueprint` in the
  new system), `routes.ts`, example components, a `dev/` folder with a standalone
  dev server, `setupTests.ts`. Most of it is example code the author deletes.
- **Creation**: `yarn new` from the app root, choosing `frontend-plugin`.
  <https://backstage.io/docs/plugins/create-a-plugin/>
- **Backend plugins are genuinely capable**: `createBackendPlugin()`, own HTTP
  routes via `httpRouter.use()`, own logical database per plugin with migrations,
  arbitrary outbound calls.
  <https://backstage.io/docs/backend-system/building-plugins-and-modules/index/>
  Architecture overview confirms "a separate logical database per plugin".
  <https://backstage.io/docs/overview/architecture-overview/>

So the plugin code proper, for a graph editor plus a K8s write path, is small.
Call it **1 to 3 engineer-weeks** for a first useful version, most of which is
the canvas, and none of which is Backstage-specific.

### Shipping outside the monorepo

Two separate questions, with two different answers.

**Can we publish a plugin without maintaining a Backstage fork?** Yes. The
marketplace at <https://backstage.io/plugins> lists 249 active and 58 inactive
third-party plugins, distributed as npm packages from independent repositories.
Nothing requires our plugin to live in `backstage/backstage`.

**Can an adopter run our plugin without maintaining a Backstage app?** No,
upstream. `npx @backstage/create-app` produces a repository the adopter owns:
`app-config.yaml`, `packages/app` (frontend), `packages/backend`, `plugins/`.
Installing a plugin means adding the dependency to `packages/app` and either
editing `packages/app/src/App.tsx` or relying on feature discovery.

The new frontend system does remove the `App.tsx` edit:

```yaml
app:
  packages: all
```

"any plugin that is added as a dependency of your app package will be
automatically discovered and installed", and this is the default for new apps.
<https://backstage.io/docs/frontend-system/building-apps/installing-plugins/>
But discovery is a **build-time** mechanism, hooked into the webpack compilation,
so the app is still rebuilt and redeployed.
<https://backstage.io/docs/frontend-system/architecture/app/>

The only true runtime-load path is a downstream distribution, not upstream
Backstage: Red Hat Developer Hub's **dynamic plugins**, loaded from npm, tarballs
or OCI images and enabled with a restart rather than a rebuild, using `rhdh-cli
export-dynamic-plugin` to repackage a standard plugin.
<https://developers.redhat.com/articles/2025/11/20/how-build-your-dynamic-plug-ins-developer-hub>
Supporting that is a second packaging target and a second compatibility matrix.

### The adopter's floor, from Backstage's own prerequisites

> 20 GB disk, 6 GB memory, Unix-like OS, GNU build tools, Node.js Active LTS
> (22 or 24), Yarn 4.4.1 via corepack, Docker, Git, ports 3000 and 7007.

<https://backstage.io/docs/getting-started/>

That is for the demo app. Production adds PostgreSQL, an auth integration, a
cache (memcache, Redis, Valkey or Infinispan), containerisation and ingress.

## 3. Graphical composition: can Backstage host an editing surface?

**Verdict: Backstage's catalogue is read-and-browse only, by design, and its
graph views are visualisation only. But a Backstage plugin is an arbitrary React
app with an arbitrary backend, so genuine graph editing is buildable inside
Backstage, provided the backing store is ours and not the catalogue.**

This is the answer the ticket asked for, and it splits, so both halves need
stating.

### The read-only half is confirmed, hard

1. **No write API for entities.** The catalogue REST API exposes
   `GET /entities`, `GET|POST /entities/by-query`, `GET /entities/by-uid/...`,
   `GET /entities/by-name/...`, `POST /entities/by-refs`, `POST /validate-entity`.
   Writes are limited to `POST /locations`, `DELETE /locations/{id}`,
   `POST /refresh`, and `DELETE /entities/by-uid/<uid>`. **There is no POST or
   PUT that creates or updates an entity.**
   <https://backstage.io/docs/features/software-catalog/software-catalog-api/>
2. **The catalogue graph plugin is a viewer.** `catalog-graph` "visualizes the
   relations between entities" and lets users "navigate through the entities and
   filter for specific relations". It exports `EntityCatalogGraphCard`,
   `CatalogGraphPage` and `EntityRelationsGraph`. There is no edge creation, no
   `onConnect`, no persistence path.
   <https://github.com/backstage/backstage/tree/master/plugins/catalog-graph>
   This matches ticket 04's finding about the wider landscape exactly: Alloy's UI
   is read-only, otelbin's graph is one-way. Backstage is another instance of the
   same pattern, not an exception to it.
3. **Relations are output-only and derived.** They cannot be authored, so the
   graph the user would want to edit is not a graph Backstage lets anyone write.
4. **The sanctioned write paths are Git-shaped.** The Scaffolder creates
   repositories and pull requests from templates; `catalog-import` registers a
   location, which means committing a descriptor file. Editing is a pull request,
   not a drag.

### The editable half is also real

Backstage does not prohibit editing. It prohibits editing *the catalogue*.

- **Announcements** (`@backstage-community/plugin-announcements`) provides "pages
  to list, view, create, edit and delete announcements", with its own database
  model, its own REST endpoints under `/api/announcements/...`, permission
  integration and audit logging.
  <https://www.npmjs.com/package/@backstage-community/plugin-announcements>
- **Orchestrator** (Red Hat / SonataFlow) embeds a graphical workflow surface in
  Backstage and calls out to a workflow engine through a backend proxy plugin.
  <https://github.com/redhat-developer/rhdh-plugins/blob/main/workspaces/orchestrator/README.md>
- Nothing stops a plugin depending on `reactflow` or any other npm package. The
  docs state plugins "depend on other plugins via regular npm dependencies", and
  a plugin is an ordinary React package.

So a Stage/Hop/Path canvas inside Backstage is technically possible. What it is
not, is *reuse*. It reuses the shell, the routing and the sign-in. It reuses none
of the catalogue, because the catalogue cannot store the authored objects. Every
line of the editor, its state model, its validation, its API client and its
write path is ours either way.

**Plainly, for the ticket's framing:** Backstage is fundamentally a
read-and-browse developer portal over data owned elsewhere. It is not a modelling
tool, and it has no editing idiom to inherit. It therefore cannot be the primary
surface on the strength of the catalogue, because the catalogue contributes
nothing to authoring.

## 4. The adoption cost, stated without diplomacy

**Verdict: expensive, and expensive in the specific way that is worst for this
project, because the cost is paid by the adopter, up front, before they get any
value from our software. "Develop as little as we can" and "adopt Backstage" do
not merely pull in opposite directions. Backstage is the single most expensive
dependency on the table, and the thing it would save us building is the cheapest
thing we have to build.**

### How many people run it

- `ADOPTERS.md` in the repository names roughly 100 organisations: Spotify,
  Netflix, American Airlines, Zalando, Epic Games, Box, VMware, Unity, Splunk,
  Snyk, Expedia-scale names.
  <https://github.com/backstage/backstage/blob/master/ADOPTERS.md>
- CNCF status: accepted 8 September 2020, **Incubating** since 15 March 2022, no
  graduation as of August 2026. <https://www.cncf.io/projects/backstage/>
- A figure of 3,400 adopters circulates in secondary write-ups of the 2025 State
  of Backstage report. Treat it as unverified: the report is published by Roadie,
  a Backstage vendor, and self-reported adopter counts have no denominator.

Either way, the comparison that matters is not absolute. It is that the set of
organisations running Kubernetes and OpenTelemetry is one or two orders of
magnitude larger than the set running Backstage. **Requiring Backstage shrinks
the addressable set to a subset of a subset.** Offering Backstage costs nothing
in reach. Requiring it costs most of it.

### The operational burden

Vendor sources first, flagged as vendor, because they are the only ones with
numbers:

- Roadie (sells hosted Backstage, so biased upward): **3 full-time engineers for
  6 to 12 months** to reach production; **2 full-time engineers ongoing**, with
  20% of that time on upgrades and migrations. Modelled totals: $762,000 year 1,
  $512,000 per year thereafter, at $125,000 fully loaded per senior platform
  engineer, plus $12,000 infrastructure.
  <https://roadie.io/blog/backstage-how-much-does-it-really-cost/>
- platformengineeringcost.com: $200k to $1.2M all-in for a self-hosted IDP;
  3 to 12 FTE for orgs satisfied with their self-hosted setup; a three-year TCO
  of $1.52M modelled for 200 developers; **2 to 5 engineer-days per custom plugin
  per release cycle**. <https://platformengineeringcost.com/backstage-cost>
- Port and Qovery, both competitors, publish similar critiques. Discount the
  framing, but the direction is unanimous across parties with opposite incentives
  only in degree, never in sign.

Now the non-vendor corroboration, which matters more:

- **The upgrade treadmill is verifiable from Backstage's own docs.** Backstage
  shipped a new backend system and then a new frontend system, each with its own
  migration guide. Plugin migration means rewriting `plugin.ts` from
  `createPlugin` to `createFrontendPlugin`, converting routable extensions to
  `PageBlueprint`, converting APIs to `ApiBlueprint`, and adding an
  `src/alpha.tsx` entry point. The guidance is to *keep both systems working*:
  "we recommend all plugins to keep support for the old system intact".
  <https://backstage.io/docs/frontend-system/building-plugins/migrating/>
  That is a maintained dual code path for every third-party plugin, indefinitely.
- **Breaking changes land in minor releases.** v1.48 (February 2026) graduated
  catalog extension points out of alpha, requiring `/alpha` import removal, and
  enforced an API restriction so plugins can only provide APIs to themselves; a
  type incompatibility needed a 1.48.1 follow-up.
  <https://roadie.io/backstage-weekly/122-backstage-v1-48-ships-patch-follows-and-cve-alert/>
- **Plugin rot is measurable from Backstage's own marketplace.** 249 active
  plugins against 58 marked inactive, defined as not updated in over 365 days.
  That is roughly 19% of the catalogue already stale, and the page carries its
  own warning that these plugins "haven't been fully vetted by the core Backstage
  team". <https://backstage.io/plugins>
- **Skills mismatch.** Backstage is a TypeScript and React application with a
  Node backend. This project is Go, Kubernetes controllers and OTel collector
  configuration. Adopting Backstage means the team that owns the control plane
  also owns a React monorepo, a webpack build and a Node service. Several
  critiques name this specifically as the reason platform teams stall on
  Backstage. <https://www.qovery.com/blog/3-reasons-not-to-use-backstage>

### The tension resolved

The reasoning that made Backstage appealing was: it already has a catalogue with
ownership and relations, so reusing it avoids building a register, an auth model
and a UI shell. Test each:

- **Register.** Section 1: the catalogue cannot hold the Hop, and ticket 07
  already decided intent lives in custom resources, which supplies storage,
  validation, RBAC, audit, a change feed and a CLI for free. Kubernetes is
  already the cheaper register. Backstage would be a *second* store to keep in
  sync with it.
- **Auth model.** Real saving, but only for adopters who already run Backstage.
  For everyone else it means standing up Backstage's auth to get Backstage's
  auth, which is circular.
- **UI shell.** Real saving, worth perhaps 1 to 2 engineer-weeks of chrome,
  navigation and sign-in. Against a 3-FTE, 6-to-12-month adoption cost imposed on
  the user.

So the tension does not survive contact. **"Develop as little as we can" points
away from Backstage, not towards it.** The saving is a UI shell; the price is an
internal developer portal.

### The optional-surface path, which is credible and is the ecosystem norm

Yes, and this is the dominant pattern rather than a compromise. Argo CD, Grafana,
Crossplane, PagerDuty and Kubernetes itself all have Backstage plugins that are
thin clients over the tool's own API, and none of those tools requires Backstage.
The `kubernetes-ingestor` precedent shows the same shape for custom resources.

The conditions for keeping that door open cost nothing today:

1. Intent is in custom resources. Already decided in ticket 07, so a Backstage
   `EntityProvider` can mirror Stages, Paths and Applications into the catalogue
   at any point, read-only, in days.
2. The console talks to a documented HTTP API (or straight to the Kubernetes API)
   rather than to a private backend, so a plugin can reuse it unchanged.
3. Nothing in the product assumes Backstage identity, Backstage entity refs, or
   the Backstage catalogue as a lookup.

A read-only Backstage plugin built later, once the API exists, is a small piece
of work: a catalogue entity provider plus one or two entity cards. Call it **2 to
4 engineer-weeks including packaging and the dual old/new frontend system
support.** Building on Backstage from day one costs the entire adoption figure
above, and charges it to every user.

## 5. The Kubernetes fit

**Verdict: reads Kubernetes well and reads custom resources by explicit
configuration. Writing is possible through a supported but coarse escape hatch,
the kubernetes-backend proxy. Using the Kubernetes API as a plugin's backing
store is a supported pattern, but the authorisation model needs care.**

### Reading

Cluster configuration lives in `app-config.yaml` under `kubernetes`, with cluster
locator methods. Custom resources are opt-in per GVK:

```yaml
kubernetes:
  customResources:
    - group: 'argoproj.io'
      apiVersion: 'v1alpha1'
      plural: 'rollouts'
```

<https://backstage.io/docs/features/kubernetes/configuration/>

The plugin is "designed around the needs of service owners, not cluster admins",
splits into `@backstage/plugin-kubernetes` and
`@backstage/plugin-kubernetes-backend`, and its documented RBAC requirement is
"read-only cluster wide": `get`, `list`, `watch` only, with no write, delete or
modify verbs.
<https://backstage.io/docs/features/kubernetes/>

So the built-in Kubernetes experience is emphatically read-only, and it is keyed
off entity annotations and label selectors, meaning it answers "what is running
for this Component" rather than "let me edit this custom resource".

### Writing

The escape hatch is the **kubernetes-backend proxy endpoint**.

- Documented, shipped, and callable from a frontend plugin as
  `kubernetesApi.proxy(CLUSTER_NAME, '/api/v1/namespaces')`.
  <https://backstage.io/docs/features/kubernetes/proxy/>
- The target cluster comes from a `Backstage-Kubernetes-Cluster` header; a
  `Backstage-Kubernetes-Authorization` bearer token is rewritten into the
  standard `Authorization` header before forwarding.
- The implementation in
  `plugins/kubernetes-backend/src/service/KubernetesProxy.ts` uses
  `createProxyMiddleware` with a per-cluster router and **no method filtering**,
  so POST, PUT, PATCH and DELETE are all forwarded.
- The originating RFC is explicit that this is for writes: it cites "performing
  write operations against clusters on-demand, such as creating and deleting
  applications or supply chains", and "interacting with Custom Resources beyond
  the default behaviors of the existing Kubernetes plugin".
  <https://github.com/backstage/backstage/issues/12231>
- Access is gated by a single permission, `kubernetes.proxy`, which a policy can
  DENY to produce a 403.

**The catch, and it is a real one.** The permission is coarse and binary: a user
either may use the proxy or may not. There is no per-verb, per-resource or
per-namespace granularity at the Backstage layer. Whatever granularity exists has
to come from Kubernetes RBAC, which means forwarding the *requesting user's*
credential rather than the Backstage service account. If it forwards the service
account, then every write is attributable to "backstage" in the audit log and
every user who can reach the proxy has the union of its permissions. For a
product whose selling point includes an authoritative control plane with a
credible audit trail, that is a material regression compared with a user talking
to the API server directly.

### The overall shape, if Backstage were used

- Custom resources are the register.
- A custom `EntityProvider` mirrors them into the catalogue, read-only, so they
  appear alongside Components and Systems (precedent: `kubernetes-ingestor`).
- The editor writes back through the proxy, or through our own backend plugin
  holding a Kubernetes client.

That works. Note that none of it uses the catalogue as the register, and steps
one and three are exactly what a standalone console would do anyway.

## 6. Alternatives worth pricing against it

### Headlamp

**Verdict: substantially cheaper than Backstage on every axis that matters here,
and it is the only option in this list whose write model already matches editing
custom resources.**

- **Status.** Accepted to CNCF at Sandbox level on 17 May 2023
  (<https://www.cncf.io/projects/headlamp/>), now developed under
  `kubernetes-sigs` and part of Kubernetes SIG UI. The Kubernetes project's own
  blog announces that "The Kubernetes Dashboard project has now been archived"
  and positions Headlamp as the successor, citing "multi-cluster visibility,
  application-centric views, extensibility through plugins, and flexible
  deployment options".
  <https://kubernetes.io/blog/2026/06/01/dashboard-to-headlamp/>
- **Plugin cost.** `npx --yes @kinvolk/headlamp-plugin create my-first-plugin`
  generates four files: `src/index.tsx`, `package.json`, `tsconfig.json`,
  `README.md`. TypeScript and React, built to a single `main.js`.
  <https://headlamp.dev/docs/latest/development/plugins/getting-started/>
- **No fork, no rebuild.** Plugins are loaded at runtime from a plugins directory
  (`-plugins-dir`, default `/headlamp/plugins` in cluster), shipped as container
  images copied in by an init container, or dropped into the desktop app's config
  directory. There is an official plugin catalogue and Artifact Hub distribution.
  <https://headlamp.dev/docs/latest/development/plugins/building/>
  This is the thing upstream Backstage cannot do.
- **Extension points.** `registerRoute`, `registerSidebarEntry`,
  `registerDetailsViewSection`, `registerDetailsViewHeaderAction`,
  `registerAppBarAction`, `registerResourceTableColumnsProcessor`,
  `registerUIPanel`, `registerAppTheme`, `registerPluginSettings`, and more. A
  plugin can own a whole route, which is all a graph editor needs.
  <https://headlamp.dev/docs/latest/development/plugins/functionality/>
- **Writes are first class.** The plugin API exposes `lib/k8s/api/v1/apply`,
  `lib/k8s/apiProxy`, `lib/k8s/patchUtils`, `lib/k8s/api/v1/scaleApi`, and
  `lib/k8s/crd` for custom resource definitions.
  <https://headlamp.dev/docs/latest/development/api/>
  The Kubernetes blog confirms the user-facing behaviour: view and edit
  manifests, delete, scale and update, "based on permissions", under "the same
  access controls as Dashboard". Headlamp acts as the signed-in user, so RBAC and
  audit are the cluster's, not a service account's.
- **What you give up.** No service catalogue, no ownership model, no Group/User
  entities, no TechDocs, no scaffolder. The audience is people with cluster
  access, not all developers. Plugins run in the same JavaScript context as the
  app, so there is no isolation between plugins. Sandbox-level maturity and a
  smaller ecosystem than Backstage. And it is Kubernetes-shaped, which suits a
  control plane whose intent is custom resources but not a surface aimed at
  application owners who never touch a cluster.
- **Rough cost.** A first working plugin hosting a canvas and writing custom
  resources: **days to a small number of weeks**, with no adopter-side platform
  to stand up beyond Headlamp itself, which is a Helm chart or a desktop app.

### Kubernetes Dashboard plugin route

**Verdict: dead. Do not price it.**

The project is archived (`kubernetes-retired/dashboard`), and kubernetes.io
directs new users to Headlamp. Its extensibility model relied on dynamically
loaded JavaScript plugins that never reached maturity. Building on an archived
project would import a security-patch liability with no upstream.
<https://kubernetes.io/blog/2026/06/01/dashboard-to-headlamp/>

### Small purpose-built console

**Verdict: the honest baseline, and cheaper than it looks, because ticket 07
already moved most of a console's cost into Kubernetes.**

What a console normally costs is storage, schema validation, authz, audit, a
change feed and a CLI. Ticket 07 put intent in custom resources with an operator,
which supplies all six from the API server. What is left is:

- A canvas for a graph that is deliberately small: Stages number in the handful,
  Collectors are never drawn. An off-the-shelf node-graph library covers the
  interaction model.
- Read views for the derived objects, which are the same views any surface needs.
- A thin API or direct API-server access, plus sign-in.

What it gives up: no free service catalogue, no free ownership graph, no existing
audience, and we own the shell. What it buys: **the authoring idiom is the
product's differentiator, and ticket 04 established that no existing tool has one
to inherit.** Bindplane infers its graph, Alloy's is read-only, otelbin's is
one-way, Cribl's canvas bypasses its authored unit. Backstage's is a relation
viewer. There is nothing to reuse here in any of them, so building the editor is
not avoidable cost, it is the work.

It also imposes nothing on adopters beyond what they already run to use the
product at all.

### Comparison

| Option | Adopter must run | Editing custom resources | Cost to us | Cost to adopter |
| --- | --- | --- | --- | --- |
| Backstage plugin | A Backstage monorepo app they own and upgrade | Possible via `kubernetes.proxy`, coarse permission, service-account audit risk | Plugin 1 to 3 weeks, plus dual frontend-system support, plus 2 to 5 engineer-days per release cycle | 3 FTE for 6 to 12 months to stand up, 2 FTE ongoing (vendor-modelled) |
| Headlamp plugin | Headlamp (Helm chart or desktop app) | First class: apply, patch, CRD support, user's own RBAC | Days to weeks, four generated files, runtime load, no fork | Low. One deployment, no monorepo, no database |
| Kubernetes Dashboard | Archived project | n/a | n/a | n/a |
| Purpose-built console | Nothing beyond the control plane | Direct, on our terms | The canvas plus a shell, with storage, RBAC, audit and CLI already supplied by Kubernetes | None |

---

## Recommendation

**Not the primary surface. Optional surface over an API, deferred until someone
asks for it.**

1. **Build the authoring surface as a small purpose-built console**, talking to
   the Kubernetes API or a thin API in front of it. The editor is the product's
   differentiator, no candidate surface supplies an editing idiom to inherit, and
   ticket 07's substrate decision already removed the expensive half of a
   console's cost.
2. **Keep the Backstage door open at zero cost** by holding to three constraints
   that are good design anyway: intent in custom resources, a documented API, and
   no assumption of Backstage identity or entity refs anywhere in the product.
3. **If a Kubernetes-native second surface is wanted, price Headlamp first.** A
   Headlamp plugin is four generated files, loads at runtime without a fork or a
   rebuild, writes custom resources through a first-class apply/patch API, and
   runs as the signed-in user so RBAC and audit come from the cluster. It is the
   Kubernetes project's own recommended UI now that Dashboard is archived.
4. **A Backstage plugin, if built at all, should be read-only**: a catalogue
   `EntityProvider` mirroring Applications, Stages and Paths from custom
   resources, plus one or two entity cards showing conformance. Roughly 2 to 4
   engineer-weeks once the API exists, and it lets Backstage shops see the estate
   in the portal they already run without anyone being required to run one.

**The cost figure, restated so it cannot be softened:** making Backstage the
primary surface would require every adopter to stand up and permanently staff an
internal developer portal, modelled at 3 engineers for 6 to 12 months and 2
engineers thereafter, in order to use a control plane whose entire register
already lives in their cluster. In exchange we would save a UI shell worth one to
two engineer-weeks, and we would still write every line of the editor ourselves,
because the Backstage catalogue has no write API for entities and no way to
represent a Hop.
