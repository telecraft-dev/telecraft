# Findings: stability signal on Fleet's OTel collector support

Research date: 4 August 2026. Every citation below carries the date of the source,
because a stability signal ages fast on a feature this young.

## Baseline: what the feature actually is, and how old it is

Fleet's OTel collector support is **OpAMP-based monitoring only**. Fleet Server runs an
OpAMP server at `/v1/opamp`; collectors you install and run yourself connect to it and
report status and effective config. Fleet does not deploy, configure, or command them.

Timeline established from primary sources:

| Date | Event | Source |
|---|---|---|
| 19 Feb 2026 | `opampextension` added to EDOT Collector, backported to 9.2 and 9.3 | [elastic-agent#12857](https://github.com/elastic/elastic-agent/pull/12857) |
| 20 Feb 2026 | Fleet Server maps OpAMP `AgentToServer` fields to Agent fields | [fleet-server#6400](https://github.com/elastic/fleet-server/pull/6400) |
| 24 Mar 2026 | OpAMP endpoint enabled by default in Fleet Server | [fleet-server#6657](https://github.com/elastic/fleet-server/pull/6657) |

| **5 May 2026** | **Stack 9.4.0** ships it (technical preview) | [Kibana 9.4.0 release notes](https://www.elastic.co/docs/release-notes/kibana); [kibana#264554](https://github.com/elastic/kibana/pull/264554) merged 5 May 2026 |

listed Kibana and Fleet Server release is 9.4.4.

## Q1. What is the GA path?

**Verdict: No public GA commitment found. No target release, no roadmap entry, no blog or
discuss statement. The only forward-looking public statement is a vague "in the near future"
from a March 2026 blog post that is about a different feature.**

Evidence:

- The docs frontmatter, checked 4 Aug 2026, is the authoritative label and says only
  `stack: preview 9.4+` / `serverless: preview` with no GA qualifier:
  [monitor-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/monitor-otel-collectors.md),
  [add-otel-collector.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/add-otel-collector.md),
  [view-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/view-otel-collectors.md).
- Every open Fleet Server issue that would constitute the GA work has **no milestone assigned**
  (checked 4 Aug 2026): [#6814](https://github.com/elastic/fleet-server/issues/6814),
  [#6815](https://github.com/elastic/fleet-server/issues/6815),
  [#6816](https://github.com/elastic/fleet-server/issues/6816),
  [#6818](https://github.com/elastic/fleet-server/issues/6818),
  [#6819](https://github.com/elastic/fleet-server/issues/6819),
  [#7447](https://github.com/elastic/fleet-server/issues/7447).
- The **"What's new in Elastic 9.4" announcement (5 May 2026)** does not mention the feature
  at all: [discuss.elastic.co/t/what-s-new-in-elastic-9-4/386175](https://discuss.elastic.co/t/what-s-new-in-elastic-9-4/386175).
  It was not a headline 9.4 feature.
- The one public forward-looking statement is from the Observability Labs blog
  ["Centrally Managing OTel Collectors with Elastic Agent and Fleet", **24 March 2026**](https://www.elastic.co/observability-labs/blog/centrally-managed-otel-collectors-with-elastic-fleet):
  > "Currently management of Elastic Agents is done via existing Fleet protocols, however in
  > the near future this will move over to OPAMP" and "Fleet will be able to provide management
  > to 3rd party OTel collectors as well."

  **Read this carefully.** That blog's "production-ready today" claim is about *Elastic Agent
  running in OTel mode under Fleet's own protocol* (a different, older, GA capability). The
  OpAMP third-party-collector path it describes as future work is precisely the feature this
  ticket is about, and it is described as unbuilt. Do not let that blog's GA language be read
  across onto this feature.

Elastic does not publish a dated public roadmap for this. **"No public commitment found"** is
the correct statement; do not infer a GA date from the 9.x cadence.

## Q2. What has broken or changed between versions?

**Verdict: Sustained, active churn including at least one behavioural revert and one
config-schema addition. Bugs are being filed and fixed faster than the docs are updated. The
wire protocol and the stored document shape are both still moving.**

Server-side changes by version ([Fleet Server release notes](https://www.elastic.co/docs/release-notes/fleet-server), checked 4 Aug 2026):

| Version | Change |
|---|---|
| 9.2.0 | OTel collector properties added to the policy schema |
| 9.2.7 / 9.2.8 | OTEL secrets handling; `/v1/opamp` endpoint backported |
| 9.3.0 | Credentials support for OTel exporters |
| 9.3.2 | Secret replacement in OTEL `receivers`/`exporters`/`processors` sections |
| 9.3.3 | `/v1/opamp` endpoint added for OpAMP clients |
| 9.4.0 | Handle OpAMP `AgentDisconnect`; report server capabilities in `ServerToAgent` (spec compliance fix) |

- **Behavioural revert.** "always set `ReportFullState` flag in OpAMP responses" was merged then
  reverted, and the revert backported to 9.4:
  [fleet-server#6831 reverted by #6878](https://github.com/elastic/fleet-server/pull/6878) (22 Apr 2026),
  [#6920](https://github.com/elastic/fleet-server/pull/6920) (27 Apr 2026). A wire-level flag
  changed meaning inside a single minor cycle.
- **`effective_config` merge bug**, fixed 8 May 2026 and backported to 8.19, 9.3 and 9.4:
  [fleet-server#6988](https://github.com/elastic/fleet-server/pull/6988). The reported config
  Fleet shows you was wrong.
- **Deleted pipelines not removed from `effective_config`** (referenced in Serverless/Fleet
  Server notes): same surface, again.
- **Namespace propagation on enrol** fixed 30 Jun 2026: [fleet-server#7298](https://github.com/elastic/fleet-server/pull/7298).
- **Document-shape additions in Kibana**: `config.name` metadata field
  ([kibana#268635](https://github.com/elastic/kibana/pull/268635), 11 May 2026, backported to 9.4)
  and a `pipeline_config` runtime field for collector grouping
  ([kibana#266665](https://github.com/elastic/kibana/pull/266665), merged 27 May 2026).
  If you index or query against collector documents, these fields did not exist at launch.
- **UI scope thrash**: OpAMP agents were filtered out of the agent table
  ([kibana#270258](https://github.com/elastic/kibana/pull/270258), 20 May 2026) then that was
  reverted nine days later ([kibana#271941](https://github.com/elastic/kibana/pull/271941), 29 May 2026).

Open bugs as of 4 Aug 2026 (all filed June to July 2026, all still open):

- [kibana#274545](https://github.com/elastic/kibana/issues/274545) (23 Jun): OpAMP managed policy is
  hidden from the Agent Policies list but reachable via search, with an enabled **Add Integration**

- [kibana#277169](https://github.com/elastic/kibana/issues/277169) (9 Jul): error-patterns panel loads

- [kibana#278415](https://github.com/elastic/kibana/issues/278415) (15 Jul): "Open in Discover" from the

- [fleet-server#6820](https://github.com/elastic/fleet-server/issues/6820) (10 Apr): **Fleet Server

Fixed in the same window (indicating the shakeout is recent, not historical): health status wrongly

([kibana#274843](https://github.com/elastic/kibana/issues/274843)), diagnostics stuck "In Progress"

space ([kibana#275528](https://github.com/elastic/kibana/issues/275528)).

## Q3. Which collector distributions and versions are supported?

**Verdict: The claim on record is confirmed verbatim: upstream/contrib otelcol 0.103.0+ and
EDOT Collector 9.2+. But "supported" means "will enrol and report". It does not mean feature
parity: upstream collectors trip Fleet's Elastic Agent version gate and lose UI features, and
that is acknowledged and unfixed.**

The support statement, from
[monitor-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/monitor-otel-collectors.md)
(published 19 May 2026, unchanged as of 4 Aug 2026):

> Supported collectors:
> * OpenTelemetry Collector (upstream and community-contributed distributions): version 0.103.0 or later
> * EDOT Collector: version 9.2 or later

What the matrix excludes or silently degrades:

1. **WebSocket transport is not supported.** Fleet Server implements HTTP only at `/v1/opamp`.
   A collector configured for the OpAMP WebSocket transport will not connect.
   Source: [fleet-server/docs/opamp.md](https://github.com/elastic/fleet-server/blob/main/docs/opamp.md), merged 8 Apr 2026.
2. **The OpAMP *supervisor* path is not the supported path.** The docs assume the in-process
   `opampextension`. Supervisor integration is an open, unmilestoned feature request:
   [fleet-server#7447](https://github.com/elastic/fleet-server/issues/7447) (23 Jul 2026).
3. **Upstream collectors lose version-gated Fleet UI features.** An `otelcol-contrib` enrolled via
   OpAMP reports its OTel version (e.g. `0.153.0`), which fails Fleet's "Elastic Agent 7.11 or
   higher" gate and disables the Logs view. Elastic acknowledged this on **22 June 2026**:
   > "Fleet behavior for upstream otel collectors is annoying, but understandable in this case.
   > We'll have to revisit the checks and figure out how to make the gates work vs arbitrary otel
   > collectors." (@swiatekm)

   Source: [elastic-agent#15066](https://github.com/elastic/elastic-agent/issues/15066). Still
   unresolved as a class of problem; the issue was closed only because the reporter switched to
   the Elastic Agent artifact.
4. **No standalone EDOT collector binary outside Docker/Linux.** Per the same issue (June 2026),
   the `elastic-otel-collector` artifact ships only as a Linux Docker image. Elastic's guidance is
   to use any Elastic Agent package and run `./elastic-agent otel --config ./otel-opamp.yaml`.
   Verified working on Windows, Linux and macOS by Elastic QA on 23 June 2026, but that means the
   practical EDOT path is an Elastic Agent install, not a slim collector.

Read together: the *fully supported* configuration is EDOT (i.e. Elastic Agent in otel mode) 9.2+.
Upstream contrib 0.103+ enrols and monitors, but is a second-class citizen in the UI today.

## Q4. Is `tls.insecure_skip_verify: true` still generated, and is there a CA path?

**Verdict: Yes, still generated by default, as of the current docs on 4 Aug 2026. It is
configurable, and there is a documented and adequate CA path. The insecure default is a
usability choice, not a capability gap, but it is a default that ships into whatever a user
copies out of the flyout.**

The generated bootstrap config still contains:

```yaml
extensions:
  opamp:
    server:
      http:
        endpoint: "https://<fleet-server-host-url>/v1/opamp"
        headers:
          Authorization: "ApiKey <fleet-enrollment-api-key>"
        tls:
          insecure_skip_verify: true   # <3>
```

with callout 3 reading: "Skips verification of the Fleet Server TLS certificate. Before deploying
to production, adjust the configuration to use a CA file."

The documented proper path, under **"Configure TLS for Fleet Server connection"**:

```yaml
tls:
  ca_file: /path/to/ca.crt
```

And an explicit warning: "Using `insecure_skip_verify: true` skips TLS certificate verification and
makes your connection vulnerable to man-in-the-middle attacks. Only use this for testing in
isolated environments, never in production."

Source: [add-otel-collector.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/add-otel-collector.md),
published 19 May 2026, verified unchanged 4 Aug 2026 (the file has exactly one commit).

Two adjacent security facts worth carrying into any design:

- **Authentication is a shared enrolment token, not a per-collector credential.** Fleet Server
  requires `Authorization: ApiKey <enrollment key>`, and that key is shared across all collectors
  on the policy. The two-token flow (exchange enrolment token for a per-agent access key, so a
  single collector can be revoked) is **open and unmilestoned**:
  [fleet-server#6512](https://github.com/elastic/fleet-server/issues/6512) (5 Mar 2026). It is
  additionally blocked upstream: the `opampextension` cannot advertise
  `AcceptsOpAMPConnectionSettings`, only the supervisor can. So per-collector revocation is not
  achievable on the supported path today.
- Fleet Server redacts keys containing `password`, `token`, `key`, `secret`, `auth`, `certificate`
  or `passphrase` from the effective config before persisting it
  ([docs/opamp.md](https://github.com/elastic/fleet-server/blob/main/docs/opamp.md)). Useful, but
  it is a substring denylist, so it is best-effort.

## Q5. Does Serverless carry the same capability and cadence? (weighted question)

**Verdict: Capability parity is ESTABLISHED and Serverless was actually FIRST. Cadence parity is
NOT established and cannot be, because the two use incomparable release models. Crucially, the
Serverless changelog is not usable as a stability signal for this feature: its published entries
stop at 30 April 2026, three months stale as of today.**

### Capability parity: established

Elastic's own `applies_to` metadata assigns Serverless the *identical* maturity label with no
version qualifier, on all three feature pages:

```yaml
applies_to:
  stack: preview 9.4+
  serverless: preview
```

Sources: [monitor-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/monitor-otel-collectors.md),
[add-otel-collector.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/add-otel-collector.md),
[view-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/view-otel-collectors.md).
All published 19 May 2026, verified 4 Aug 2026.

The prerequisites line names Serverless explicitly and as an equal:
> "An {{stack}} deployment version 9.4 or later **or** an {{serverless-full}} {{observability}} project"

and notes Fleet Server is already provisioned on Serverless and ECH, so the self-managed Fleet
Server deployment step does not apply.

**Serverless received the feature ~3 weeks before the Stack.** The Serverless changelog entry for
**15 April 2026** reads:
> "Enables OpenTelemetry collector agents in Fleet (technical preview), including an **Add collector**
> action, Agent list visibility, and monitoring views [#260654]"

Same Kibana PR ([#260654](https://github.com/elastic/kibana/pull/260654)) that later shipped in
Stack 9.4.0 on 5 May 2026. Source: [Serverless changelog](https://www.elastic.co/docs/release-notes/cloud-serverless),
cross-checked against the raw source at
[release-notes/elastic-cloud-serverless/index.md](https://github.com/elastic/docs-content/blob/main/release-notes/elastic-cloud-serverless/index.md).

This is the expected shape: Kibana Serverless deploys continuously from `main`, so Fleet UI work
lands on Serverless first and is then cut into the next Stack minor.

### One documented Serverless-specific difference

On Serverless Observability projects (and ECH), the generated `elasticsearch/otel` exporter can be
replaced with the **Managed OTLP Endpoint (mOTLP)**, which takes OTLP directly and uses an
APM-scoped API key rather than an Elasticsearch API key. Source:
[reference/fleet/_snippets/otel-motlp-exporter-alternative.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/_snippets/otel-motlp-exporter-alternative.md).
This is an export-path difference, not an OpAMP-control-path difference: the OpAMP half is
identical. But it means **the bootstrap config a user copies on Serverless may not be
byte-identical to the self-managed one**, and a connector that parses or templates that config
must handle both exporter shapes.

### Cadence parity: NOT established, and the changelog is unreliable

- Serverless has no version numbers. Its changelog is date-headed
  (`## April 30, 2026`), roughly weekly to twice-weekly, with no semver mapping to 9.x. There is
  no published statement anywhere that a given Serverless project is "at" 9.4.x, and none that
  guarantees Serverless will receive a future GA promotion on the same date as a Stack minor.
- **The published Serverless changelog is stale.** As of 4 Aug 2026 its newest entry is
  **30 April 2026**. On 17 July 2026 the page was converted to a CDN-fed
  `:::{changelog} :cdn: cloud-serverless:::` directive
  ([docs-content#6599](https://github.com/elastic/docs-content/pull/6599)) and on 29 July 2026 the
  static entries after that date were removed
  ([docs-content#7628](https://github.com/elastic/docs-content/pull/7628), "Remove outdated
  Serverless changelog entries"). The CDN content does not render to a plain fetch. **The practical
  consequence: you cannot currently read the Serverless changelog to find out what changed in
  your Serverless project between May and August 2026.** For a PoC on Serverless this is the single
  most important operational finding: the change-notification channel for the platform you are
  targeting is, right now, not legible.
- No Serverless-specific known issues are recorded for this feature:
  [known-issues.md](https://github.com/elastic/docs-content/blob/main/release-notes/elastic-cloud-serverless/known-issues.md)
  contains no OTel/collector/OpAMP entries as of 4 Aug 2026. Read that as "nothing published",
  not "nothing wrong".

**Net for a Serverless-targeted design:** you get the capability, you get it slightly earlier than
Stack users, you get the same "preview, no support SLA" terms, and you get *less* ability to see
what changed under you and *no* ability to pin a version. Serverless removes the one mitigation
self-managed users have against a churning preview feature: staying on a known build.

## Q6. Do Fleet-managed collector policies remain unmodifiable, and does that constrain a read-only integration?

**Verdict: Yes, unmodifiable, and far more strongly than ADR-0003 records. This is not a UI
restriction, it is a protocol-level absence. Fleet Server has no remote-config capability at all.
For a read-only integration this is not a constraint; it is the strongest possible guarantee that
read-only is the only thing on offer. The constraint bites in the opposite direction: it forecloses
any future upgrade path to enforcement without Elastic shipping unbuilt work.**

The docs statement, repeated on two pages:
> "Unlike Elastic Agents, OTel Collectors don't display an agent policy in the **Agents** list. They
> use managed policies that can't be modified and aren't displayed in the **Agent policies** tab."

Sources: [monitor-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/monitor-otel-collectors.md),
[view-otel-collectors.md](https://github.com/elastic/docs-content/blob/main/reference/fleet/view-otel-collectors.md),
both 19 May 2026.

The underlying reason, from Fleet Server's own spec-deviation doc
([docs/opamp.md](https://github.com/elastic/fleet-server/blob/main/docs/opamp.md), merged 8 Apr 2026,
current on `main` as of 4 Aug 2026):

> "**Fleet-server operates in monitoring-only mode.**
> - **No remote configuration.** The spec defines `ServerToAgent.remote_config` for pushing configuration to agents.
> - **No connection settings management.** ...
> - **No package management.** ...
> - **No server-initiated commands.** The spec defines `ServerToAgent.command` (e.g., restart).
> - **No custom messages.** ..."

And the corresponding agent-to-server fields Fleet Server **ignores**: `remote_config_status`,
`package_statuses`, `connection_settings_request`, `available_components`,
`connection_settings_status`, `custom_capabilities` / `custom_message`.

Every one of the capabilities that would make enforcement possible is an open, unmilestoned issue:

| Issue | Capability | Opened | State (4 Aug 2026) |
|---|---|---|---|
| [#6814](https://github.com/elastic/fleet-server/issues/6814) | `AcceptsRemoteConfig` (push config) | 10 Apr 2026 | open, no milestone |
| [#6815](https://github.com/elastic/fleet-server/issues/6815) | `AcceptsOpAMPConnectionSettings` | 10 Apr 2026 | open, no milestone |
| [#6816](https://github.com/elastic/fleet-server/issues/6816) | `AcceptsOtherConnectionSettings` | 10 Apr 2026 | open, no milestone |
| [#6818](https://github.com/elastic/fleet-server/issues/6818) | `AcceptsRestartCommand` | 10 Apr 2026 | open, no milestone |
| [#6819](https://github.com/elastic/fleet-server/issues/6819) | `AcceptsPackages` | 10 Apr 2026 | open, no milestone |
| [#6817](https://github.com/elastic/fleet-server/issues/6817) | own-telemetry destination offering | 10 Apr 2026 | open, no milestone |
| [#7447](https://github.com/elastic/fleet-server/issues/7447) | OpAMP Supervisor integration for EDOT | 23 Jul 2026 | open, no milestone |

Note also from #6814 that even once Fleet Server implements it, the **upstream OpAMP supervisor does
not advertise `accepts_remote_config` by default**: it must be explicitly enabled per collector. So
config authority would remain opt-in at the collector, not assertable from the server. That is a
durable architectural property of OpAMP, not a temporary Elastic gap.

### Does it constrain a read-only integration?

Three real constraints, none of them blocking, all of them worth designing around:

1. **You cannot correct stale identity.** Per [fleet-server#6820](https://github.com/elastic/fleet-server/issues/6820)
   (open since 10 Apr 2026), `AgentDescription` updates after enrolment are silently dropped.
   Hostname, OS, version and identifying/non-identifying attributes freeze at enrol time. A
   fleet-visibility view will show stale identity for any collector whose config was edited after
   enrolment, and there is no API to fix it; re-enrolment is the only remedy. **This is the single
   most consequential finding for a read-only visibility product.**
2. **Health fidelity is reduced.** Fleet Server maps `ComponentHealth` down to `online` / `error` /
   `degraded` and **does not traverse the nested `component_health_map`**
   ([docs/opamp.md](https://github.com/elastic/fleet-server/blob/main/docs/opamp.md)). Per-component
   (per-receiver, per-exporter) health is not retrievable through Fleet, even though the collector
   reports it.
3. **The "unmodifiable" boundary leaks in the UI.** [kibana#274545](https://github.com/elastic/kibana/issues/274545)
   (open since 23 Jun 2026): the OpAMP managed policy is hidden from the Agent Policies list but
   findable via search, and the **Add Integration** button is enabled on it. A related fix hid the
   Settings tab ([kibana#276208](https://github.com/elastic/kibana/pull/276208), 3 Jul 2026). Do not
   treat "hidden in the UI" as an enforced invariant; treat the protocol-level absence of
   `remote_config` as the real invariant, because that one is genuine.

**Conclusion on ADR-0003.** The ADR's constraint that v1 must not build enforcement on top of this
should be **tightened, not merely confirmed**. It is not that enforcement is inadvisable in v1; it
is that enforcement is *impossible* at the protocol level today, has no committed delivery date, and
would remain collector-opt-in even after Elastic ships it. "Config authority retained by the
customer" is not a v1 concession that a v2 can walk back; it is a property of the OpAMP integration
as Elastic has scoped it.
