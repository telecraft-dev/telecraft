# Findings: how do people actually manage and apply OTel collector configuration?

Resolves `issues/20-how-do-people-actually-apply-collector-config.md`.

Researched 2026-08-04. The ticket asks seven numbered questions and a closing
verdict on whether targeting Argo CD alone is sufficient, insufficient, or
premature. Each section below opens with a verdict line, then the evidence.

## Method, and where it is weak

Primary sources were read directly wherever they exist: the CNCF 2024 Annual
Survey PDF (extracted locally, not read via a summary), the CNCF GitOps
Microsurvey PDF, Argo CD's own documentation, the OpenTelemetry documentation,
and the OpenTelemetry Helm chart and operator repositories via the GitHub API.
Secondary commentary was used only to locate primary sources, never as the
citation for a number.

Three limits are worth stating up front, because they shape every answer:

1. **No survey asks the decisive question.** Neither OpenTelemetry's collector
   surveys nor CNCF's annual survey asks "what applies your collector
   configuration". The OTel collector surveys (2024, n=186; 2025/2026 follow-up)
   ask about deployment *topology* (daemonset, sidecar, gateway) and *substrate*
   (Kubernetes, VM, bare metal), never about the *application mechanism* (Helm,
   Argo CD, Flux, Ansible). The distribution asked for in Question 1 therefore
   has to be assembled from adjacent evidence, and the assembly is stated as such
   rather than presented as a measured distribution.
2. **Every GitOps number is drawn from a cloud-native-engaged population.** The
   CNCF 2024 sample was sourced from "Linux Foundation subscribers, members,
   partner communities, and social media" (2024 CNCF Annual Survey, methodology
   section, p.33). That is a population already selected for cloud-native
   engagement. Its GitOps figures are an upper bound on the general population,
   not a central estimate.
3. **The most-cited Argo CD statistic is a survey of Argo CD users.** The
   frequently repeated "97% use Argo CD in production" and "60% of clusters"
   come from the CNCF *Argo CD end user survey*, whose respondents are Argo CD
   users. It measures depth of use among adopters, not share of the market. It
   is not evidence that Argo CD is what applies most collector config, and it is
   used below only for the former claim.

## Q1. Actual distribution of application mechanisms

**Verdict: no measured distribution exists. Nobody has surveyed it. What the
adjacent evidence supports is that Helm is the single most common mechanism, that
the OpenTelemetry project itself points users at Helm and never at GitOps, and
that roughly half of collector fleets now include hosts that no Kubernetes
GitOps tool can reach at all.**

### Nobody has measured it

The OpenTelemetry End User SIG has run two collector surveys. Neither asks how
config is applied.

- 2024 survey, n=186
  ([opentelemetry.io/blog/2024/otel-collector-survey](https://opentelemetry.io/blog/2024/otel-collector-survey/)).
  Questions cover collector count, environment, usage scenario, custom
  distributions, and monitoring. There is no question on Helm, operator,
  manifests, GitOps, Argo CD, Flux, Kustomize or Ansible.
- 2025/2026 follow-up
  ([opentelemetry.io/blog/2026/otel-collector-follow-up-survey-analysis](https://opentelemetry.io/blog/2026/otel-collector-follow-up-survey-analysis/);
  the post does not state a publication date, survey period or n). Same gap. No
  deployment-mechanism question.

The CNCF Annual Survey does not ask it either. Its closest questions are
"preferred method for packaging Kubernetes applications" (Q22-equivalent, Figure
12) and "tools in use to manage CI/CD pipelines" (Q57, Figure 25). Neither is
scoped to collectors, and neither separates "applies config" from "packages
config".

**So: no quantitative data found for the distribution the ticket asks for.** The
rest of this section is the best available proxy evidence, labelled as proxy.

### What OpenTelemetry itself recommends

This is the strongest available signal, because it is the default path a new
adopter follows.

- The Kubernetes getting-started guide says: "To install the collector, we'll use
  the OpenTelemetry Collector Helm chart". It explicitly deprioritises the
  operator: "If you're interested in using a Kubernetes operator, see
  OpenTelemetry Operator, but this guide will focus on the Helm chart."
  ([opentelemetry.io/docs/platforms/kubernetes/getting-started](https://opentelemetry.io/docs/platforms/kubernetes/getting-started/))
- The Kubernetes platform section lists Helm charts before the operator
  ([opentelemetry.io/docs/platforms/kubernetes](https://opentelemetry.io/docs/platforms/kubernetes/)).
- **GitOps, Argo CD, Flux and Kustomize are not mentioned on any of these
  pages.** Not as a recommendation, not as an alternative, not in passing. The
  official install path has no GitOps step in it.
- For non-Kubernetes fleets the project's own scaling guidance is Ansible:
  "Manage OpenTelemetry Collectors at scale with Ansible"
  ([opentelemetry.io/blog/2024/scaling-collectors](https://opentelemetry.io/blog/2024/scaling-collectors/)),
  2024. That post also does not mention GitOps, Argo CD or Flux.

### Proxy evidence on Kubernetes packaging and tooling

From the CNCF 2024 Annual Survey, fielded November to December 2024, n=689,
published April 2025
([PDF](https://www.cncf.io/wp-content/uploads/2025/04/cncf_annual_survey24_031225a.pdf)):

| Measure | 2024 | 2023 |
|---|---|---|
| Helm, preferred packaging method (Figure 12, select one) | 75% | 56% |
| Kustomize, preferred packaging method | 14% | 15% |
| Managed Kubernetes offering | 5% | 16% |
| Buildpacks | 2% | 4% |
| Helm, in production use (Figure 13) | 77% (+10% evaluating) | |
| Argo, in production use (Figure 13) | 43% (+19% evaluating) | |
| Flux, in production use (Figure 13) | 17% (+11% evaluating) | |

Two cautions on that table. "Argo" in Figure 13 is the graduated CNCF *Argo
project family*, which includes Argo Workflows, Argo Rollouts and Argo Events
alongside Argo CD. 43% is therefore an upper bound on Argo CD specifically, and
Argo Workflows has substantial independent use in ML and batch pipelines. And
Figure 12 is "select one", so Helm's 75% is a preference, not exclusivity.

Helm in production (77%) runs at roughly 1.8x the whole Argo family (43%) and
4.5x Flux (17%).

### The substrate shift matters more than the tooling split

From the OTel collector surveys, comparing 2024 (n=186) with the 2025/2026
follow-up:

| Environment | 2024 | Follow-up | Change |
|---|---|---|---|
| Kubernetes | 80.6% | 81% | unchanged |
| Virtual machines | 33.3% | 51% | +18% |
| Bare metal | 10.8% | 18% | +7% |

Also from the follow-up: 65% now operate more than 10 collectors in production
(+10%); of large deployments (>100 collectors), **50% use both Kubernetes and
VMs**, and 25% of small deployments (<100 collectors) do.

This is the single most consequential number in this document for the product
question. Argo CD is a Kubernetes controller that applies Kubernetes manifests to
Kubernetes clusters. It has no reach into a VM or bare-metal collector. Half of
large collector fleets span both. A lens whose only input is Argo CD is
structurally blind to the VM half of those fleets, irrespective of how popular
Argo CD is inside Kubernetes.

### Mechanisms with no quantitative data

No quantitative data found for the share of collector config applied by: the
OpenTelemetry Operator, plain `kubectl apply` of manifests, Kustomize overlays
applied by CI, Ansible/Chef/Puppet, cloud-vendor agents (AWS Distro for
OpenTelemetry, Google Ops Agent, Azure Monitor agent), or hand-edited files.
Vendor documentation confirms these paths exist and are supported (for example
Sumo Logic ships CDN-based collector installation for Ansible, Chef and Puppet,
[release notes 2026-02-19](https://www.sumologic.com/help/release-notes-collector/2026/02/19/otel/);
Splunk ships `signalfx/splunk-otel-collector` with Ansible, Chef, Puppet and Salt
integrations), but no survey sizes them.

## Q2. Is GitOps actually the majority position?

**Verdict: no, not in the sense the product needs. The headline "77% adhere to
GitOps principles" is real but is a low bar that counts "some". Only 22% say
nearly all of their deployment is GitOps, and 23% have either not started or are
just beginning. On the strictest honest reading, a lens that assumes GitOps is a
lens over roughly a fifth to a half of an already cloud-native-biased population.
Helm-directly and non-GitOps paths are not a rump; they are the larger share.**

This is the question the ticket flagged as most likely to produce a comfortable
wrong answer, so the underlying distribution is given in full rather than the
headline.

### The full distribution, not the headline

CNCF 2024 Annual Survey, Q55, n=689, "To what extent has your organization
adopted practices and tools that adhere to GitOps principles? (select one)",
Figure 30, don't-know responses excluded:

| Response | 2024 | 2023 |
|---|---|---|
| Have not started using GitOps practices/tools | 8% | 8% |
| Just beginning to use | 15% | 20% |
| **Some** of our deployment practices and tools adhere | 30% | 28% |
| **Much** of our deployment practices and tools adhere | 25% | 25% |
| **Nearly all** of our deployment practices and tools adhere | 22% | 19% |

The widely quoted 77% is `30 + 25 + 22`, that is, everyone who said "some" or
more. Read against what a lens actually requires, which is that the repository
Argo CD watches is the place collector config genuinely lives:

- **22%** say nearly all deployment is GitOps.
- **47%** say much or nearly all.
- **53%** say some, just beginning, or not started, meaning GitOps is a minority
  of their deployment activity or absent.
- **23%** are not meaningfully doing GitOps at all.

The 2023 CNCF GitOps Microsurvey
([PDF](https://www.cncf.io/wp-content/uploads/2023/11/CNCF_GitOps-Microsurvey_Final.pdf),
conducted July to September 2023, 220 responses) asked the coverage question
directly: "What percentage of your cloud native deployments leverage GitOps?"

| Coverage | Share |
|---|---|
| 26% or more | 54% |
| 5-20% | 18% |
| Less than 5% | 16% |
| 21-25% | 12% |

That is a self-selected GitOps-interested audience, and even there, 46% of
respondents use GitOps for a quarter or less of their deployments. The top band
is "26% or more", which is a floor with no ceiling reported, so it cannot be read
as "most of their deployments".

### GitOps tracks maturity, which means it is concentrated

The 2025 CNCF Annual Survey (published 2026-01-20) reports that "58% of 'cloud
native innovators' use GitOps principles extensively, compared to only 23% of
'adopters'"
([CNCF announcement](https://www.cncf.io/announcements/2026/01/20/kubernetes-established-as-the-de-facto-operating-system-for-ai-as-production-use-hits-82-in-2025-cncf-annual-cloud-native-survey/)).

This is the gap the ticket suspected, stated by CNCF itself. Extensive GitOps is
a marker of the most advanced cohort. Among ordinary adopters it is under a
quarter. Conference talks and vendor blogs are written by and for the innovator
cohort, which is why the described world and the surveyed world diverge.

### The stacking bias

Every number above is generous to GitOps, for reasons that compound:

- CNCF 2024's sample came from Linux Foundation subscribers, members, partner
  communities and social media (methodology, p.33). Cloud-native-engaged by
  construction.
- The 2023 microsurvey was a GitOps microsurvey, advertised to a GitOps-
  interested community.
- The Argo CD end user survey samples Argo CD users.
- Octopus Deploy's State of GitOps report (released 2025-06-17, 660 responses,
  [octopus.com/news/state-of-gitops](https://octopus.com/news/state-of-gitops))
  reports 93% "plan to continue or increase" GitOps adoption, which is a
  statement of intent among current users, not a measure of current share.

If 22% "nearly all" is the figure from the friendliest available sample, the
general-population figure is lower.

### Plain answer

GitOps is mainstream in the sense that most organisations do some of it. It is
not the majority position in the sense the product needs, which is that a
majority of collector config is applied by a GitOps controller reading a
repository. On the evidence, Helm invoked directly (by a CI job, a platform
script, or a human) plus plain manifests plus non-Kubernetes configuration
management together account for more collector config application than Argo CD
does. A lens that assumes Argo CD is a lens over a minority of users, and the
OpenTelemetry project's own documentation, which never mentions GitOps, points
the same way.

## Q3. Argo CD versus Flux

**Verdict: Argo CD leads by roughly 2.3x to 3x on every independent measure, and
both projects are growing. Flux is not dying: its production-use share rose from
17% to 23% between the 2024 and 2025 CNCF waves, even though its commit volume
fell by around 60% in the Weaveworks year. But "target one or both" understates
the problem, because they do not expose the same things. Argo CD publishes drift
as a first-class status and will hand you rendered manifests over an API. Flux
does neither. There is no common machine-readable abstraction, and the nearest
candidate for one is dormant.**

### Relative adoption

CNCF Annual Survey, graduated projects in production use or evaluation, same
question wording across waves:

| | Argo (family) | Flux | Ratio |
|---|---|---|---|
| **2024** (Figure 13, Q32, n=689, fielded Nov-Dec 2024) | 43% prod, 19% eval | 17% prod, 11% eval | 2.5:1 |
| **2025** (Figure 19, Q32, n=395-596, published Jan 2026) | 52% prod, 20% eval | 23% prod, 11% eval | 2.3:1 |

CI/CD pipeline tools, CNCF 2024 Figure 25 (Q57, n=596, select all): Argo 45%
(2023: 39%), Flux 16% (2023: 16%). The 2025 report breaks this figure out by
maturity segment rather than by tool, so there is no 2025 equivalent.

Two things to note. As in Q1, the row is labelled "argo", not "Argo CD", so it
includes Workflows, Rollouts and Events and overstates Argo CD by an unknown
amount. The "flux" row has no equivalent ambiguity. And **both grew**: the gap
narrowed slightly rather than widening, which is the opposite of the usual
telling.

The Octopus Deploy / Codefresh "State of GitOps Report 2025" (n=660) reports
"ArgoCD (50%) is the most popular open-source GitOps tool, with second place
going to Flux (11%)". Directionally consistent with CNCF, but note the conflict:
it is co-published with Codefresh, an Argo CD commercial vendor, and Octopus
employs an Argo maintainer. Not independent.

**A correction to a figure in wide circulation, including in my own earlier
draft.** The claim that "nearly 60% of Kubernetes clusters rely on Argo CD"
originates in the CNCF press release of 2025-07-24. It could not be reproduced
from the underlying results post
([blog.argoproj.io, 2025-07-02](https://blog.argoproj.io/argo-cd-2025-user-survey-results-ab045f7d5d9a)),
which contains no matching question. The closest actual statement is that almost
60% of respondents report 75%+ of production apps run on Kubernetes, which is a
different claim entirely. **This figure should not be used.** The survey itself
is n=185, distributed to the Argo community, with recruitment method and fielding
dates undisclosed, and it does not mention Flux. Its usable findings (NPS 79, 97%
production use, 42% managing 500+ apps per instance) describe depth of use among
adopters and say nothing about share.

### Flux after Weaveworks: development slowed, adoption did not

Weaveworks ceased commercial operations in February 2024. ControlPlane hired core
maintainers Stefan Prodan and Soule Ba on 2024-02-15, and CNCF announced
broadened corporate backing at KubeCon EU in March 2024 (Microsoft Azure, GitLab,
Cisco, Giant Swarm, Fairwinds and others).

Commits per calendar year (GitHub Search API, measured 2026-08-04, includes bots):

| Repo | 2023 | **2024** | 2025 | 2026 YTD |
|---|---|---|---|---|
| argoproj/argo-cd | 1,237 | **1,639** | 1,751 | 1,397 |
| fluxcd/flux2 | 658 | **239** | 329 | 224 |
| fluxcd/source-controller | 543 | **201** | 205 | 132 |
| fluxcd/kustomize-controller | 362 | **151** | 178 | 157 |

Flux commit volume fell 58% to 64% in 2024 and stabilised without returning to
2023 levels. Argo CD's grew through the same period. GitHub scale as of
2026-08-04: argo-cd 23,834 stars / 424 contributors; flux2 8,315 stars / 191
contributors (not strictly comparable, since Flux's reconcilers live in separate
repos).

The honest summary: Flux survived, is actively maintained (v2.9.3, 2026-07-23),
held its first FluxCon at KubeCon NA 2025, and its *adoption* rose. What fell and
stayed down is development throughput and contributor breadth, with the core now
concentrated in one consultancy. Treating Flux as a dead end would be wrong.

### There is no common abstraction, and the asymmetry is worse than expected

| | Argo CD | Flux |
|---|---|---|
| Unit | one `Application` (`argoproj.io/v1alpha1`) | `Kustomization` + `HelmRelease` + separate `GitRepository`/`OCIRepository` source objects |
| Source URL and revision | same object: `spec.source.repoURL`, `status.sync.revision` (bare SHA) | multi-object join; `status.lastAppliedRevision` is a **composite string** `master@sha1:<commit>` that must be parsed. **`HelmRelease` carries no git revision at all** |
| Rendered manifests | **`GET /api/v1/applications/{name}/manifests`** over the API | **No equivalent found.** Only `flux build kustomization`, which needs a **local checkout** |
| Drift signal | `status.sync.status` = `Synced` / `OutOfSync`, first-class, per-resource | **No `Synced`/`OutOfSync` concept at all** |
| Drift correction | opt-in, off by default (`selfHeal`) | `Kustomization`: **always on, no object-level off switch**. `HelmRelease`: `driftDetection.mode` **off by default** |
| Status vocabulary | **bespoke**: three separate enums, `ApplicationCondition` has no `status`/`reason`/`observedGeneration`, and **no positive condition exists** | **standard `metav1.Condition`** (`Ready`, `Reconciling`, `Stalled`, `Healthy`) with `observedGeneration` |
| Managed resources | `status.resources[]` structured, **with per-resource status and health** | `status.inventory.entries[]` is a packed `ns_name_group_kind` string with **no status or health** |

Three corrections to what I assumed before reading the APIs:

1. **Argo CD does not use Kubernetes-standard conditions.** `metav1.Condition`
   and `observedGeneration` appear zero times in its Application types. Flux
   does use the standard, and implements `kstatus`; Argo CD does not. So the one
   place a shared vocabulary might have existed, it is Flux that is standard and
   Argo CD that is bespoke.
2. **Flux ships two drift models with opposite defaults in the same product.**
   `Kustomization` re-applies on every interval, so drift correction cannot be
   disabled at object level (only via per-target annotations such as
   `kustomize.toolkit.fluxcd.io/reconcile: disabled`). `HelmRelease` drift
   detection is **disabled by default**. Any integration must handle both.
3. **The rendered-manifest gap is the biggest asymmetry**, and it matters
   directly for Q4. Argo CD will return rendered manifests and a resolved
   revision over its API. Flux has no such endpoint at all; getting desired state
   means a local checkout plus `flux build`, or reimplementing the controller.
   Given that Q4 shows rendering is the hard part of reading a collector repo,
   this is a substantial argument for Argo CD as the first integration that has
   nothing to do with drift.

Flux's `Ready=True` means "the last reconciliation succeeded", not "live matches
desired right now". A Flux object can sit at `Ready=True` while a resource has
drifted, until the next interval tick re-applies it. Argo CD's `OutOfSync` is a
genuinely different signal with no Flux equivalent.

**No cross-tool standard closes this, and the candidate is dormant.**
OpenGitOps (CNCF Sandbox) ships exactly two prose documents, `PRINCIPLES.md` and
`GLOSSARY.md`. No CRD, no API, no schema, no conformance suite. Its only release
is **v1.0.0, dated 2021-10-08**, with nothing in nearly five years; its own README
still describes interoperability in the future tense. `kstatus` is the nearest
shared status standard and only Flux implements it, and even then it covers
workload readiness rather than sync or drift.

### There is no common abstraction

This is the part that decides the integration question, and it is not a matter of
adoption percentages.

The Flux docs describe the interval as the controller "applies it on the cluster,
correcting any existing drift in the process", and note that with the `Merge`
policy, "If you use `kubectl` to edit a Kubernetes resource managed by Flux, all
changes will be reverted when the controller reconciles"
([fluxcd.io Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/)).
Drift is corrected as a side effect of reconciling and never surfaces as a
distinct state.

**The practical consequence for a lens.** The intended-versus-declared cross that
Q5 hopes to get for free exists in Argo CD and does not exist in Flux.
Integrating with Flux gets you "which commit is live" (after parsing a composite
string, and not at all for `HelmRelease`), but not "and the cluster drifted from
it", and not rendered manifests. Detection latency is also worse and less
predictable, since Flux's interval is user-set per Kustomization rather than
defaulting to Argo CD's roughly three minutes.

"GitOps status" is therefore not a portable concept. A tool wanting both needs a
per-backend adapter and an internal model that is the union of (source URL,
resolved SHA, last-applied SHA, reconcile outcome, drift verdict, managed-resource
list), with drift populated differently per backend and left **unknown** for Flux
`HelmRelease` unless the user has explicitly enabled `driftDetection`.

## Q4. What is the repository actually shaped like?

**Verdict: there is no single shape, and three of the four common shapes are
materially harder to statically analyse than a plain config file. In the two
most common paths the committed artifact is not the effective collector config
at all: the Helm chart merges user values with defaults and injects components
via presets, and the operator either holds the config as an opaque quoted string
(v1alpha1) or as structured-but-open nested maps (v1beta1), and rewrites parts of
it. A lens that assumes it can read collector YAML off disk and reason about it
will be wrong most of the time.**

### The five shapes, and what each costs to parse

**1. Helm values file.** The mainstream path, and the one OpenTelemetry's own
docs send you to. The collector config sits nested under a `config:` key in
`values.yaml`: "You can add/modify any part of the configuration using the
`config` section in your `values.yaml`"
([Helm collector chart docs](https://opentelemetry.io/docs/platforms/kubernetes/helm/collector/)).

Two things make the committed file an unreliable input:

- **The chart supplies defaults that merge.** "the chart provides a few default
  collector components to get you started", with receivers (jaeger, otlp,
  prometheus, zipkin), exporters, processors and service pipelines preconfigured.
  A values file that mentions only one receiver still yields a collector running
  several. The docs warn about the merge semantics: "When changing a pipeline,
  you must explicitly list all the components that are in the pipeline, including
  any default components."
- **Presets inject components invisibly.** "the OpenTelemetry Collector Chart
  comes with some presets that, when enabled, handle the complex setup for these
  important components." Setting `presets.logsCollection.enabled: true` adds a
  `filelogreceiver` to the logs pipeline; `presets.kubernetesAttributes` adds a
  `k8sattributesprocessor` to every enabled pipeline and configures RBAC. The
  string `filelogreceiver` never appears in the committed values file.

Three further mechanics make this worse, all from the chart's own files:

- **Presets are one-way.** `values.yaml` states verbatim that `.Values.config`
  "can be used to modify/add to a preset component configuration, but CANNOT be
  used to remove preset configuration. If you require removal of any sections of
  a preset configuration, you cannot use the preset."
- **Lists do not merge.** The README states "lists in helm are not merged, so if
  you want to modify any default list you must specify all items, including any
  default items you want to keep." Pipeline `receivers:` and `exporters:` are
  lists, so a partial edit silently drops components. Removing a default
  component at all requires the null trick (`receivers: {jaeger: null}`).
- **`alternateConfig`** exists and is documented as having "NO default values and
  IS NOT MERGED with config", but presets still merge into it. So there are two
  config entry points with different merge semantics.

**The chart's own JSON schema gives a validator nothing.**
`values.schema.json` fully constrains `presets` with `additionalProperties:
false`, but types the collector config as bare `{"type": "object"}` with no inner
schema. Schema-driven tooling (kubeconform, `helm lint`, IDE validation) is
therefore blind to the part that matters.

The clinching evidence that rendering is mandatory is that the OpenTelemetry
project cannot do without it either: the chart repo keeps **23 checked-in golden
renders** under `charts/opentelemetry-collector/examples/*/rendered/`, regenerated
by `make generate-examples`, because there is no other way to see what a values
file produces. The rendered artifact is a ConfigMap with the config as a block
scalar under the `relay` key.

So the effective config is a function of (user values, chart version, preset
flags, merge-entry-point), and recovering it requires rendering the chart at the
pinned version, not parsing the values file. Values files are also Go-templated
when the chart is used as a subchart, which is the case in
[helm-charts #1194](https://github.com/open-telemetry/opentelemetry-helm-charts/issues/1194).

**`opentelemetry-kube-stack` nests one level deeper again.** Top-level
`defaultCRConfig.config:` and `collectors.<name>.config:`, each with its own
`presets:`. That is a Helm values file containing an `OpenTelemetryCollector` CR
spec containing a collector config. Real users of this shape include
`elastic/elastic-agent`, `DataDog/opentelemetry-examples` and `k0rdent/kof`.

**2. `OpenTelemetryCollector` custom resource.** Two API versions, with different
parsing difficulty, verified directly from the operator source:

- **v1alpha1**: `apis/v1alpha1/opentelemetrycollector_types.go` line 173 declares
  `Config string \`json:"config,omitempty"\`` with the comment "Config is the raw
  YAML to be used as the collector's configuration." The entire collector config
  is a **quoted string blob inside a YAML document**. Statically analysing it
  means parsing YAML, extracting a string, then parsing that string as YAML
  again, and any indentation or block-scalar handling error corrupts the result.
- **v1beta1**: `apis/v1beta1/config.go` line 104 declares a structured `Config`
  with typed fields `Receivers`, `Exporters`, `Processors`, `Connectors`,
  `Extensions`, `Service` and `Telemetry`. Better, but each is an `AnyConfig`
  (line 34, "AnyConfig represent parts of the config"), an arbitrary nested map
  with `PreserveUnknownFields`. So pipeline wiring (which receivers feed which
  pipelines) is statically readable; individual component settings are opaque
  maps.

The operator's own `docs/crd-changelog.md` (readable at tag v0.99.0; the path
404s on `main`) gives the rationale for the change, and it is the same problem a
lens faces: the string field was hard because "It's easy to make YAML formatting
errors in the content", "The field can have a lot of content, and may not show
useful diffs for changes", and "It's more difficult for the operator to reject
invalid configurations at admission." v1alpha1 is deprecated, with conversion
webhooks handling migration.

**The operator does not treat the config as inert. Four mutations, so the CR as
committed is not what the collector runs:**

1. **The target allocator rewrites the Prometheus receiver.** Verbatim from
   [the target allocator docs](https://opentelemetry.io/docs/platforms/kubernetes/operator/target-allocator/):
   "The Operator removes any existing service discovery configurations (e.g.,
   `static_configs`, `file_sd_configs`, etc.) from the `scrape_configs` section
   and adds an `http_sd_configs` configuration pointing to a Target Allocator
   instance it provisioned." Implemented in
   `internal/manifests/collector/config_replace.go`, which edits the YAML tree in
   place rather than round-tripping, to avoid Prometheus regex validation
   choking on `$$`.
2. **Default internal telemetry injection.** `internal/otelconfig/config.go`
   `ApplyDefaults()`: when neither `service.telemetry.metrics.address` nor
   `.readers` is present, it logs "no telemetry readers configuration found,
   applying default Prometheus endpoint" and injects a reader on `localhost:8888`.
3. **Per-component defaulting** across receivers, exporters and extensions.
4. **Port inference**: v1alpha1 line 179, "the operator will attempt to infer the
   required ports by parsing the `.Spec.Config` property".

Also worth noting: the operator ships an `OpAMPBridge` CRD with a
`componentsAllowed` field, "a list of allowed OpenTelemetry components for each
pipeline type". That is the closest thing to a semantic guardrail anywhere in the
official stack, and it is enforced at delivery time rather than in the repo.

**3. Raw collector YAML in a ConfigMap.** The easiest case, and the only one
where the committed bytes are the effective config. The collector config is a
plain YAML document under a ConfigMap `data` key (the chart requires the key be
named `relay`: "The ConfigMap MUST include the collector configuration via a key
named 'relay' or the collector will not start", `values.yaml` line 164). Still
nested one level inside another YAML document as a block scalar, but not
templated and not merged. This is also the shape most exposed to the staleness
gap in Q5, because externally managed ConfigMaps bypass the chart's checksum
annotation.

**4. Kustomize overlays.** 14% name Kustomize as their preferred packaging method
(CNCF 2024, Figure 12). Overlays apply strategic-merge and JSON patches to a
base, so as with Helm the committed overlay is a delta, not the config, and
recovering the effective config requires running `kustomize build`.

**5. Go-templated block scalar inside a Helm chart template.** The worst case,
and it is not rare. A chart template emits a ConfigMap whose data key is a block
scalar containing collector config with `{{- if }}` directives interleaved, for
example `OneUptime/oneuptime/HelmChart/Public/kubernetes-agent/templates/configmap-daemonset.yaml`.
**This is not valid YAML at all.** It cannot be tokenised, let alone parsed,
without a full Helm render against a specific values file, and different values
produce structurally different configs.

### Relative prevalence

GitHub code search totals, run 2026-08-04. These are best-effort,
index-dependent and capped by GitHub, so treat them as relative magnitudes and
not as a census. **No reliable quantitative data found** for true prevalence.

| Query | `total_count` |
|---|---|
| `filename:otel-collector-config.yaml receivers exporters service` | 3,484 |
| `kind: OpenTelemetryCollector opentelemetry.io/v1beta1` | 1,352 |

Standalone config files and raw ConfigMaps are, on this evidence, very much alive

### The general shape of the problem

| Shape | Parseable as YAML? | Effective config without rendering? |
|---|---|---|
| Plain standalone file | Yes, directly | **Yes.** The only free case. |
| v1beta1 CR `spec.config` | Yes, sub-tree extraction | Almost. Operator injects telemetry readers, and rewrites `receivers.prometheus` entirely if the target allocator is on. |
| Quoted string blob (v1alpha1 CR, ConfigMap `data`) | Two-stage parse; indentation and `$$` escaping are hazards | Yes for the string; same operator mutations apply. |
| Kustomize overlay | Yes, but it is a delta | No. Requires `kustomize build`. |
| Helm values `config:` | Yes syntactically, but it is not the effective config | **No.** Requires `helm template` to resolve defaults, ten presets, `alternateConfig`, and non-merging lists. |
| kube-stack double nesting | Yes syntactically | **No.** Needs Helm *and* the operator's mutations. |
| Go-templated block scalar | **No. Not valid YAML.** | **No.** Full Helm render required. |

Only the first row is analysable for free. For the rest the lens must either
render (Helm template, kustomize build, at the pinned chart or base version) or
accept that it is reasoning about intent rather than effect. This is a real
constraint on the product: "a lens over the repository" implies rendering
infrastructure, and rendering is exactly the work Argo CD already does.

That last point cuts both ways. Argo CD's repo-server renders manifests and
exposes the rendered desired state via its API. A lens integrating with Argo CD
could consume rendered output rather than re-implementing Helm and Kustomize
rendering, which is a genuine argument for the Argo CD integration that has
nothing to do with drift detection. It does not apply to the Helm-directly
majority.

### OpAMP: the structural threat to the premise

**No quantitative adoption data found**, but this is the mechanism most likely to
invalidate the "repository is the source of truth" assumption, and it is moving.

The [spec](https://github.com/open-telemetry/opamp-spec) is at status **Beta**,
with v0.19.0 released **2026-08-03** and a steady cadence through 2025 and 2026.
There are two implementations, and the split matters:

- **`opampextension`** (contrib, stability **alpha**) is genuinely **report-only
  for config**. It implements `ReportsEffectiveConfig`, `ReportsHealth` and
  `ReportsAvailableComponents`, all defaulting true. It does **not** implement
  `AcceptsRemoteConfig`. A lens could consume this as a source of ground truth
  about effective config, which is interesting.
- **`opampsupervisor`** (contrib, stability **alpha**) implements
  `AcceptsRemoteConfig` and merges remote config with local `agent::config_files`.

The structural point: OpAMP is a *push* protocol, and its adoption model makes the
OpAMP server the config authority. Git, where it survives, becomes an input that
gets pushed into that server rather than the thing the cluster reconciles against.
This is already how the commercial products work (Q7): Bindplane's own GitOps
guide describes a GitHub Action that "will apply resources to Bindplane", after
which "All affected Bindplane configurations will have a pending rollout".

For a product whose whole premise is a lens over a repository, this is the risk
to watch. It is not a reason to change course today, since the extension is alpha
and no adoption data exists, but it should be a tracked assumption rather than a
background detail.

## Q5. What does Argo CD already report, and does sync status really answer "is the cluster running what git says"?

**Verdict: partly, and with enough qualifications that the claim should not be
treated as load-bearing without configuration checks. Argo CD does detect an
out-of-band `kubectl edit` of a tracked ConfigMap and does mark the Application
`OutOfSync` without self-heal being enabled. But `Synced` is a weaker statement
than "the cluster is running what git says": it is scoped to fields present in
the git manifest, on resources Argo CD tracks, minus anything `ignoreDifferences`
suppresses, and it says nothing about whether the process consuming the config
has picked it up. Detection is not instant, and the answer changes materially
depending on diff strategy, self-heal and ignore rules. All of this is from Argo
CD's own documentation.**

### What it does detect, and how fast

Argo CD computes sync status by diffing rendered desired manifests against live
cluster state. A `kubectl edit` that changes a field which *is* present in the
git manifest (which is the case for a collector config stored in a ConfigMap's
`data`, since the whole `data` block is in git) produces a diff and flips the
Application to `OutOfSync`.

Detection is *reported* independently of correction. From the automated sync
policy page
([argo-cd.readthedocs.io/en/stable/user-guide/auto_sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)):

> "By default, changes that are made to the live cluster will not trigger
> automated sync."

That sentence is about *triggering a sync*, not about *computing status*. The
status still goes `OutOfSync`. The FAQ confirms the reporting split for the git
side: "Applications with auto-sync enabled will automatically sync to match the
new state. Applications without auto-sync will simply be marked as OutOfSync in
the UI" ([FAQ](https://argo-cd.readthedocs.io/en/latest/faq/)).

Timing, from the FAQ:

> "By default, Argo CD checks (polls) Git repositories every 3 minutes to detect
> changes."

calculated as "120 seconds + up to 60 seconds of jitter". Webhooks can make the
*git* side near-instant, but a webhook is fired by the git host and therefore
cannot cover cluster-side drift. Cluster-side drift is caught by the application
controller's cluster cache and the reconciliation loop, so the practical worst
case for noticing a `kubectl edit` is the same up-to-three-minute window. Setting
`timeout.reconciliation` to `0` disables polling entirely, in which case Argo CD
"only detect[s] changes when triggered through webhooks or a manual refresh",
which removes out-of-band drift detection almost completely.

With `selfHeal` enabled, correction is attempted after the self-heal timeout,
"5 seconds by default", controlled by `--self-heal-timeout-seconds`.

### What it misses, or can be configured to miss

Six qualifications, each from Argo CD's documentation:

1. **`ignoreDifferences` deliberately suppresses drift.** The diffing page
   ([user-guide/diffing](https://argo-cd.readthedocs.io/en/latest/user-guide/diffing/))
   documents `jsonPointers`, `jqPathExpressions` and `managedFieldsManagers` at
   Application level, plus `resource.customizations.ignoreDifferences` in
   `argocd-cm` at system level, which "is possible to configure ... to be applied
   to all resources in every Application" via the `all` key. Anything matched is
   invisible to sync status. In practice teams add these rules to silence noisy
   false positives, and they are a standing risk of silencing real drift too.
2. **Status fields are ignored by default.** `ignoreResourceStatusField` defaults
   to ignoring `status`, since "the `status` field of many resources is often
   stored in Git/Helm manifest and should be ignored during diffing".
3. **Untracked resources do not affect sync status.** Resource tracking is by the
   `argocd.argoproj.io/tracking-id` annotation (default) or the
   `app.kubernetes.io/instance` label
   ([resource_tracking](https://argo-cd.readthedocs.io/en/latest/user-guide/resource_tracking/)):
   "If the tracking annotation does not reference the resource it is applied to,
   the resource will neither affect the application's sync status nor be marked
   for pruning." A collector ConfigMap created out of band, or one that lost its
   annotation, is simply not part of the answer.
4. **Orphan detection is off by default.** Resources in the cluster belonging to
   no Application are only surfaced if `orphanedResources` is explicitly enabled
   in AppProject settings, and the docs warn that "enabling orphaned resource
   monitoring has performance implications"
   ([orphaned-resources](https://argo-cd.readthedocs.io/en/stable/user-guide/orphaned-resources/)).
   So "is the cluster running what git says" does not, by default, include "and
   nothing else".
5. **Deletion is not reverted by default.** "By default (and as a safety
   mechanism), automated sync will not delete resources when Argo CD detects the
   resource is no longer defined in Git."
6. **Diff strategy changes the answer.** Argo CD has three strategies
   ([diff-strategies](https://argo-cd.readthedocs.io/en/stable/user-guide/diff-strategies/)):
   Legacy (default), a 3-way diff "based on live state, desired state and
   last-applied-configuration (annotation)"; Structured-Merge Diff, which "is
   being discontinued in favour of Server-Side Diff" after "different issues were
   identified by the community" and which has "challenges ... for CRDs that define
   default values"; and Server-Side Diff, stable since v3.1.0, which runs a
   dry-run server-side apply per resource but "will not be performed during the
   creation of new resources". The common thread is that the diff is anchored on
   fields the desired manifest owns. Fields *added* to a live resource that
   appear in neither git nor the last-applied-configuration annotation are the
   weakest case across all three strategies, and the documentation does not
   commit to flagging them.

### The gap that matters most for collectors

`Synced` means the ConfigMap object in the cluster matches git. It does not mean
the collector process is running that config. Kubernetes does not restart pods
when a mounted ConfigMap changes; it only rolls pods when the pod spec changes.

For the mainstream path this is handled, and the finding should not be
overstated. The OpenTelemetry collector Helm chart sets
`enableConfigChecksumAnnotation: true` by default
(`charts/opentelemetry-collector/values.yaml`, line 480) and the deployment
template renders `opentelemetry-collector.configTemplateChecksumAnnotation` into
the pod annotations when it is set (`templates/deployment.yaml`), so a config
change rolls the pods. The operator likewise annotates pods with a ConfigMap hash
(`internal/manifests/manifestutils/annotations.go`: "Adding the ConfigMap Hash
only to PodAnnotations"), and the corresponding issues are closed
([operator #197](https://github.com/open-telemetry/opentelemetry-operator/issues/197),
closed 2021-03-04;
[operator #2070](https://github.com/open-telemetry/opentelemetry-operator/issues/2070),
closed 2023-09-06).

The gap survives in the cases that matter for a fleet:

- **Externally managed ConfigMaps.** `configMap.existingName` mounts a ConfigMap
  the chart did not render, so the checksum annotation does not cover it. This
  was [helm-charts #1194](https://github.com/open-telemetry/opentelemetry-helm-charts/issues/1194)
  ("[collector] No collector reload when using external configmap", opened
  2024-05-21, closed 2024-08-29) and
  [#1219](https://github.com/open-telemetry/opentelemetry-helm-charts/issues/1219)
  (closed 2024-06-12). This is exactly the shape a GitOps-managed fleet tends to
  adopt when config is generated elsewhere.
- **No supported hot reload in the collector.**
  [opentelemetry-collector #5966](https://github.com/open-telemetry/opentelemetry-collector/issues/5966),
  "Configuration reloading logic and customizability", has been **open since
  2022-08-25** and remains open. The 2025/2026 collector survey reports users
  highlighting "the difficulty of operating the Collector in dynamic, production
  environments, especially when configuration changes require full restarts", and
  **63% named configuration management and resolution as their top improvement
  request**, the single highest-ranked item.

So the honest form of the claim is: Argo CD's sync status answers "does the
ConfigMap object in the cluster match git", subject to tracking, ignore rules and
diff strategy. It does not answer "is the collector process running that config",
and it certainly does not answer the telemetry question in Q6.

### What Argo CD's health status is, and is not

Health is Kubernetes resource readiness, not application behaviour
([operator-manual/health](https://argo-cd.readthedocs.io/en/stable/operator-manual/health/)).
Built-in checks assess, for Deployments/ReplicaSets/StatefulSets/DaemonSets,
whether "desired generation matches observed generation and updated replicas
equal desired replicas"; for Services, LoadBalancer ingress population; for PVCs,
phase `Bound`. Custom checks can be written in Lua and return Healthy,
Progressing, Degraded or Suspended. Nothing in that vocabulary can express
"telemetry arrived".

### What a lens would get for free, and what it would not

Free from Argo CD: the git repo URL and target revision, the resolved commit SHA
actually deployed, `Synced`/`OutOfSync` per Application and per resource, the
rendered desired manifest, a resource-level diff, and Kubernetes-level health.
That is a genuine and useful intended-versus-declared cross, and the claim is
directionally right.

Not free, and the lens would still have to build: semantic understanding of the
collector config *inside* the ConfigMap (Argo diffs it as an opaque string blob,
so it can say "this changed" but never "the otlp receiver was removed from the
traces pipeline"); any check that config matched intent rather than matched git;
coverage of resources Argo does not track or is told to ignore; anything on VMs;
and the entire telemetry-arrival question.

## Q6. What does none of them answer?

**Verdict: confirmed. Every mechanism reports whether configuration was applied.
None reports whether the telemetry that configuration asked for actually arrived.
The nearest thing in the ecosystem, the collector's own healthcheckv2 extension,
is still at development stability and reports component status, not data
delivery.**

The chain of evidence:

- **Argo CD** reports sync (object matches git) and health (Kubernetes resource
  readiness), per Q5. A collector whose exporter endpoint is wrong, whose
  credentials expired, whose filter processor drops everything, or whose scrape
  config matches no targets, will run with all replicas ready. Argo CD reports
  `Synced` and `Healthy` throughout. Argo CD's health vocabulary has four values
  and none of them is about data.
- **Flux** reports reconciliation success on its `Kustomization` and `HelmRelease`
  resources: whether the source was fetched, built and applied, and whether the
  applied resources became ready. Same category of claim as Argo CD.
- **Helm** reports release status (deployed, failed, pending). It has no runtime
  view at all after the release succeeds.
- **The OpenTelemetry Operator** reconciles the `OpenTelemetryCollector` CR into
  a workload and reports on that workload. It does not inspect the data plane.
- **The collector's own health_check extension** "enables an HTTP url that can be
  probed to check the status of the OpenTelemetry Collector" and is intended as a
  Kubernetes liveness/readiness probe. It reports that the collector is up.
- **healthcheckv2** does go further, aggregating "the statuses for the individual
  components in each pipeline" including receivers, processors and exporters. But
  its stability level is **development**, and "users wishing to experiment with
  this extension will have to build a custom collector binary"
  ([healthcheckv2extension README](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/extension/healthcheckv2extension)).
  Even fully adopted, per-component status is "this exporter is erroring", which
  is closer to the question but is still a producer-side self-report, not
  confirmation that data arrived at the destination.

The distinction the product rests on is real and is not covered:

- **Applied** is a control-plane fact. Argo CD, Flux, Helm and the operator all
  assert it, from different angles.
- **Arrived** is a data-plane fact, observable only at the destination, and
  requires correlating what a config declared it would produce against what the
  backend actually received.

Nothing in the application-tooling chain crosses that line. The supporting
survey signal is consistent: 63% of collector-survey respondents named
configuration management and resolution as their top improvement area, the
single highest-ranked item, up from 30.1% in 2024.

One caveat on the monitoring figures, which do not reconcile between the two
surveys and so should not be quoted as a trend. The 2024 post reports 81.7%
monitoring and 16.6% not monitoring. The follow-up reports 23% not monitoring
and describes it as "-6% vs. 2024", which implies a 2024 baseline of 29% rather
than 16.6%. The two are not comparable as published; treat only the within-survey
figures as usable.

Corroboration from the commercial fleet-management space, which is the closest
anyone gets: Grafana Fleet Management advertises "Assign configurations to
collectors based on their attributes", "Remotely configure collectors" and
"Monitor the health of individual collectors"
([Grafana Cloud docs](https://grafana.com/docs/grafana-cloud/send-data/fleet-management/)),
with no documented data-arrival verification. Datadog Fleet Automation offers
"View Agent and OTel Collector configurations along with historical changes" plus
version and config management
([Datadog docs](https://docs.datadoghq.com/agent/fleet_automation/)), again with
no documented telemetry-arrival check. Both push config; neither closes the loop.

### How the commercial space decomposes "did it work"

Across nine products checked (Grafana Fleet Management, Datadog Fleet Automation,
Dash0, ControlTheory, Mezmo, Cribl, Edge Delta, Honeycomb Telemetry Pipeline,
Bindplane), "did it work" resolves into four things, none of which is the fifth:

1. **Agent heartbeat and liveness.** All nine.
2. **Config-applied status.** OpAMP `applying`/`applied`/`failed`.
3. **Pipeline throughput and drop metrics.** Bytes in/out, queue depth.
4. **Config-gap inference from inventory.** Datadog only, and it is the most
   sophisticated version in the market: it "surfaces hosts where telemetry is
   missing or misconfigured, whether due to unconfigured integrations or missing
   Agent settings". But it reasons over inventory versus config, not over data
   received.
5. **Absent everywhere: "the config asked for signal X, therefore assert data
   matching X is present."**

Two products come close enough to be worth naming, because they define the edge
of the unoccupied ground:

- **Cribl Stream** has a **"No Data Received"** Source notification, plus "Low
  Data Volume" and "High Data Volume"
  ([docs.cribl.io](https://docs.cribl.io/stream/notifications/)). Two limits: it
  measures data arriving **at Cribl**, not at the eventual destination, and it is
  a per-Source volume alarm configured by hand, not derived from what the config
  declared it would produce.
- **Honeycomb Telemetry Pipeline** lands pipeline self-telemetry in a free,
  queryable `$pipeline-telemetry$` environment, so you can build SLOs on it and
  alert "when pipelines stop receiving data". Architecturally the most
  interesting, because the pipeline's own telemetry becomes a first-class
  dataset. Still the collector reporting its own throughput, not an assertion
  that a named service's traces are present in the billed dataset.

The gap is therefore narrower than "nobody thought of this" and wider than
"someone already ships it". The missing step in both cases is deriving the
expectation from the config rather than having a human configure the alarm.

## Q7. Prior art for a read-only lens over a GitOps repo with semantic checks

**Verdict: the pattern is thoroughly established and the space is crowded, but
only at the syntactic and policy layer. Read-only, pre-deployment, file-based
checking over a config repo is a completely normal thing to build and nobody will
find it novel. What is not occupied is the semantic layer specific to telemetry,
and above all the arrival check. The prior art validates the delivery model and
leaves the differentiating claim open.**

### The pattern is established, generically

Read-only policy evaluation over manifests in a repository, without a cluster, is
a standard CI capability. Versions verified 2026-08-04:

| Tool | Read-only? | Renders Helm? | Status |
|---|---|---|---|
| **Kyverno CLI** `apply` (files, dirs, URLs, git via `--git-branch`) | Mostly; mutate rules emit output but never write to a cluster | **No.** Pipe `kustomize build \| kyverno apply` | Active, v1.18.2 (2026-07-10) |
| **OPA Gatekeeper `gator test`** (files, dirs, OCI, stdin) | `test`/`verify` yes | **No** | Active, v3.23.0 (2026-07-09) |
| **Conftest** (~19 parsers) | Yes | **No** built-in; `helm template \|` is community practice | Active, v0.69.0 (2026-08-03) |
| **kubeconform** (schema only) | Yes | No | Active, v0.8.0 (2026-06-04) |
| **Polaris** | **No.** Has `polaris fix` and a mutating webhook | Renders a chart dir via `--helm-chart` | Active, v10.2.1 (2026-07-21) |
| **Checkov** | Yes in OSS CLI | **Shells out**: needs `helm` on `$PATH`, runs `helm template --dependency-update` | Active, 3.3.9 (2026-08-02) |
| **Trivy config** | Yes for filesystem scan | **Best in class.** Renders Helm **in-process**, no helm binary needed | Active, v0.73.0 (2026-08-03) |
| **Datree** | Yes | Via plugin | **DEFUNCT.** Repo archived 2024-06-06; the company that maintained it closed in July 2023 |

So "a read-only lens over the repo that adds checks" is a well-worn delivery
model. That is good news for adoption friction and bad news for novelty. The
product cannot claim the pattern; it can only claim the checks. Note also that
only Trivy solves the rendering problem cleanly, which is the Q4 constraint: if
the product needs Helm rendering, Trivy's in-process approach is the reference
implementation to study, and most of the field simply punts.

**None of them does semantic checking.** The languages differ (Kyverno
patterns/CEL/JMESPath, Rego for OPA/Conftest/Trivy, JSON Schema for Polaris,
Python plus a YAML graph DSL for Checkov) but the computation is identical in
shape: parse to a data structure, assert structural facts. "Field exists",
"matches regex", "image tag is not `:latest`". None has a model of runtime
behaviour. None would flag a collector pipeline whose receiver feeds no exporter,
a `memory_limiter` set above the container limit, or two scrape configs
double-counting a metric. The rule *author* holds the semantics; the tool encodes
a structural proxy.

**Cross-repo analysis is universally unsupported.** Conftest's `--combine` gives
one Rego rule sight of every file in a single invocation, and Gatekeeper's
`gator verify` can populate `data.inventory` from hand-assembled files. That is
the ceiling. No tool maintains a persistent index across repositories or treats
"the fleet" as a first-class object. For a product whose unit of value is a
fleet, that is unclaimed ground adjacent to the arrival check.

### Argo CD's extension surface is a poor host for a read-only lens

This matters directly, because "ship it as an Argo CD plugin" is the obvious
distribution idea and the evidence says it is a trap.

- **Config Management Plugins cannot be read-only, and are dangerous as
  validators.** A CMP is a sidecar next to `argocd-repo-server` whose `generate`
  command must write manifests to stdout. A validating CMP must therefore echo
  every manifest through unchanged, and can only signal failure by failing the
  whole sync. There is no advisory mode. Argo CD's own docs carry the warning
  verbatim: "If a CMP renders blank manifests, and `prune` is set to `true`,
  Argo CD will automatically remove resources"
  ([config-management-plugins](https://argo-cd.readthedocs.io/en/stable/operator-manual/config-management-plugins/)).
  A bug in a read-only lens deployed this way deletes production workloads.
- **Notifications is genuinely read-only but sees almost nothing.** Trigger
  expressions run over the `Application` object only (`app.status.sync.status`,
  `app.status.health.status`, annotations). It cannot see manifest content.
- **UI extensions and proxy extensions** can add read-only panels, but installing
  either requires patching `argocd-server` and/or `argocd-cm`, that is,
  admin access to the Argo CD installation rather than tenant self-service.
  Proxy extensions (Beta since v2.7.0) are also not read-only by construction:
  Argo CD proxies whatever verbs the backend accepts.
- **ApplicationSet** templates `Application` CRs only, never workload manifests,
  and is a writer.

Third-party layers over Argo CD (Akuity KubeVision, Codefresh GitOps Runtime,
Harness, argocd-image-updater) are almost all on the write path.
`argocd-image-updater` definitively writes, either mutating the Application spec
via the API or committing `.argocd-source-<appName>.yaml` back into the source
repo. Akuity KubeVision's read-only status could not be verified: the docs page
404'd, and Akuity's own 2025 material describes "safe, automated remediation".

**Conclusion for distribution:** a read-only lens should sit beside Argo CD in
CI, consuming its API, not inside it as a plugin.

### OpenTelemetry-specific config tooling exists, and is syntactic

- **`otelcol validate`**: "Validates the config without running the collector"
  ([command_validate.go](https://github.com/open-telemetry/opentelemetry-collector/blob/main/otelcol/command_validate.go)).
  It goes further than expected: `col.DryRun()` resolves and unmarshals the
  config, runs `confmap.Validate`, `service.Validate()` and `graph.Build(...)`,
  so it **does** build the pipeline graph. But it does not instantiate
  components, open ports or contact backends. **The distro limitation is
  load-bearing**: builders come from the factory maps compiled into *that binary*,
  and the official docs state "only components included in your specific
  Collector binary can be used". A config validated against contrib tells you
  little about a custom OCB distribution. The package docs concede validation is
  "basic" with "more subtle invalid cases that aren't currently checked for": it
  will not catch `send_batch_max_size` below `send_batch_size`, or an effectively
  disabled memory limiter.
- **OtelBin** (by Dash0, [otelbin.io](https://www.otelbin.io/), Apache-2.0,
  launched 2023-10-20) visualises pipelines as swimlanes and validates:
  "References to nonexistant elements are presented as errors, while unused
  elements are displayed as warnings", plus opt-in distribution- and
  version-aware component validation. **No CI mode or GitHub Action found**, no
  git or repo awareness, no fleet concept, and it cannot validate a custom OCB
  distribution.
- **There is no official JSON schema for collector config.**
  opentelemetry-collector issue #9769 ("Improve otel collector configuration w/
  JSON schema") has been **open since 2024-03-15**, unassigned, with no linked
  PRs. Unofficial attempts are tiny (`srikanthccv/otelcol-jsonschema`, 6 stars,
  described by its author as "a fun and good learning experience";
  `nimbushq/otel-validator`, ~30 stars, no connector support) and
  `lightstep/otel-config-validator` was **archived 2024-02-13**. Do not confuse
  this with `open-telemetry/opentelemetry-configuration`, which is stable JSON
  Schema for the **SDK** declarative config, not the collector pipeline.
- **`telemetrygen`** (alpha) "Simulates a client generating telemetry data". **It
  asserts nothing.** It is a traffic source, not an oracle.
- **The collector testbed** is an internal CI harness that validates the
  Collector, not your config.

Everything here answers "is this config well-formed". Nothing answers "did the
config do what it was for". The absence of even a JSON schema after two and a
half years is a notable signal about how little static analysis capability
exists in this domain.

### The commercial fleet space applies config rather than observing it

Of nine products checked, **eight apply configuration and only OtelBin does not**,
and OtelBin is a browser tab with no fleet, no repo and no control plane. Every
one of the eight is a control plane whose defining proposition is that it owns
the config. Where git appears at all (Bindplane, Grafana, Edge Delta, Mezmo,
Cribl), it is either an authoring surface pushing into the control plane or a
mirror the control plane pushes out to. **In no case does a product read a repo
and stop there.**

Delivery mechanisms differ in a way that matters: Grafana Fleet Management (GA
2025-03-12) uses Alloy `remotecfg` plus an OpAMP endpoint; **Datadog uses its own
Remote Configuration, not OpAMP**; Bindplane, Honeycomb and ControlTheory use
OpAMP. Consolidation is live: **Dynatrace announced it would acquire Bindplane on
2026-04-08** ([press release](https://www.dynatrace.com/news/press-release/dynatrace-to-acquire-bindplane/)),
and Bindplane was the canonical OpAMP implementation.

The only adoption figure located anywhere in this space: Grafana's Fleet
Management GA blog states its public preview reached "more than 4,000 Grafana
Cloud stacks across 23,000+ collectors" (2025-03-12). **No quantitative data
found** for any other product's fleet size.

The read-only-lens-over-a-repo position is therefore genuinely vacant. That is
either an opportunity or a signal that the market has concluded config authority
and observation belong together. The evidence cannot distinguish those two
readings, and it would be dishonest to present the vacancy as validation.

### The unoccupied ground

Nothing found does either of these:

1. Semantic analysis of collector configuration specifically, as opposed to
   generic Kubernetes policy. "Every service in this repo exports traces to a
   configured endpoint", "this pipeline drops all logs from namespace X", "the
   `k8sattributes` processor is missing from the metrics pipeline on 4 of 30
   collectors" are collector-domain statements that no generic policy engine
   expresses naturally.
2. The conformance cross between declared intent and observed arrival. No tool
   found reads a config, derives what telemetry it should produce, and checks a
   backend to see whether it did.

The second is the product's remaining claim, and it survives this search intact.

## Bottom line: is targeting Argo CD alone sufficient, insufficient, or premature?

**Insufficient, and premature, for different reasons. Not wrong, but wrong as a
sole target.**

**Insufficient**, on the numbers that exist:

- Argo CD is the leading GitOps controller, but GitOps applies to *nearly all*
  deployment for only 22% of an already cloud-native-biased CNCF sample, and 53%
  say some, just beginning, or not started (CNCF 2024, Q55, n=689).
- Helm is in production use at 77% against 43% for the entire Argo project
  family, and is the preferred packaging method for 75% against Kustomize's 14%
  (CNCF 2024, Figures 12 and 13). Argo grew to 52% in the 2025 wave, but so did
  Flux (17% to 23%), so the GitOps segment is not consolidating onto one tool.
- OpenTelemetry's own documentation sends new adopters to the Helm chart and
  never mentions GitOps, Argo CD, Flux or Kustomize on any install page.
- 51% of collector deployments now include VMs and 18% bare metal, and 50% of
  fleets over 100 collectors span both Kubernetes and VMs. Argo CD cannot reach
  any of that, at any adoption level.

An Argo-CD-only lens is therefore a lens over a minority of collector fleets, and
a partial lens even within the fleets it does cover.

**Premature**, because the strongest reason to integrate with Argo CD is not the
one currently being relied on. The load-bearing claim in the ticket is that
Argo CD's sync status supplies the intended-versus-declared cross for free. It
partly does, but with real qualifications: it is scoped to fields git owns, on
tracked resources, minus whatever `ignoreDifferences` suppresses, on a diff
strategy that varies, with up to a three-minute detection window, and it treats
the collector config inside a ConfigMap as an opaque string, so it can say "this
changed" but never "the otlp receiver left the traces pipeline". Meanwhile the
*better* argument for Argo CD integration, that its repo-server already renders
Helm and Kustomize so a lens could consume rendered manifests instead of
re-implementing rendering, is not the one being made, and is exactly the argument
that Q4 shows matters most.

**What the evidence supports instead:**

1. **Make the input format the primary target, not the tool.** Q4 shows the hard
   problem is rendering: Helm values plus presets, Kustomize overlays, v1alpha1
   string blobs, v1beta1 open maps. A lens that can render and analyse those is
   useful regardless of what applies them, and it works for the Helm-directly
   majority, for CI-driven `kubectl apply`, and for Argo CD and Flux alike.
2. **Treat Argo CD as the first integration, not the architecture.** Q3 gives it
   two advantages that are stronger than the drift argument: it answers "which
   commit is live" from a single object, and it is **the only one of the two that
   returns rendered manifests over an API** (`GET /api/v1/applications/{name}/manifests`).
   Given that Q4 shows rendering is the hard part, that is the real prize. Flux
   has no rendered-manifest endpoint at all. Build to Argo CD, but behind a
   boundary that also admits Flux, a rendered-manifest directory, and eventually
   a VM-side inventory. Expect the Flux adapter to be strictly poorer: a
   composite revision string to parse, no revision at all on `HelmRelease`, no
   `OutOfSync` concept, and two drift models with opposite defaults.
3. **Do not let Argo CD's sync status stand in for conformance.** Q5 and Q6
   together show that `Synced` plus `Healthy` is fully compatible with zero
   telemetry arriving. That gap is real, is confirmed rather than refuted, and is
   unoccupied by any tool found in Q7. It is the claim worth building on, and it
   does not depend on Argo CD at all.
4. **Do not ship it as an Argo CD plugin.** Q7 found that the Config Management
   Plugin interface cannot be read-only, and that a CMP emitting blank manifests
   with `prune: true` deletes resources. Notifications sees only the Application
   object. UI and proxy extensions need admin access to the Argo CD install. Sit
   beside Argo CD in CI and consume its API; do not sit inside it.

### Two things that would change the verdict

**Direct evidence on the actual question, which nobody has collected.** The
highest-value next research step is not more desk research; it is getting the
OpenTelemetry End User SIG to add a deployment-mechanism question to the next
collector survey, or running that question independently. Every number in this
document is a proxy for it.

**OpAMP maturing past alpha.** If config authority moves to OpAMP servers, the
repository stops being the thing the fleet reconciles against and becomes an
input pushed into a control plane, which is already how all eight config-applying
commercial products work. The spec is Beta and shipping (v0.19.0, 2026-08-03);
the collector extensions are alpha. This is a tracked assumption, not a current
problem.

### One honest caution on the Q7 result

The read-only-lens-over-a-repo position being vacant is not by itself validation.
It is equally consistent with the market having concluded that config authority
and config observation belong in the same product, which is what eight of nine
vendors have built. The arrival check is genuinely unoccupied and genuinely
valuable. The read-only constraint around it is a product choice that the
evidence neither supports nor refutes.
