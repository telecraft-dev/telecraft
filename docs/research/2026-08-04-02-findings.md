# 02: What Elastic Fleet exposes over its API for OTel collectors

Resolves `issues/02-fleet-api-for-otel-collectors.md`. Two evidence sources: Elastic
documentation plus `elastic/kibana`, `elastic/fleet-server` and `elastic/elastic-agent-libs`
source; and a live read-only probe of the PoC Serverless project.

## Method and its limits

**Live target.** `https://playground-d57725.kb.europe-west2.gcp.elastic.cloud`, Kibana
`9.6.0`, `build_flavor: serverless`, build date 2026-07-28. Fleet reports
`{"isReady":true,"missing_requirements":[]}`. All calls were `GET` with an `ApiKey`
header. No state was created or modified.

**The population is empty.** Every collection endpoint returned zero rows:

```
GET /api/fleet/agents          -> {"items":[],"total":0,"page":1,"perPage":5}
GET /api/fleet/agent_status    -> all counters 0, "all":0, "active":0
GET /api/fleet/agent_policies  -> {"items":[],"total":0}
GET /api/fleet/enrollment_api_keys -> {"list":[],"items":[],"total":0}
```

The `.fleet-agents` index does not yet exist on this project (a request that reads it
returns `index_not_found_exception`). So the live probe establishes **that the endpoints
exist, are registered, and what their envelopes look like**. It cannot show a populated
collector record. Everything below about per-record *field content* is from schema and
source, and is labelled as such.

Throughout, I distinguish **"the API has no such field"** from **"the API returned nothing
because nothing is enrolled"**. Where a claim rests only on an empty response, I say so.

**One probe technique needs a caveat.** I tried to enumerate the agent schema by feeding
candidate field names to the `kuery` parameter and watching for
`KQLSyntaxError: This type 'X' is not allowed`. A control test showed the validator is
**permissive for any dotted path**: `zzzbogus.status`, `health.zzzbogus` and
`effective_config.zzzbogus` were all accepted. So dotted-path acceptance proves nothing
about nested structure, and I have not used it as evidence. Bare single-segment names *are*
checked against a real allowlist, and that part is informative: `type`, `status`, `active`,
`tags`, `policy_id`, `last_checkin`, `local_metadata`, `upgrade_details`,
`unhealthy_reason` were accepted; `health`, `effective_config`, `components`,
`pipeline_config`, `last_known_status` were rejected as bare names (they are object or
runtime fields, not queryable leaves).

**Version caveat.** Source was read on `main` (post-9.5). The live target is 9.6.0
Serverless. Feature landing dates are from changelogs, not by checking out old branches.

## Q1. Which endpoints return OTel collectors, as distinct from Elastic Agents? What does a collector's record contain?

**Verdict: there is no separate collector endpoint. Collectors are returned by the ordinary
agent endpoints and are distinguished by the top-level field `type: "OPAMP"`. The record is
an Elastic Agent record plus seven collector-specific fields.**

There is no dedicated collector API. Probed live and confirmed absent:

```
GET /api/fleet/otel_collectors -> HTTP 404 {"statusCode":404,"error":"Not Found"}
GET /api/fleet/collectors      -> HTTP 404 {"statusCode":404,"error":"Not Found"}
```

That is a genuine "no such endpoint" (bare `Not Found`), not an empty result.

Collectors come back from `GET /api/fleet/agents`, `GET /api/fleet/agents/{agentId}` and
`GET /api/fleet/agents/{agentId}/effective_config`.

The discriminator is the top-level `type` field. Its enum gained a fourth value
(`x-pack/platform/plugins/shared/fleet/common/constants/agent.ts`):

```typescript
export const AGENT_TYPE_PERMANENT = 'PERMANENT';
export const AGENT_TYPE_EPHEMERAL = 'EPHEMERAL';
export const AGENT_TYPE_TEMPORARY = 'TEMPORARY';
export const AGENT_TYPE_OPAMP = 'OPAMP';
```

The value is the literal string `OPAMP`. There is no `otel-collector` value anywhere in the
source. The published API reference for "Get agents" lists the same enum:
`PERMANENT`, `EPHEMERAL`, `TEMPORARY`, `OPAMP`
(<https://www.elastic.co/docs/api/doc/kibana/operation/operation-get-fleet-agents>).

Live, `kuery=type:OPAMP` is accepted and returns `{"items":[],"total":0}` — the field and
value are valid; there are simply no collectors enrolled. So filtering the ungoverned
population is a one-parameter query: `GET /api/fleet/agents?kuery=type:OPAMP`.

A second, differently-scoped field matters. The **nested** `agent.type` is set by
fleet-server from the collector's own OpAMP `AgentDescription` identifying attribute
`service.name` (`elastic/fleet-server/internal/pkg/api/handleOpAMP.go`, ~L330):

```go
case semconv.ServiceNameKey:
    agentType = ia.GetValue().GetStringValue()
    meta.Elastic.Agent.Name = agentType
```

So `type` is `OPAMP` (Fleet's classification) while `agent.type` is the collector's
self-declared identity, e.g. `otelcol-contrib`. That same string is also injected as the
first entry in `tags`.

Collector-specific fields on the agent record
(`x-pack/platform/plugins/shared/fleet/common/types/models/agent.ts`):

```typescript
identifying_attributes?:     { [key: string]: string | number };
non_identifying_attributes?: { [key: string]: string | number };
sequence_num?:  number;
capabilities?:  string[];
health?:        ComponentHealth;
effective_config?: any;
signals?:       string[];
pipeline_config?: string;
```

`identifying_attributes` and `non_identifying_attributes` are the collector's full OpAMP
`AgentDescription` attribute sets, stored verbatim as key/value maps. This is where
resource attributes such as `service.name`, `service.version`, `host.name` and `os.type`
land. `capabilities` is the collector's declared OpAMP capability list.

The `.fleet-agents` document schema (`elastic/fleet-server/model/schema.json`) carries these
as free-form:

```json
"effective_config": { "description": "The effective config that the collector is running", "format": "raw" },
"health":           { "description": "Health information of the collector", "format": "raw" },
"capabilities":     { "description": "List of capabilities of the collector", "type": "array", "items": {"type":"string"} },
"sequence_num":     { "description": "The sequence number of the last collector message", "type": "integer" }
```

Two collector-only lifecycle routes exist, both `POST` and therefore **not exercised**:
`/api/fleet/agents/{agentId}/remove_collector` and `/api/fleet/agents/bulk_remove_collectors`
(`common/constants/routes.ts` L196-197). `server/services/agents/remove_collector.ts` guards
with `if (agent.type !== AGENT_TYPE_OPAMP)`. Their description is worth noting for the
governance model: removal "does not invalidate API keys, so the collector can reconnect on
its own" — list hygiene, not revocation.

## Q2. What is the shape of the reported effective config?

**Verdict: a structured JSON object — the collector's YAML config parsed into a tree, not a
raw blob and not a typed schema. It is the full config, with scalar secret-looking values
replaced by the string `REDACTED`. It is returned by a dedicated per-agent endpoint, not on
the list response.**

Endpoint (`common/constants/routes.ts` L185):

```
GET /api/fleet/agents/{agentId}/effective_config
```

**Confirmed registered on the live target.** This is the one place the empty population
still yielded a positive signal. Compare the two 404s:

```
GET /api/fleet/agents/x/effective_config
  -> {"message":"index_not_found_exception ... no such index [.fleet-agents]"}
GET /api/fleet/agents/x/bogus_route
  -> {"message":"Not Found"}
```

The first reached a handler and tried to query `.fleet-agents`; the second did not match a
route. Since the route is registered behind `if (experimentalFeatures.enableOpAMP)`
(`server/routes/agent/index.ts` L168), **OpAMP support is enabled on this Serverless
project**, not merely present in the source.

The transformation happens in fleet-server, before anything is written to Elasticsearch
(`internal/pkg/api/handleOpAMP.go` L487-507):

```go
func ParseEffectiveConfig(effectiveConfig *protobufs.EffectiveConfig) ([]byte, error) {
	if effectiveConfig.ConfigMap != nil && effectiveConfig.ConfigMap.ConfigMap[""] != nil {
		configMap := effectiveConfig.ConfigMap.ConfigMap[""]
		if len(configMap.Body) != 0 {
			bodyBytes := configMap.Body
			obj := make(map[string]any)
			if err := yaml.Unmarshal(bodyBytes, &obj); err != nil {
				return nil, fmt.Errorf("unmarshal effective config failure: %w", err)
			}
			redact.Redact(obj, redact.WithIgnoreKeys("routekey"))
			effectiveConfigBytes, err := json.Marshal(obj)
			...
```

So: OpAMP delivers config-file bytes; fleet-server YAML-unmarshals them, redacts, and
re-marshals to JSON. It is persisted whole
(`internal/pkg/checkin/checkinWithEffectiveConfig.painless`):

```painless
ctx._source.effective_config = params.OpAMPEffectiveConfig;
```

Kibana applies **no further transformation**. The response schema
(`server/types/rest_spec/agent.ts` L421-423) is deliberately untyped:

```typescript
export const GetAgentEffectiveConfigResponseSchema = schema.object({
  effective_config: schema.maybe(schema.any()),
});
```

matching `effective_config?: any` on the model. So the consumer receives the whole OTel
config tree as plain JSON and must interpret it itself. The Fleet UI round-trips it back to
YAML for display (`agent_effective_config_flyout.tsx`: `yaml.stringify(agentData.effective_config)`).

**Full or subset?** Full, with two real losses.

1. **Only the unnamed config file survives.** `ParseEffectiveConfig` reads only
   `ConfigMap.ConfigMap[""]`. OpAMP permits a collector to report several named config
   files; any non-empty key is silently dropped, as is `content_type`. A collector that
   reports its config split across named entries will surface partially or not at all.
2. **Redaction.** `redact.Redact` from `elastic/elastic-agent-libs`
   (`redact/redact.go` L276-289):

```go
func redactKey(k string, ro *redactOptions) bool {
	if slices.Contains(ro.ignoreKeys, k) { return false }
	k = strings.ToLower(k)
	return strings.Contains(k, "auth") || strings.Contains(k, "certificate") ||
		strings.Contains(k, "passphrase") || strings.Contains(k, "password") ||
		strings.Contains(k, "token") || strings.Contains(k, "key") ||
		strings.Contains(k, "secret")
}
```

Case-insensitive **substring** matching, value replaced by the constant `"REDACTED"`.
`strings.Contains(k, "key")` is broad — it catches `api_key` as intended but also anything
merely containing "key", which is why the routing connector's `routekey` needed an explicit
exemption.

**Redaction does not damage structure.** Reading the traversal (`redact.go` L150-215): maps
and slices are *recursed into*, never replaced wholesale; only leaf `string` values under a
matching key become `REDACTED` (plus URL userinfo rewritten via `redactURL`). None of
`service`, `pipelines`, `receivers`, `processors`, `exporters`, `connectors`, `extensions`
contains a trigger substring. So the config skeleton and every component name survives
intact; only secret scalars are masked.

Historical caveat: redaction of values nested inside lists-of-maps was only fixed in
fleet-server 9.4.2 / 9.3.5 (PR elastic/fleet-server#6955). Before that, secrets inside list
items were **not** redacted.

## Q3. Can it be parsed into receivers, processors, exporters *and the pipelines wiring them together*?

**Verdict: yes, fully — including pipeline wiring, not merely component lists. This is the
strongest finding in the ticket. Two independent routes give it, one per-collector and one
in bulk.**

Because `effective_config` is the parsed YAML tree (Q2), the entire OTel config structure is
present verbatim under its normal keys:

- `effective_config.receivers` / `.processors` / `.exporters` / `.connectors` — maps keyed
  by component instance name, including variant suffixes (`otlp/grpc` vs `otlp/http` remain
  distinct keys)
- `effective_config.service.pipelines.<pipelineName>.receivers` — array
- `effective_config.service.pipelines.<pipelineName>.processors` — array, **order preserved**
- `effective_config.service.pipelines.<pipelineName>.exporters` — array
- `effective_config.service.extensions` — array

This is not inference from the YAML round-trip. Elastic itself reaches into exactly these
paths in two Painless runtime fields, which is direct proof the structure is present,
stable, and depended upon.

`server/services/agents/build_pipeline_config_runtime_field.ts` walks the wiring:

```painless
if (cfg.service.pipelines instanceof Map) {
  def pipeNames = new ArrayList(cfg.service.pipelines.keySet());
  Collections.sort(pipeNames);
  for (def p : pipeNames) {
    def pipe = cfg.service.pipelines[p];
    def r  = pipe.receivers  instanceof List ? new ArrayList(pipe.receivers)  : new ArrayList();
    def pr = pipe.processors instanceof List ? new ArrayList(pipe.processors) : new ArrayList();
    def ex = pipe.exporters  instanceof List ? new ArrayList(pipe.exporters)  : new ArrayList();
    Collections.sort(r); Collections.sort(ex);
    parts.add('pipe:' + p + '[' + String.join(',', r) + '|' + String.join(',', pr) + '|' + String.join(',', ex) + ']');
  }
}
```

with the file's own header comment stating the contract:

```
// service.pipelines: sorted pipeline names; receivers+exporters sorted, processors in config order
// top-level component sections (receivers, processors, exporters, connectors): sorted keys
// service.extensions: sorted active extension list
```

and, in the loop over top-level sections, the note that variant-suffixed names are kept
whole so `otlp/grpc` and `otlp/http` are distinct.

Note processors are deliberately **not** sorted, because "order is semantically
significant". That means processor ordering within a pipeline is recoverable — which
matters if Amp-Up ever wants to reason about, say, a redaction processor sitting after an
exporter-bound batch step.

### Two routes to the wiring, with different costs

**(a) Bulk, one call: the `pipeline_config` field on the agent list response.** The runtime
field above emits a fingerprint string of the form:

```
receivers:<sorted keys>;processors:<...>;exporters:<...>;connectors:<...>;ext:<sorted>;pipe:<name>[<recv>|<proc>|<exp>];pipe:...
```

Kibana attaches it in `server/services/agents/helpers.ts`:

```typescript
if (hit.fields?.pipeline_config?.length) {
  agent.pipeline_config = hit.fields.pipeline_config[0];
}
```

This string **is itself the full pipeline wiring in compact form** — every pipeline name
with its receiver, processor and exporter lists. It arrives on `GET /api/fleet/agents`, so
N collectors cost one request. It carries **names only, never config values**, and the REST
schema caps it at 10000 characters, so a very large config could be truncated or rejected.

A companion runtime field `signals` (`build_signals_runtime_field.ts`) derives the distinct
pipeline-type prefixes:

```painless
if (params._source?.effective_config?.service?.pipelines == null) return;
for (def k : params._source.effective_config.service.pipelines.keySet()) {
  int i = k.indexOf('/');
  def seg = i == -1 ? k : k.substring(0, i);
  if (seen.add(seg)) emit(seg);
}
```

so `logs/foo` and `logs/bar` both yield `logs`. Live, both are accepted as sort fields:
`GET /api/fleet/agents?sortField=pipeline_config` and `?sortField=signals` return HTTP 200
with `{"items":[],"total":0}` — accepted, and empty only because nothing is enrolled.

**(b) Per-collector, full fidelity: `GET /api/fleet/agents/{agentId}/effective_config`.**
Returns the whole tree including component *configuration*, not just names — endpoints,
timeouts, filters, and so on. Costs one request per collector.

This directly answers the ticket's worry. A `filelog` receiver appearing in
`effective_config.receivers` proves nothing on its own, but
`effective_config.service.pipelines` tells you precisely which pipelines reference it and
what those pipelines export to. The wiring is available, both cheaply in bulk and in full
per collector.

**Caveat, stated plainly:** I could not exercise either against a real collector, because
the population is empty. The structure is established from the Painless source, the
response schema, and Elastic's own dependence on those paths — not from an observed record.

## Q4. What health and status fields are exposed, and at what granularity?

**Verdict: two granularities, and the distinction matters. The full recursive OpAMP
`ComponentHealth` tree is stored and returned under `health`. But the roll-up `status` that
drives the agent list is flattened from the top level only, and never traverses that tree.**

fleet-server marshals the OpAMP health message whole
(`handleOpAMP.go` L439, then the Painless upsert):

```go
healthBytes, err := json.Marshal(aToS.Health)
```
```painless
if (params.OpAMPHealth != null) { ctx._source.health = params.OpAMPHealth; }
```

Kibana passes it straight through in `helpers.ts` (`health: hit._source?.health`) and types
it recursively (`common/types/models/agent.ts` L436-445):

```typescript
export interface ComponentHealth {
  healthy: boolean;
  status: string;
  status_time_unix_nano?: number;
  start_time_unix_nano?: number;
  last_error?: string;
  component_health_map?: {
    [key: string]: ComponentHealth;
  };
}
```

That is a faithful mapping of the OpAMP spec's `ComponentHealth`
(`open-telemetry/opamp-spec`, `proto/opamp/v1/opamp.proto` L790-819), whose
`component_health_map` is documented as able to "nest as deeply as needed to describe the
underlying system". Kibana omits only the spec's development-stage `attributes` field.

Collectors populate that map per component, and the Fleet UI renders the tree
(`opamp_component_health.tsx` builds an `EuiTreeView`, splitting keys on `:` into
`Pipeline: logs/foo`, `Receiver: otlp`, and so on). So **per-pipeline and per-receiver health
is reachable through the API**, at whatever depth the collector reports it.

The flattening is separate and happens at ingest, for the coarse status only
(`handleOpAMP.go` L423-431):

```go
status := CheckinRequestStatusOnline
if aToS.Health != nil {
    if !aToS.Health.Healthy {
        status = CheckinRequestStatusError
    } else if aToS.Health.Status == healthStatusRecoverableError {
        status = CheckinRequestStatusDegraded
    }
```

`elastic/fleet-server/docs/opamp.md` states it outright: Fleet-server maps `ComponentHealth`
to simplified statuses, and "the spec's nested `component_health_map` is not traversed; only
the top-level health is used".

Practical consequence: a collector whose `filelog` receiver is failing but whose top-level
health is `true` will show as `online` in the list, and the failure is only visible by
reading `health.component_health_map`. Amp-Up should read the tree, not the status.

Other status fields, confirmed live in the empty-population envelope of
`GET /api/fleet/agents?getStatusSummary=true`:

```json
"statusSummary":{"online":0,"error":0,"inactive":0,"offline":0,"updating":0,
"unenrolled":0,"degraded":0,"enrolling":0,"unenrolling":0,"orphaned":0,"uninstalled":0}
```

That enumerates the full status vocabulary directly from the live API. Also present per
record: `last_checkin`, `last_checkin_status` (`error`/`online`/`degraded`/`updating`/
`starting`/`disconnected`), `last_checkin_message` (set from `Health.LastError`, falling
back to `Health.Status`), `unhealthy_reason` (`input`/`output`/`other`), and `sequence_num`
for detecting missed OpAMP messages.

The `components[]` array with `STARTING`/`CONFIGURING`/`HEALTHY`/`DEGRADED`/`FAILED`/
`STOPPING`/`STOPPED` per unit is an **Elastic Agent** construct, described in the schema as
"Elastic Agent components detailed status information". For OPAMP-type records the
equivalent granularity lives in `health.component_health_map`, not here.

## Q5. What does Fleet expose about collectors it did not configure?

**Verdict: this is the whole population — Fleet's OTel support is monitoring-only, so every
collector it sees is one it did not configure. But visibility requires the collector to opt
in by pointing its OpAMP extension at Fleet Server with a valid enrollment key. Collectors
that never connect are invisible; Fleet offers no discovery.**

Fleet never pushes config to an OpAMP collector. `elastic/fleet-server/docs/opamp.md` lists
`ServerToAgent.remote_config` under features **not implemented**, alongside
`remote_config_status`, `package_statuses`, `connection_settings_request` and
`available_components`. The intent is stated in the enrolment code itself
(`handleOpAMP.go` L384-402):

```go
// Setting revision to 1, the collector won't receive policy changes and 0 would keep the collector in updating state
PolicyRevisionIdx: 1,
```

So the `policy_id` on a collector record is a bookkeeping and authorisation artefact,
deliberately pinned so no policy is ever delivered. The docs confirm the user-visible
consequence: "OTel Collectors don't display an agent policy in the Agents list. They use
managed policies that can't be modified"
(<https://www.elastic.co/docs/reference/fleet/monitor-otel-collectors>).

There is consequently **no managed/unmanaged distinction in the data model**. The record is
identical either way. Everything in Q1-Q4 applies uniformly to self-configured collectors:
their hand-authored `effective_config`, their pipeline wiring, their nested health.

For the `ungoverned` quadrant this is close to ideal — Fleet reports config it did not
author, faithfully — with one hard boundary.

**The boundary: collectors must opt in.** Enrolment requires a valid Fleet enrollment API
key. `handleOpAMP.go` calls `dl.FindEnrollmentAPIKey(...)` and rejects otherwise (HTTP 401).
`docs/opamp.md`: "Fleet-server auto-enrolls unknown agents on first message using the
enrollment API key's associated policy, creating a document in the `.fleet-agents` index
with type `OPAMP`." Transport is HTTP at `/v1/opamp`; no WebSocket.

So the practical taxonomy is three-way, not two:

| Population | Visible to Fleet API? |
|---|---|
| Collector with `opamp` extension + valid enrollment key | Yes — full record, full effective config, full health |
| Collector running but not configured to talk to Fleet Server | **No.** Fleet has no scan, discovery or inventory capability |
| Elastic Agent in otel/EDOT mode, Fleet-policy-managed | Yes, but as `type: PERMANENT` — a different population |

Amp-Up's `ungoverned` quadrant is therefore only partly served: Fleet covers
*self-configured but connected*, and is blind to *unconnected*. Closing that gap needs a
source other than Fleet.

Live evidence is limited here. `GET /api/fleet/enrollment_api_keys` returned
`{"list":[],"items":[],"total":0}` — no enrollment key exists yet, so nothing could have
enrolled. That is consistent with, but not proof of, the above; the mechanism is established
from source and `docs/opamp.md`.

Supporting detail: Kibana's "Add > Collector (OpAMP)" flow auto-creates a hidden managed
placeholder policy (`add_collector_flyout.tsx`, `OPAMP_POLICY_ID = 'opamp'`,
`is_managed: true`) purely to mint an enrolment token, and filters it out of the policy list.
Live, `GET /api/fleet/agent_policies` returned `{"items":[],"total":0}`, so that policy has
not been created on this project.

## Q6. What authentication does the API need, and can a read-only key reach all of it?

**Verdict: a Kibana API key carrying the Fleet `fleet-agents-read` privilege reaches every
read described above. Nothing in Q1-Q5 requires a write privilege. I could not empirically
prove the *minimal* key works, because minting one is a write operation and out of scope for
this ticket.**

Authentication is a Kibana API key in an `Authorization: ApiKey <key>` header. Fleet's
mutating routes additionally require `kbn-xsrf: true`; the reads used here did not, though
I sent it throughout.

The privilege on the effective-config route (`server/routes/agent/index.ts` L170-177):

```typescript
router.versioned.get({
  path: AGENT_API_ROUTES.EFFECTIVE_CONFIG_PATTERN,
  security: { authz: { requiredPrivileges: [FLEET_API_PRIVILEGES.AGENTS.READ] } },
  summary: `Get an agent's effective config`,
```

and the constant resolves to `fleet-agents-read`
(`server/constants/api_privileges.ts`, with `PLUGIN_ID = 'fleet'`):

```typescript
AGENTS: {
  READ: `${PLUGIN_ID}-agents-read`,
  ALL:  `${PLUGIN_ID}-agents-all`,
},
```

The same `AGENTS.READ` privilege covers the agent list and agent-detail routes. So a key
scoped to Fleet **Agents: Read** reaches: the collector list filtered by `type:OPAMP`, each
record's `health` tree, `identifying_attributes`, `capabilities`, `sequence_num`, the
`pipeline_config` and `signals` runtime fields, and the full `effective_config` per
collector. That is the entire declared-state reading.

**Honest limits on the live check.** The PoC key is broad, not minimal. `_has_privileges`
returned:

```json
{"has_all_requested":true,"application":{"kibana-.kibana":{"*":{
  "feature_fleet.read":true,"feature_fleetv2.all":true,"feature_fleetv2.read":true}}}}
```

`feature_fleetv2.all` is a write-capable privilege, so the successful reads above do **not**
demonstrate that a read-only key suffices. Confirming that would mean creating a restricted
key — a write — which this ticket forbids. The `fleet-agents-read` claim rests on the route
declarations in source, which is strong but not live-verified. Ticket 06 should verify it
when it provisions a key.

Two further notes. The key is a Kibana key: it does **not** grant direct access to the
underlying index. Probing `.fleet-agents` returned
`security_exception: action [indices:data/read/search] is unauthorized ... on restricted
indices [.fleet-agents]`, and the mapping read was refused likewise. Reading collectors must
go through the Fleet API; there is no shortcut to the index, and on Serverless there is
unlikely ever to be one. Separately, enrolling a collector needs an *enrollment* API key,
which is a different credential from the Kibana API key used for reading — relevant to
ticket 06, not to a read-only connector.

## Consolidated answer for the wayfinder

Fleet can populate a **genuinely structured declared-state reading** for OTel collectors,
not a shallow one. The pipeline graph — which receivers and exporters each named pipeline
wires together, with processor order preserved — is available, and that was the load-bearing
uncertainty.

Suggested read pattern for the connector:

1. `GET /api/fleet/agents?kuery=type:OPAMP&perPage=...` — one call. Yields identity,
   `agent.type`, `status`, `last_checkin`, the recursive `health` tree, `capabilities`,
   `identifying_attributes`, plus `pipeline_config` (compact full wiring) and `signals`.
2. `GET /api/fleet/agents/{agentId}/effective_config` — one call per collector, only when
   component *configuration values* are needed beyond names.

Four caveats to carry forward:

- Fleet sees only collectors that opt in via OpAMP with an enrollment key. It has no
  discovery. The truly unconnected part of the `ungoverned` quadrant needs another source.
- Fleet is monitoring-only for these collectors: it can read declared state but cannot
  change it. Any "govern" action is out of Fleet's reach today.
- Secret-ish scalar values are redacted to `"REDACTED"` by substring match on key names, and
  only the unnamed OpAMP config-file entry is ingested. Structure survives; some values do not.
- The roll-up `status` ignores nested component health. Read `health.component_health_map`,
  not `status`, or a collector with a dead receiver will read as healthy.

Everything about record *content* is established from schema and source. The live probe
confirmed the endpoints exist, that OpAMP support is enabled on this 9.6.0 Serverless
project, and the response envelopes — but with zero collectors enrolled it could not show a
populated record. Ticket 06 should re-run steps 1 and 2 against a real collector to confirm.
