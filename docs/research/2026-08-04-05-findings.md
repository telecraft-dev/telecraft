# 05: What "conformance with the proposed schema" means in OTel terms

Research findings for issue `05-schema-conformance-in-otel-terms.md`. Sources are the
OpenTelemetry specification, the semantic-conventions repo, and OTel Weaver. Read
against `internal/model/model.go` (`ConfigAssertion`, `SignalAssertion`) and
`internal/provider/provider.go` (`TelemetryProvider`).

## Headline

There are two separate things the ecosystem calls a "schema", and conflating them is
the trap this ticket exists to avoid.

1. **Telemetry Schema / schema URL** (in the OTel *specification*). This is a version
   migration mechanism. It is explicitly **not** a validator. Nothing about it can be
   used to check conformance.
2. **Semantic convention registry** (the semconv YAML model, tooled by Weaver). This
   *is* a shape declaration: types, requirement levels, enum members, units,
   instruments. This is the thing to adopt.

The declaration side is a solved standard. The checking side is solved only for an
OTLP stream at collection time, and not at all for telemetry that has already landed
in a backend. That second half is the gap.

---

## Q1. Semantic conventions: versioning, publication, machine-readable form, tooling

**Verdict: a real, machine-readable, versioned standard exists. Adopt it. The YAML
model is the artefact to build against, and Weaver is the toolchain that consumes it.**

### Versioning and publication

- Published from `open-telemetry/semantic-conventions`, tagged `v{major}.{minor}.{patch}`.
- The human-readable docs in `docs/` are *generated* from the YAML in `model/`. The
  YAML is the source of truth, the Markdown is an artefact.
- `model/manifest.yaml` carries the registry's `schema_url`. Post-release automation
  bumps it to `{major}.{minor+1}.0-unreleased`
  (`RELEASING.md`: the post-release workflow "opens a pull request against main bumping
  the development `schema_url` in `model/manifest.yaml`").
- The corresponding *schema file* is published at `https://opentelemetry.io/schemas/<version>`,
  auto-discovered downstream: "New release is then auto-discovered by opentelemetry.io
  pipelines which (via bot-generated PR) eventually results in new version of schema
  file being published" (`RELEASING.md`). Note this published file is the migration
  document from Q2, not the convention definitions.

### The machine-readable form

The semconv YAML model (`open-telemetry/weaver/schemas/semconv-syntax.md`). Groups are
typed: `attribute_group`, `span`, `event`, `metric`, `resource`, `entity`, `scope`.
Per attribute the model carries:

| Field | Allowed values |
|---|---|
| `type` | `string`, `int`, `double`, `boolean`, `string[]`, `int[]`, `double[]`, `boolean[]`, `template[<type>]`, or an enum with `members` |
| `requirement_level` | `required`, `conditionally_required`, `recommended`, `opt_in` |
| `stability` | `stable`, `development`, `alpha`, `beta`, `release_candidate` |
| `examples`, `note`, `brief`, `deprecated`, `sampling_relevant` | metadata |

Metric groups add `metric_name`, `instrument` (`counter`, `histogram`, `gauge`,
`updowncounter`) and `unit`. Enum members carry `id`, `value`, `stability`.

`requirement_level` is the field that matters most for Amp-Up, because it is the direct
analogue of `SignalAssertion.RequiredAttributes`. Its definitions
(`docs/general/attribute-requirement-level.md`):

- **Required**: "All instrumentations MUST populate the attribute."
- **Conditionally Required**: "All instrumentations MUST populate the attribute when the
  given condition is satisfied."
- **Recommended**: "Instrumentations SHOULD add the attribute by default if it's readily
  available and can be efficiently populated."
- **Opt-In**: "Instrumentations SHOULD populate the attribute if and only if the user
  configures the instrumentation to do so."

This four-level scale is strictly richer than Amp-Up's current binary
`RequiredAttributes []string`. It is also a better fit for `AttributeCoverage`:
`recommended` is exactly the case where partial coverage is legitimate rather than a
finding.

### Tooling that consumes it

**Weaver** (`open-telemetry/weaver`) is the reference toolchain. Subcommands:

- `registry check`: validates the registry YAML itself, plus Rego policies (`-p/--policy`).
- `registry generate`: templated codegen and docs (MiniJinja + JQ preprocessing).
- `registry diff`: differences between two registry versions.
- `registry live-check`: checks **actual telemetry** against a registry. See Q3.
- `registry emit`: emits example signals from the registry.
- `registry infer`: derives a registry **from observed OTLP**. See Q4/Q5.
- `registry package`, `registry json-schema`, `registry stats`, `registry mcp`.
- `registry resolve` and `registry search` are **deprecated** under the V2 schema.

Caveat worth carrying into ticket 16: Weaver is actively churning (V2 registry schema,
deprecated subcommands). It is the standard, but it is not a frozen one.

## Q2. Schema URLs and schema files: transformation, not validation

**Verdict: the working understanding is CORRECT, and the specification says so in its
own words. The OTel telemetry schema mechanism is a version-to-version migration
format. It is NOT a conformance-checking mechanism and cannot be made into one. Amp-Up
must not build schema conformance on schema URLs.**

This is confirmed from the specification text, not inferred.

### Direct spec evidence

`specification/schemas/README.md`, section **"What is Out of Scope"**:

> "The concept of schema defined in this proposal does not attempt to fully describe the
> shape of telemetry. The schema for example does not define all possible valid values
> for attributes or expected data types for metrics, etc."

> "Our goal is narrowly defined to solve the following problem only: to allow
> OpenTelemetry Semantic Conventions to evolve over time. For that reason this document
> is concerned with _changes_ to the schema as opposed to the _full state_ of the schema."

> "We intentionally limit the types of transformations of schemas to the bare minimum
> necessary to handle the most common changes."

Section **"How Schemas Work"**:

> "Telemetry schemas explicitly define transformations that are necessary to convert
> telemetry data between different versions of the schema."

The same wording originates in OTEP 0152 (`oteps/0152-telemetry-schemas.md`), so this is
the founding intent, not a later narrowing.

### The file format confirms it exhaustively

`specification/schemas/file_format_v1.1.0.md`. The complete set of expressible
operations:

| Section | Permitted changes |
|---|---|
| `all` | `rename_attributes` |
| `resources` | `rename_attributes` |
| `spans` | `rename_attributes` |
| `span_events` | `rename_events`, `rename_attributes` |
| `metrics` | `rename_metrics`, `rename_attributes`, `split` |
| `logs` | `rename_attributes` |

Every construct is a rename or a split. There is **no** construct for "this attribute
must be present", "this value must be of type X", "this value must be one of". The
format is structurally incapable of expressing a constraint.

The published file at `https://opentelemetry.io/schemas/1.37.0` bears this out. It is
`file_format: 1.1.0` plus a `versions:` block of rename maps, for example:

```yaml
versions:
  1.37.0:
    all:
      changes:
        - rename_attributes:
            attribute_map:
              android.state: android.app.state
              container.runtime: container.runtime.name
              gen_ai.system: gen_ai.provider.name
```

A pure changelog of renames. Nothing else.

### Corroboration from the Collector

The only first-party consumer of schema files, the Collector's `schemaprocessor`, is a
transformer: "The _Schema Processor_ is used to convert existing telemetry data or
signals to a version of the semantic convention defined as part of the configuration."
It validates nothing. It is still **alpha** for traces, metrics and logs.

### What this changes for the platform

It removes an entire imagined shortcut. There is no "point at the schema URL and get a
verdict" path. Any conformance check Amp-Up performs must be built against the semconv
*registry* (Q1), and Amp-Up must supply the checking machinery itself for landed data (Q3).

### The one genuinely useful role for schema URLs

`schema_url` is carried on every Resource and InstrumentationScope, and OTel
instrumentation libraries populate it. So while it cannot validate anything, it is an
**observable claim about which convention version the application is emitting**. That
is directly checkable with the vocabulary Amp-Up already has:

- "Telemetry carries a `schema_url` at all" is an attribute presence check. It fits
  `SignalAssertion.RequiredAttributes` unchanged.
- "The claimed version is at or above 1.30.0" is a low-cardinality value check, which is
  the cheapest possible extension to the seam (see Q6).

This is a real requirement worth writing, and it is cheap. It just is not what the
schema mechanism was built for.

## Q3. Can telemetry be validated against semantic conventions today?

**Verdict: yes, by exactly one tool, `weaver registry live-check`, and only against a
live OTLP stream or a sample file. Nothing in the ecosystem validates telemetry that
has already landed in a backend. That is the gap Amp-Up sits in.**

### What exists: `weaver registry live-check`

Inputs (`--input-source`, `--input-format`):

- **OTLP receiver**: a gRPC listener (default `:4317`) that consumes a live stream.
  Stops on CTRL+C, SIGHUP, an HTTP `/stop` endpoint, or `--inactivity-timeout`.
- **File**: JSON sample arrays, or text files of attribute names / `name=value` pairs.
- **stdin**.

Output: `PolicyFinding` records, rendered via Jinja templates (`--format` json, jsonl,
yaml, ansi, or a template), to stdout, a file, or HTTP. `--emit-otlp-logs` sends findings
as OTLP log records. `--fail-on {violation,improvement,information,none}` sets the exit
code, which makes it usable as a CI gate.

### What it actually checks

This is the vocabulary to steal. From `crates/weaver_live_check/docs/finding.md`:

**Violations** (hard conformance failures):

| Finding id | Meaning |
|---|---|
| `missing_attribute` | attribute not defined in the registry |
| `missing_metric` | metric not defined in the registry |
| `missing_event` | event not defined in the registry |
| `type_mismatch` | attribute value type differs from the registry's declared type |
| `unit_mismatch` | metric unit differs from the registry |
| `unexpected_instrument` | metric instrument type differs or is unsupported |
| `undefined_enum_variant` | enum value outside the allowed member set |
| `required_attribute_not_present` | a `required` attribute is absent |
| `conditionally_required_attribute_not_present` | a `conditionally_required` attribute is absent |
| `entity_required_attribute_not_present` | required entity attribute absent on a resource |
| `entity_conditionally_required_attribute_not_present` | as above, conditional |
| `entity_association_not_satisfied` | no entity in a `one_of` association group satisfied by the resource |
| `missing_namespace` | attribute name has no dot-separated namespace |
| `invalid_format` | attribute or metric name fails the naming format |
| `illegal_namespace` | name uses a namespace colliding with an existing attribute |

**Improvements** (quality, not failure):

`deprecated`, `not_stable`, `recommended_attribute_not_present`,
`opt_in_attribute_not_present`, `entity_recommended_attribute_not_present`,
`entity_opt_in_attribute_not_present`, `extends_namespace`.

**Information**: `template_attribute`.

That three-level severity split (`violation` / `improvement` / `information`) maps
cleanly onto a tiering model and is worth adopting verbatim rather than inventing.

### What does not exist

- No backend-side validator. Nothing reads Elasticsearch, Prometheus, ClickHouse or
  Loki and reports semconv conformance.
- No Collector processor that validates. `schemaprocessor` transforms; there is no
  first-party "validate against semconv and reject/flag" processor.
- No validation in the OTLP protocol or SDKs.

So the only supported placement is a **tap on the pipeline**, not a **read of the store**.
That distinction drives Q5 and Q6.

## Q4. Expressing a custom, organisation-specific schema

**Verdict: supported and standardised, not bespoke. A custom Weaver registry is the
correct home for `enterprise.criticality_tier` and FGS labels. Amp-Up should consume a
registry rather than grow its own attribute-definition syntax.**

### Mechanism: a custom registry with a manifest

From `weaver/docs/define-your-own-telemetry-schema.md`, a custom registry is a directory
with `manifest.yaml`:

```yaml
name: <custom registry name>
description: <an optional description of the custom registry>
schema_url: <base URL where the registry's schema files are hosted>/<version of this custom registry>
dependencies:
  - schema_url: <base URL of the dependency>/<version of the dependency>
    registry_path: <the location of the dependency>
```

`schema_url` identifies the registry and its version for provenance and conflict
resolution. It does not have to be fetchable: files are located via `registry_path`.
This gives Customer C a versioned, addressable schema identity without hosting anything.

### Importing and extending OTel

```yaml
imports:
  metrics:
    - db.*                # import all metrics in the `db` namespace
  entities:
    - gcp.*               # import all entities in the `gcp` namespace
  events:
    - session.start       # import the `session.start` event
```

Imported conventions can have their requirement level **tightened locally**, which is
precisely the "Customer C is stricter than baseline OTel" case:

```yaml
groups:
  - id: span.example_message
    type: span
    stability: development
    brief: This span represents a simple message.
    span_kind: client
    attributes:
      - ref: host.name                 # imported from OTEL semantic conventions
        requirement_level: required    # requirement level redefined locally
```

So `enterprise.criticality_tier` would be a new attribute in a customer namespace, typed
as an enum with `members` for the tier values, `requirement_level: required`, plus a
`stability`. FGS labels likewise. All standard model constructs, no invention needed.

### For rules the YAML model cannot express: Rego

Two policy surfaces:

1. `weaver registry check -p/--policy <file|dir>`: policies over the **registry itself**
   ("all attributes in our namespace must have examples", "no `development` stability in
   a production registry"). All `.rego` files in a directory are loaded.
   `--display-policy-coverage` reports coverage.
2. `weaver registry live-check --advice-policies <dir>`: policies over **observed
   samples**, in package `live_check_advice`. Inputs available to a policy:
   `input.sample` (e.g. `input.sample.attribute`), `input.resource`,
   `input.instrumentation_scope`, `input.registry_attribute`, `input.registry_group`, and
   `data`. `--advice-preprocessor` takes a JQ script to reshape registry data first, and
   `--advice-data` loads extra JSON/YAML into the OPA data namespace.

Example from the Weaver docs:

```rego
package live_check_advice

import rego.v1

# checks attribute name contains the word "test"
deny contains make_finding(id, level, context, message) if {
	input.sample.attribute
	contains(input.sample.attribute.name, "test")
	id := "contains_test"
	level := "violation"
	context := {
		"attribute_key": input.sample.attribute.name
	}
	message := sprintf("Attribute name must not contain 'test', but was '%s'", [input.sample.attribute.name])
}
```

The docs note policies "are independent of the semantic convention registry, so you can
define application or library specific checks as needed".

### Bootstrapping

`weaver registry infer` derives a candidate registry from observed OTLP: it accumulates
samples (OTLP, file or stdin) and emits a registry file, grouping resources into one flat
attribute group, spans by span name, metrics by metric name with instrument details, and
logs by event name, keeping up to five example values per attribute. For a customer with
an existing estate and no written schema, this turns "write a schema from scratch" into
"review and prune a generated one". That is a materially different onboarding story and
worth noting for the product shape.

### The catch

All of this is **Weaver tooling**, not the OTel *specification*. Custom registries are a
convention supported by one tool, not a ratified standard with multiple implementations.
Adopting it is still the right call (it is the only game in town and it is the official
OTel tool), but it should be recorded as a dependency on a single, still-moving project.

## Q5. Declared config versus observed telemetry

**Verdict: declared is dramatically cheaper and structurally weaker. Config cannot
express semconv conformance at all; at best it proves an attribute-injector is
configured. Observed is the only place conformance is genuinely knowable, and it is the
expensive one. The existing cross is the right pattern, but the two halves are far more
asymmetric here than they are for signal presence.**

### What a config check can and cannot say

`ConfigAssertion` reads receivers, processors and exporters. A collector config states
which components run. It says nothing about which attributes an application's SDK emits,
what types those values have, or whether metric units match. The application, not the
collector, produces most of what a schema constrains.

The narrow set of schema-adjacent things config *can* prove:

- A `resource` or `attributes` processor is configured to inject a required attribute
  (this is the realistic path for `enterprise.criticality_tier` and FGS labels, which are
  environment facts rather than application facts).
- A `transform`/OTTL processor is configured to normalise or rename.
- A `schemaprocessor` is pinned to a target semconv version.

That is: config proves **intent to inject**, never **conformance**. For customer-specific
environment labels it is actually a strong check, because injection is where those
attributes come from. For semconv conformance of application telemetry it is nearly
worthless.

### Cost

- **Declared**: O(applications) metadata reads against the fleet API. No data scanned.
  Cost is flat in telemetry volume. Effectively free at estate scale.
- **Observed**: O(applications x signals x required-attributes) aggregations over a time
  window. In the current Elastic provider, each application is one `_msearch` with three
  index queries, each carrying one `filter`/`exists` sub-aggregation per required
  attribute (`internal/provider/telemetry/elastic.go:175-206`). Cost grows with the
  attribute list, and a semconv-derived required-attribute list is much longer than a
  hand-written one. Scanning cost also grows with data volume, unlike the config check.

Extending observed checks to semconv granularity makes this worse in a specific way: a
correct check is scoped **per span name / metric name / event name**, not per signal,
because the required attributes for `http.server.request.duration` differ from those for
`db.client.operation.duration`. That adds a grouping dimension and multiplies the
aggregation count. This is the main scale risk in the whole design.

Mitigations that stay inside the current architecture: batching (already done via
`_msearch`), longer evaluation windows evaluated less frequently, capping the
required-attribute list per requirement, and sampling rather than exhaustive scans.

### The honest recommendation

Keep the cross, but do not pretend the halves are equal:

- **Declared**: cheap, and the right home for "is the injector configured", with a
  precise remediation attached.
- **Observed**: authoritative, and the only source of truth for whether the attribute
  actually arrived.
- **A third placement, absent from the current model**: a collection-time tap running
  `weaver registry live-check`. This is neither declared nor observed as Amp-Up currently
  defines them. It reads a stream. It is where the checks that Q6 rules out at query time
  become possible, and it is worth treating as a first-class option rather than forcing
  everything through `TelemetryProvider`.

## Q6. What is expressible without a backend query language

**Verdict: roughly half the semconv check surface survives the constraint, and it is a
predictable half. Anything that depends on the NAMES in use is expressible and cheap.
Anything that depends on VALUES is expressible only for low-cardinality attributes.
Anything that depends on TYPES is not expressible at all, because most backends destroy
the type information at ingest. Structural and cross-record checks are out.**

Assessed against `TelemetryProvider.Observe(ctx, app, window) (Observed, error)`
(`internal/provider/provider.go:35`), which today yields `{Present, Volume,
AttributePresence map[string]float64}` per signal, and must be implementable against
Prometheus, ClickHouse and Loki as readily as Elasticsearch.

### Green: expressible with the seam as it stands

| Check | Why it works |
|---|---|
| `required_attribute_not_present` | This is exactly `RequiredAttributes` + `AttributeCoverage`. Elastic: `exists` filter agg. ClickHouse: `countIf(has(mapKeys(attributes), k))`. Prometheus: `count(m{k!=""})`. Loki: label filter. All four have the primitive. |
| `recommended_attribute_not_present` | Same primitive, mapped to a coverage threshold below 1.0 rather than a hard fail. `AttributeCoverage` already models this; `requirement_level` gives it principled defaults. |
| `schema_url` presence | A single attribute presence check on the resource. Free. |

Note the fidelity limit already present: `AttributePresence` is per signal, but semconv
required-attribute sets are per span name / metric name / event name. Getting this
correct needs a **grouping key** added to the seam (presence per signal per group). That
is still backend-neutral: terms aggregation in Elastic, `GROUP BY` in ClickHouse, series
name in Prometheus, label grouping in Loki. It is a widening of the interface, not a
breach of it.

### Green, but needs one new provider primitive: `AttributeNames`

A primitive returning "the set of attribute names in use for this application, this
signal, this window" unlocks a whole family of checks that then run entirely in the
platform as string logic against the registry, with zero further backend involvement:

- `missing_attribute` (in use but not defined in the registry)
- `missing_metric`, `missing_event`
- `invalid_format`, `missing_namespace`, `illegal_namespace`, `extends_namespace`
- `deprecated`, `not_stable`

This is the highest-leverage single addition available: one primitive, nine finding types.

Honesty about the primitive: all four backends can produce it, but by structurally
different routes and at uneven fidelity. Prometheus and Loki expose `/api/v1/labels` and
`label_values`, which is a clean fit. ClickHouse does it with `arrayJoin(mapKeys(...))`.
Elasticsearch does it best via the field-caps/mapping API, which is **index-scoped, not
application-scoped**, so an Elastic implementation either loses the per-application
scoping or falls back to a costly terms aggregation. Mark this amber on fidelity even
though it is green on feasibility.

### Amber: values, only for low cardinality

`undefined_enum_variant` needs the distinct values of an attribute compared against the
registry's `members`. A `DistinctValues(attr, limit)` primitive is available everywhere:
terms agg (Elastic), `topK`/`GROUP BY` (ClickHouse), `label_values` (Prometheus and Loki).

It works precisely because enums are low-cardinality by definition, which is also the
constraint that keeps it safe. The primitive must carry a hard cap and must report
truncation, otherwise a mis-declared enum over a high-cardinality field turns a
compliance check into a backend incident. Restrict it to attributes the registry declares
as enums. Do not offer it as a general facility.

This also covers the useful `schema_url` version check from Q2: `schema_url` is a
low-cardinality resource attribute, so "which convention version is this app claiming"
is answerable through the same primitive.

### Red: not expressible without backend-specific querying, or not at all

| Check | Why it fails |
|---|---|
| `type_mismatch` | The type information is usually **gone**. Prometheus and Loki labels are strings, universally. OTel-in-ClickHouse commonly lands attributes as `Map(String, String)`, erasing the distinction. Elasticsearch retains a mapping type, but reading it is a mapping-API call with different semantics from a query, and dynamic mapping means the mapping reflects the first document seen rather than the declared type. There is no honest backend-neutral answer here. |
| `unit_mismatch`, `unexpected_instrument` | Metrics-only and highly backend-specific. Prometheus exposes this well via `/api/v1/metadata`; Elasticsearch and Loki have no equivalent. A provider primitive would be unimplementable for most backends, which is worse than not offering it. |
| `entity_association_not_satisfied` | Requires evaluating a `one_of` group over a single resource's full attribute set, per record. Record-level structural inspection. |
| `conditionally_required_attribute_not_present` | The condition is prose in the registry (`brief`/`note`), not a machine-evaluable predicate. Even with unlimited query power this cannot be automated from the registry alone. |
| Cross-signal and structural shape | Span parent/child relationships, event body structure, exemplar linkage. All need per-record traversal. |

### The conclusion that matters for the design

The constraint does not merely trim the feature list. It **partitions the check surface
by where the check has to run**:

- **Query-time, through `TelemetryProvider`**: presence, coverage, name-set conformance,
  low-cardinality value conformance. Backend-neutral, works on landed data, catches the
  long tail of an estate. This is where Amp-Up already lives and the extension is
  natural: two new primitives (`AttributeNames`, `DistinctValues`) plus a grouping key.
- **Collection-time, at an OTLP tap with `weaver registry live-check`**: types, units,
  instruments, structural checks, and everything else. Needs **no query language at all**,
  because it reads a stream rather than a store. It does not breach the
  `TelemetryProvider` abstraction; it sidesteps it.

So type conformance is not lost, it is **relocated**. The honest position is that Amp-Up
cannot check types from a backend and should stop trying, and should instead treat
"a live-check tap is deployed and reporting clean" as a requirement in its own right,
evaluated like any other. Weaver's `--emit-otlp-logs` makes that mechanical: findings
arrive as OTLP log records, which land in the backend, which makes them observable
through the existing `TelemetryProvider` as ordinary telemetry. The expensive check runs
where it is cheap, and only its verdict is read back.

---

## Summary: adopt or fill

**Adopt, do not invent:**

- The semconv YAML model as the schema declaration language, including
  `requirement_level`, `stability`, typed attributes and enum `members`.
- Weaver custom registries (`manifest.yaml`, `imports`, `ref` with local
  `requirement_level` override) for customer-specific schemas.
- Weaver's finding taxonomy and its `violation` / `improvement` / `information` severity
  split, as Amp-Up's conformance vocabulary.
- `weaver registry infer` as the onboarding path from an existing estate to a written
  schema.

**Do not build on:**

- OTel telemetry schema files and schema URLs, as a conformance mechanism. The spec
  states they are not one. Their only useful role is as an observable version claim.

**The gap to fill:**

- Evaluating semantic convention conformance against **telemetry that has already
  landed**, per application, per tier, across a whole estate. No tool in the ecosystem
  does this. Weaver checks a stream; Amp-Up governs an estate. That is the product.

**What the query-language constraint rules out:**

Type conformance, unit and instrument conformance, conditionally-required evaluation,
and all structural or cross-record checks. These must move to a collection-time tap, or
be dropped. Everything driven by attribute *names*, and by *values* of low-cardinality
attributes, survives, and needs two new provider primitives plus a grouping key.
