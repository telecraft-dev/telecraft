Resolves `issues/23-supervisor-cost-enumeration.md`.

Researched 2026-08-04. The ticket asks four questions and a closing statement on
whether the serve half of "git stores, OpAMP serves" survives the price. Each
section opens with a verdict line, then the evidence, and each ends with what the
evidence does not cover.

## Q1. The deployment delta of mandating the Supervisor

**Verdict: the delta is real but it is smallest on exactly the substrate that
justifies serving, and largest on the substrate that does not. On VMs and bare
metal the Supervisor is a first-class upstream artefact: signed deb and rpm
packages with a systemd unit, a Windows MSI that registers a service, and
prebuilt binaries for six OS/arch pairs. On Kubernetes there is nothing:
zero references to the Supervisor in the OpenTelemetry Operator, zero in the
OpenTelemetry Helm charts, and the only upstream pattern is the container image's
own Dockerfile, which runs the Supervisor as the entry point with the collector as
a child process in the same container. So the ticket's sharp point does not land
as feared. The Supervisor is hardest precisely where GitOps already works, and
easiest where GitOps cannot reach.**

The one cost that is universal and is not about packaging: the Supervisor
replaces the collector's own service unit. It owns the collector process. That is
a migration, not an addition, and it is the part an operator will actually feel.

### Universal costs, on every substrate

Four things are true regardless of how the Supervisor is installed, and they are
read from `supervisor/supervisor.go` `Start()` at lines 342-427:

1. **The collector process is started three times at Supervisor boot.**
   `getFeatureGates()` runs the collector binary with the `featuregate` argument
   and reads its output. `getBootstrapInfo()` then starts the collector against a
   generated bootstrap config, waits for its `opamp` extension to connect back to
   the Supervisor's own local OpAMP server, harvests the `AgentDescription` and
   available components, then stops it. Only after that does the real collector
   start. On a slow host this is visible startup latency, and `bootstrap_timeout`
   defaults to **3 seconds** (`supervisor/config/config.go:465`), after which
   `Start()` returns an error and the Supervisor does not come up at all.
2. **The Supervisor runs a local OpAMP server on a loopback port**, by default a
   random free port (`supervisor.go:2650-2680`, `getSupervisorOpAMPServerPort` falling through to `findRandomPort`), fixable via
   `agent::opamp_server_port`. The collector connects out to it via an injected
   `extensions.opamp` block at `ws://127.0.0.1:<port>/v1/opamp`
   (`supervisor/templates/opampextension.yaml`). One extra loopback listener per
   supervised collector.
3. **`accepts_remote_config` is off by default.** `DefaultSupervisor()` sets
   `AcceptsRemoteConfig: false`, `ReportsRemoteConfig: false` and
   `AcceptsRestartCommand: false` (`config.go:446`, `447`, `454`). A Supervisor installed
   from the package with the example config edited only for the endpoint will
   report but will not accept config. Amp-Up's install guidance has to turn these
   on explicitly.
4. **The collector config the operator writes stops being the collector's
   config.** The Supervisor merges `agent::config_files`, the remote config, its
   own OpAMP extension block and own-telemetry config into
   `<storage::directory>/effective.yaml` and passes that as `--config`
   (`supervisor.go:405-407`, `specification/README.md:261`). Anyone debugging by
   looking at the file they edited is looking at an input, not the config.

### VMs and bare metal: distro packages exist, and are signed

`opentelemetry-collector-releases` ships the Supervisor as its own release train
with its own goreleaser configuration at `cmd/opampsupervisor/.goreleaser.yaml`.
What it produces:

| Artefact | Detail |
|---|---|
| Linux binaries | `amd64`, `arm64`, `ppc64le` (`builds: id: opampsupervisor-linux`) |
| macOS binaries | `amd64`, `arm64` |
| Windows binary | `amd64` |
| deb and rpm | `nfpms: formats: [deb, rpm]`, package name `opampsupervisor`, licence Apache 2.0, maintainer `cncf-opentelemetry-maintainers@lists.cncf.io` |
| Windows MSI | `msi: wxs: cmd/opampsupervisor/windows-installer.wxs` |
| Container images | `otel/opentelemetry-collector-opampsupervisor` and `ghcr.io/open-telemetry/opentelemetry-collector-releases/opentelemetry-collector-opampsupervisor`, multi-arch manifest over amd64, arm64, ppc64le |
| Supply chain | `signs: cmd: cosign` over all artefacts, `sboms` for archives and packages |

The deb and rpm are not a binary drop. `nfpms.contents` installs:

- `/lib/systemd/system/opampsupervisor.service`
- `/etc/opampsupervisor/opampsupervisor.conf` (systemd `EnvironmentFile`)
- `/etc/opampsupervisor/config.example.yaml`

with `preinstall.sh` creating a system user:

```sh
getent passwd opampsupervisor >/dev/null || useradd --system --user-group --no-create-home --shell /sbin/nologin opampsupervisor
```

and `postinstall.sh` running `systemctl daemon-reload` and
`systemctl enable opampsupervisor.service`.

The unit itself (`cmd/opampsupervisor/opampsupervisor.service`) is a conventional
systemd service:

```
[Unit]
Description=OpenTelemetry Collector OpAMP Supervisor
After=network.target
AssertPathExists=/etc/opampsupervisor/config.yaml

[Service]
EnvironmentFile=/etc/opampsupervisor/opampsupervisor.conf
ExecStart=/usr/bin/opampsupervisor $OPAMP_OPTIONS
Restart=on-failure
Type=simple
User=opampsupervisor
Group=opampsupervisor
ConfigurationDirectory=opampsupervisor
StateDirectory=opampsupervisor
LogsDirectory=opampsupervisor
```

Two details in that unit matter to Amp-Up. `AssertPathExists=/etc/opampsupervisor/config.yaml`
means the unit will not start until the operator writes a supervisor config, and
the package deliberately ships only `config.example.yaml`, so a fresh install is
enabled but inert until configured. And `StateDirectory=opampsupervisor` means
systemd creates and owns `/var/lib/opampsupervisor`, which is the identity
directory question 3 turns on. On the packaged path, identity persistence is
handled correctly by default.

**So the honest per-substrate answer for a VM is: two packages instead of one, and
one config file instead of one.** The operator installs `otelcol-contrib` (or any
collector) as they do today, plus `opampsupervisor`, and writes
`/etc/opampsupervisor/config.yaml` pointing `agent::executable` at the collector
binary. The packaged example
(`cmd/opampsupervisor/config.example.yaml`) shows the intended shape, with
`agent::executable: /etc/opampsupervisor/otelcol-contrib` and
`storage::directory: /var/lib/opampsupervisor/`.

**The genuine cost is the process-ownership swap, and upstream does not smooth
it.** The collector's own package ships
`distributions/otelcol-contrib/otelcol-contrib.service`, a systemd unit that runs
the collector directly. Under the Supervisor the collector must not be started by
that unit, because the Supervisor starts it as a child with `--config` pointed at
its own generated `effective.yaml` (`supervisor/supervisor.go:405-407`). Nothing in
the Supervisor package disables `otelcol-contrib.service`, and nothing warns about
it. Running both yields two collectors racing for the same ports. That is the
concrete migration step an operator has to perform and nobody has automated.

**Bare metal and anything without a package manager** is the binary-plus-unit
path: download the binary from the release asset (the README documents the exact
`curl` invocation and asset naming
`opampsupervisor_<VERSION>_<OS>_<ARCH>`), write the unit yourself, or run it
under whatever process supervisor already exists. Nothing about the Supervisor
requires a package manager. It is a static CGO-disabled Go binary
(`.goreleaser.yaml`, `env: CGO_ENABLED=0`).

### Windows: supported, and better supported than expected

Windows is a first-class target, not an afterthought.

- `cmd/opampsupervisor/main_windows.go` implements a real Windows service:
  `svc.Run("", supervisor.NewSvcHandler())`, falling back to interactive mode on
  `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT`. It also calls `AllocConsole` so it
  can send `CTRL_BREAK_EVENT` to the collector child process, with the comment
  "windows services don't get created with a console / need to allocate a console
  in order to send CTRL_BREAK_EVENT to agent sub process".
- `supervisor/supervisor_windows.go` (172 lines) and
  `supervisor/supervisor_windows_service_test.go` exist as dedicated code and
  tests.
- The MSI (`cmd/opampsupervisor/windows-installer.wxs`) contains a
  `<ServiceInstall>` and a `<ServiceControl>` element, installs into
  `%ProgramFiles%\OpenTelemetry OpAMP Supervisor`, creates
  `%ProgramData%\opampsupervisor\logs`, and registers an event log
  `EventMessageFile`.
- The default storage directory on Windows is `%ProgramData%\Otelcol\Supervisor`,
  with a fallback to `C:\ProgramData` when `ProgramData` is unset
  (`supervisor/config/config.go:422-433`).

One caveat, read from the installer: `<ServiceInstall Start="demand">`. The MSI
registers the service for manual start, so an unattended install leaves it not
running and not set to start at boot. That is a real deployment step an operator
must add.

### Kubernetes: nothing upstream, and the pattern is not a sidecar

This is the negative that matters, and it is a hard one.

- **`grep -ril supervisor` across the whole OpenTelemetry Operator at
  `936faf56` returns zero files.** Not a CRD field, not a manifest, not a
  doc, not a comment. The Operator has no notion of the Supervisor.
- **The same grep across `opentelemetry-helm-charts` at `8bbe49ae` returns zero
  files.** Neither `opentelemetry-collector` nor `opentelemetry-kube-stack`
  supports it.
- Two Operator issues ask for it and both are still open:
  [#1319 "Supervisor creation via the CRD"](https://github.com/open-telemetry/opentelemetry-operator/issues/1319),
  opened 2022-12-12, and
  [#1933 "OpAMP Supervisor Conveniences"](https://github.com/open-telemetry/opentelemetry-operator/issues/1933),
  opened 2023-07-17. Requested for over three and a half years, unbuilt.
- The Supervisor's own design document,
  `cmd/opampsupervisor/specification/README.md` (980 lines), contains **zero
  occurrences of "Kubernetes", "sidecar", "container" or "DaemonSet"**. The design
  is a host-process design and says so by omission.

**What upstream actually does, where it does anything, is entry-point-with-child,
not sidecar.** `cmd/opampsupervisor/Dockerfile` builds a single image containing
both binaries:

```dockerfile
FROM otelcontribcol AS col
...
COPY --chmod=755 opampsupervisor /
COPY --from=col --chmod=755 /otelcontribcol /otelcontribcol
ENTRYPOINT ["/opampsupervisor"]
CMD ["--config", "/etc/otel/supervisor.yaml"]
```

That is one container, one process tree, the Supervisor as PID 1 and the
collector as its child.

**A sidecar container is not a supported shape, and the reason is structural
rather than a missing feature.** The Supervisor starts the collector by forking
it: `exec.CommandContext(ctx, c.cfg.Executable, args...)` followed by
`c.cmd.Start()` (`supervisor/commander/commander.go:84`, `142`). It also signals
it directly, `Process.Signal(syscall.SIGHUP)` for reload (line 101) and
`Process.Signal(os.Kill)` for stop (lines 398, 469). And the collector is made to
notice if the Supervisor dies: the injected extension carries
`ppid: {{.PID}}` with a `ppid_poll_interval`
(`supervisor/templates/opampextension.yaml`), so the collector exits when its
parent goes away.

Parent, child, signals and a shared filesystem path to the executable. In
Kubernetes terms the workable shapes are a combined image, which is what upstream
ships and what Interchange runs, or two containers sharing
`shareProcessNamespace` plus a volume carrying the collector binary. Upstream
neither documents nor tests the second, and `cmd/opampsupervisor/e2e_test.go` is
4,115 lines with **zero occurrences of "kubernetes", "docker" or "container"**.

Interchange already runs the first shape, which is a live existence proof rather
than a reading. `testbed/edge/Dockerfile` composes
`otel/opentelemetry-collector-opampsupervisor:0.156.0` and
`otel/opentelemetry-collector-contrib:0.156.0` into one Alpine image with the
Supervisor as `ENTRYPOINT`. It works, and it is about ten lines.

**The Kubernetes cost, stated plainly**: you cannot use the OpenTelemetry Operator
or the OpenTelemetry Helm chart to deploy a supervised collector. You build and
maintain your own image and your own DaemonSet or Deployment. For an adopter whose
whole Kubernetes estate is Operator-managed or chart-managed, that is a
replacement of their deployment mechanism, not an addition to it.

### What OpenTelemetry itself tells adopters to do

This is the strongest available signal on intent, and it points the same way as
the packaging.

OpenTelemetry's own blueprint for non-Kubernetes environments,
[Infrastructure and Processes in Non-K8s Environments](https://opentelemetry.io/docs/guidance/blueprints/instrumenting-applications-and-processes-on-nonk8s-environments/),
says: "Use OpAMP, where supported and operationally suitable, to centrally manage
OpenTelemetry agents running as system services or service containers." It then
names the two integration shapes and ranks them. The Supervisor is described as
"a separate host-local process that manages the Collector lifecycle and applies
remote configuration in addition to reporting status, health, and capabilities.
**This is the most capable integration.**" The in-process extension is "a
lightweight integration that reports status, health, and capabilities to the
management service, but does not handle remote configuration delivery or
lifecycle management", which is ticket 01's finding restated by the project
itself.

The same page carries the caveat, verbatim: "Because the OpAMP specification is
currently in Beta, organizations should evaluate the maturity and supportability
of the implementations available in their environment before standardizing on a
specific solution."

The [Collector Management](https://opentelemetry.io/docs/collector/management/)
page documents the download for Linux amd64, arm64 and ppc64le, macOS amd64 and
arm64, and Windows amd64. It makes **no statement about stability, maturity or
production readiness**, and mentions neither Kubernetes nor systemd.

So: OpenTelemetry recommends the Supervisor for the VM and bare-metal population,
recommends it as the more capable of the two options, and says nothing at all
about it for Kubernetes. That is exactly congruent with what the code and the
packaging show.

### Where the evidence is weak

- No measured adoption exists for any of these paths. The packaging is evidence
  that upstream expects the VM path to be used, not evidence that it is used.
- The claim that a sidecar is impossible is inference from
  `commander.Start` executing the binary directly. It is a strong inference but
  no upstream document states it, and no upstream issue was found rejecting the
  sidecar shape.
- Debian and RPM repositories: the packages are published as GitHub release
  assets. No evidence was found of an apt or yum repository, a Homebrew formula, a
  Chocolatey package or a winget manifest. That is a real friction point for a
  fleet, and it may simply not have been searched exhaustively enough.

## Q2. The maturity risk of `opampsupervisor`

**Verdict: premise 8 is not satisfied, and the gap is worse than the alpha label
alone suggests. The Supervisor is alpha, has been alpha since it was created, and
the tracking issue that defined alpha was closed on 2025-04-04 with the words
"not necessarily something that we intend for production usage" and nothing has
replaced that statement. There is no beta tracking issue, no milestone on any
open issue, and no graduation criteria in the design document. Against that:
the release machinery is genuinely mature, at least two vendors ship or require
it in a supported path, and the open defect profile is small and contains none of
the classes that would be fatal. So the risk is not "this will corrupt configs".
The risk is "there is no declared destination, the config surface is still
breaking, and the bench is five people."**

### Declared stability, and it has never moved

`cmd/opampsupervisor/metadata.yaml`:

```yaml
type: opampsupervisor
status:
  disable_codecov_badge: true
  class: cmd
  stability:
    alpha: [metrics]
  codeowners:
    active: [evan-bradley, atoulme, tigrannajaryan, douglascamata, dpaasman00]
```

The `[metrics]` signal list is an artefact of the mdatagen schema for a `class:
cmd` artefact, not a claim scoped to metrics. Sibling binaries carry the same
shape. Read it as: the whole binary is alpha.

The README adds a design warning, verbatim: "The design is still undergoing
changes, and as such this implementation may change as well." And the design spec
itself states the ambition rather than the achievement
(`specification/README.md:64`): "*Important: the Supervisor needs to be highly
stable, so we need to keep its complexity and functionality to minimum. The
features listed in this section need a critical review and may be removed.*"

There is also a live alpha feature gate, `opampsupervisor.Extensions`, introduced
in v0.153.0.

**Note the inconsistency worth knowing about**: OpenTelemetry's own
[Collector Management](https://opentelemetry.io/docs/collector/management/) page
documents the install with no alpha, preview or experimental caveat anywhere. The
label and the documentation disagree, and the documentation is the thing an
adopter reads.

### Release cadence and artefact: this part is mature

Ticket 09 corrected an "abandoned" reading of the spec. The same correction is
needed here, and more strongly: the Supervisor is a properly released artefact
with a biweekly train.

- Own Go module, `github.com/open-telemetry/opentelemetry-collector-contrib/cmd/opampsupervisor`,
  `go 1.25.0`, pinning `opamp-go v0.23.0`.
- Released from `opentelemetry-collector-releases`, not from contrib. Contrib's
  own releases carry zero assets. **53 stable `cmd/opampsupervisor/vX.Y.Z` tags
  exist**, from `v0.122.0` to `v0.158.0`, plus a nightly channel.
- Recent cadence: v0.158.0 on 2026-08-04, v0.157.0 on 2026-07-22, v0.156.0 on
  2026-07-07, v0.155.0 on 2026-06-24, v0.154.0 on 2026-06-09, v0.153.0 on
  2026-05-26. Roughly biweekly, tracking contrib.
- v0.158.0 carries 76 assets over six platform binaries, three deb, three rpm and
  one MSI, with sigstore attestations and SBOMs. Details in Q1.
- One gap: `cmd/opampsupervisor/v0.143.0` returns HTTP 404, between v0.142.0
  (2025-12-16) and v0.144.0 (2026-01-20). Contrib did cut a v0.143.0. **The reason
  was not found.**

**The counterweight, and it is the real maturity signal for a product that would
mandate it: the configuration surface is still breaking.** Eight breaking-change
entries mention the Supervisor across the contrib CHANGELOG, and **one landed in
v0.158.0, released the day this was written**, removing the
`reports_package_statuses` capability option. Earlier ones include v0.130.0
(remote config now merges *over* user config, a semantic change), v0.126.0
(removed `agent.health_check_port`) and v0.115.0 (strict unmarshalling). An
adopter mandating this component inherits a config surface that changes roughly
every few releases.

### Open defect profile

**19 open, 149 closed** against label `cmd/opampsupervisor`, as of 2026-08-04.
The label taxonomy does not support a clean bug/enhancement split: 3 carry `bug`,
10 carry `enhancement` and 6 carry neither, but at least two `enhancement`-labelled
issues read as defects. Call it 5 or 6 genuine defects out of 19.

Against the classes that would bite a product mandating it:

Historically real: config validation before apply was added in #46144 precisely because bad config used to crash the collector. |
| Restart / crash loops | **None open.** | Four closed: #34377, #32959, #27891, #21077, all 2023-2024. This class was real and has been dealt with. |

| Memory growth / leaks | **Nothing, open or closed.** | Genuine absence of evidence in both directions. |
| Windows | **The weakest platform.** | #49999 (bootstrap binds the collector's default telemetry port 8888, failing Windows e2e on `main`), opened 2026-08-02, two days old. #48386 (Windows service logging). Closed: #40368, "Opampsupervisor on Windows Does Not Start, Crashes Without Meaningful Errors", 2025-05-29. All seven `t.Skip` calls in the supervisor test suite are Windows or platform related. |

**One unreported risk, found by reading rather than in the tracker, and flagged as
such.** `supervisor/persistence.go` `writeState()` writes the identity file
non-atomically:

```go
return os.WriteFile(p.configPath, by, 0o600)
```

No temp-file-and-rename. A crash or power loss mid-write leaves a truncated
`persistent_state.yaml`. And `loadOrCreatePersistentState` only falls back to
creating fresh state on `os.ErrNotExist`; a YAML unmarshal failure returns an
error, so a corrupted state file makes the Supervisor **fail to start** rather
than regenerate. For a product that would mandate this component on every served
host, that is a failure mode worth knowing about and probably worth upstreaming a
fix for under premise 13.

### Does anyone run it in production, and does any vendor ship it supported?

**Yes, two do, and this is the finding that most changes the calculus. But the
dominant vendor pattern by a wide margin is an embedded OpAMP client extension
inside the collector, not a supervising parent process. Six vendors independently
built or bought the alternative, including the one with the most incentive to
standardise on the Supervisor.**

**Vendors that ship or require the upstream Supervisor:**

- **Coralogix ships its own build.** It maintains a fork,
  `github.com/coralogix/opentelemetry-collector-releases` (confirmed `fork=true`,
  parent `open-telemetry/opentelemetry-collector-releases`), cutting its own
  non-prerelease `cmd/opampsupervisor/*` tags: `0.156.0` on 2026-07-29, plus
  `0.155.1`, `0.155.0`, `0.154.0`, `0.153.0`, `0.152.1`, `0.151.x`, `0.147.0`,
  `0.146.0`. Its first-party Linux install docs invoke the installer with
  `-- --supervisor` and tell the user to check `systemctl status opampsupervisor`.
  The installer pulls upstream binaries below 0.146.0 and Coralogix's own build
  from 0.146.0 onward. It also publishes a first-party Terraform module,
  `coralogix/telemetry-shippers/otel-ecs-supervisor/`, deploying the Supervisor on
  ECS, active since 2025-09-25 and updated 2026-07-29.
- **GrafanaFleetManagement requires it, and the path is GA.** Its
  onboarding page for a standalone OpenTelemetry Collector lists as a
  prerequisite: "The OpAMP Supervisor installed on the same host", linking
  directly to the upstream contrib directory, and gives
  `opampsupervisor --config=supervisor.yaml`. **The page carries no alpha, preview
  or experimental disclaimer**, and GrafanaFleetManagement's remote management of
  OpenTelemetry Collectors went GA on 2026-07-08. GrafanaFleetManagement does not
  build the binary; it points at upstream. Note the split: **GrafanaAlloy does not
  speak OpAMP at all**, using Grafana's own `remotecfg`, so the Supervisor is only
  on the bring-your-own-collector path.
- **HyperDX** ships `docker/otel-collector/supervisor_docker.yaml.tmpl`, a live
  Supervisor config templated at container start.

**Vendors that built or bought an alternative instead:**

- **Bindplane (observIQ) built its own, and this is the most informative
  refusal.** They are the most OpAMP-native vendor in the market and a maintainer
  of `opamp-go`. `bindplane-otel-collector` uses an **embedded** OpAMP client
  configured via `manager.yaml`, with its own ULID `agent_id` rather than the
  Supervisor's UUIDv7, plus first-party `internal/extension/opampconnectionextension`
  and `extension/opampgateway`. GA agent v1.105.1 on 2026-07-29. They do maintain
  `observIQ/bindplane-supervisor`, but it is pure repackaging of the upstream
  binary with **exactly one release ever**, `v0.145.0`, marked prerelease,
  published 2026-02-17, no commits in about five and a half months. Their own
  how-to page steers production users away from the Supervisor toward their agent.
- **`splunk-otel-collector` does not ship it.** No release asset contains
  "supervisor" from v0.154.1 through v0.157.0 (2026-07-24). The repo does contain
  `internal/opampsupervisor/launcher/` and `cmd/otelcollauncher/`, gated by
  `WITH_OPAMP_SUPERVISOR?=false` in the Makefile and `SPLUNK_OPAMP_SUPERVISOR_ENABLED`
  at runtime, but **no CI or packaging job sets that flag to true**. Work started
  2026-06-02 and is still churning. Their shipped story is the embedded
  `opamp/splunk_o11y` extension, feature gate `splunk.opamp.enabled`, promoted to
  **beta** and on by default. Their fleet-management documentation documents the
  extension and never mentions the Supervisor.
- **ElasticAgent does not use OpAMP for collector management at all.** Its full
  `NOTICE.txt`, a complete transitive manifest at 6.4 MB, has **zero** occurrences
  of `opampsupervisor`. ElasticAgent runs the collector in-process via a
  gob-encoded stdin confmap provider, managed over the ElasticFleet protocol. Its
  OpAMP investment is server-side: `apmconfigextension` hosts an OpAMP server for

## Q3. What the Supervisor persists, where, and what it does when the server is unreachable

**Verdict: premise 9 holds for the served population, and it holds by
construction rather than by luck. The Supervisor caches the last received remote
config on disk as a protobuf blob, and on restart with no server reachable it
composes the collector config from that cache and starts the collector. There is
no TTL, no retry ceiling, and no code path anywhere that stops the collector
because the OpAMP connection dropped. Amp-Up being down loses delivery and loses
nothing else. Two qualifications with teeth: the first-ever start with no server
and no cache yields a running collector with a noop pipeline, not a useful one,
unless `startup_fallback_configs` is set; and identity is a single UUID in a
single file, so the storage directory is load-bearing and getting it wrong is
exactly ticket 06's duplicate-agent defect.**

### What it writes, where, and which kind of thing each is

Default storage directory: `/var/lib/otelcol/supervisor` on posix,
`%ProgramData%\Otelcol\Supervisor` on Windows
(`supervisor/config/config.go:422-433`, and README "Persistent data storage").
Overridable via `storage::directory`. The packaged deb and rpm instead point at
`/var/lib/opampsupervisor/` via `config.example.yaml` and systemd's
`StateDirectory=opampsupervisor`, so the documented default and the packaged
default differ. Worth knowing before writing an install guide.

Everything the Supervisor writes into that directory, from the constants at
`supervisor/supervisor.go:72-81` and the writers at `2388-2420`:

| File | Written by | Mode | Kind |
|---|---|---|---|
| `persistent_state.yaml` | `persistence.go` `writeState()` | `0600` | **Identity and delivery state.** Holds `instance_id` (UUIDv7) and `last_remote_config_status` (status, hex hash, error message). |
| `last_recv_remote_config.dat` | `saveLastReceivedConfig` | `0600` | **Last-known config.** `proto.Marshal` of the whole `AgentRemoteConfig`. |
| `last_working_remote_config.dat` | `saveLastWorkingRemoteConfig` | `0600` | **Last-known-good config.** Only written when `agent::automatic_config_rollback: true`, which is **off by default**. |
| `last_recv_own_telemetry_config.dat` | `saveLastReceivedOwnTelemetrySettings` | `0600` | Cached `ConnectionSettingsOffers` for the Supervisor's own telemetry destination. |
| `effective.yaml` | `writeAgentConfig` (`supervisor.go:2220`) | `0600` | **Derived, not a record.** The merged config handed to the collector as `--config`. Regenerated from the inputs above on every compose. |
| `agent.log` | `commander.NewCommander(..., agentLogFileName, ...)` | n/a | Collector stdout/stderr. Transient. |
| `validate-config-*` | `os.CreateTemp` (`supervisor.go:2244`) | temp | Only when `agent::validate_config: true`. Transient. |

So the split the ticket asks for: **identity** is `persistent_state.yaml` and
nothing else. **Last-known config** is `last_recv_remote_config.dat`, plus
optionally `last_working_remote_config.dat`. **Transient** is `effective.yaml`,
`agent.log` and the validate temp files.

Note what is *not* there. No packages directory: `AcceptsPackages` is rejected at
startup with an explicit error (`supervisor.go:373-379`,
"accepts_packages capability is not yet fully implemented"), and every method on
`packageManager` returns `errors.ErrUnsupported` (`supervisor/packages.go`). And no
history: the Supervisor keeps one last-received config and at most one
last-working config. It is a cache, not a record, which is the shape premise 9
asks for.

### Across a server outage while running: the collector keeps running, indefinitely

Nothing stops it. The evidence is a negative and it is checkable:

- `commander.Stop` is called from exactly three places
  (`supervisor.go:1923`, `2116`, `2276`), and all three are config-application or
  shutdown paths. `stopAgentApplyConfig` is called when a new config arrives
  (`2005`) or on HUP reload with an empty config map (`2183`).
- The OpAMP client's `OnConnectFailed` callback
  (`supervisor.go:701-703`) does one thing: `s.telemetrySettings.Logger.Error("Failed to connect to the OpAMP server", ...)`.
  It does not touch the collector.
- There is no timer, no TTL and no counter anywhere that relates connection
  state to collector state.

`runAgentProcess` (`supervisor.go:1961`) is a `select` over three sources: a new
config, the collector process exiting, and a restart timer. Connection loss is not
one of them. If the collector crashes during an outage the Supervisor restarts it,
from the same on-disk `effective.yaml`, using its normal restart backoff.

**So: no TTL, no retry ceiling, no fallback triggered by an outage of a running
Supervisor.** The `startup_fallback_configs` mechanism is startup-only, which the
README states directly: it applies "when the OpAMP server is unreachable at
startup and there's no previous configuration state persisted in disk".

### On restart with no server reachable: three outcomes, decided by what is on disk

The decision is one condition, at `supervisor.go:1483`:

```go
if !s.initialOpampConnSuccess.Load() && !s.hasAgentConfigState() && s.config.Agent.FallbackEnabled() && !s.hasPersistedRemoteConfig() {
```

Which resolves to:

1. **`last_recv_remote_config.dat` exists.** `hasPersistedRemoteConfig()` is true,
   so the fallback branch is skipped, `loadRemoteConfig()` reads the file,
   `composeMergedConfig` merges it with `agent::config_files`, `effective.yaml` is
   written, and `runAgentProcess` starts the collector because the config file is
   present. **The collector comes up on the last-good config with no server
   reachable.** This is the case premise 9 depends on and it is true.
2. **No cache, but `agent::startup_fallback_configs` is set.** The Supervisor
   composes the collector config from those files instead
   (`composeFallbackConfig`, `supervisor.go:1828`), records the fallback state as
   a metric, and starts the collector. When the server later connects,
   `onConnect` (`supervisor.go:1051`) re-runs `loadAndWriteInitialMergedConfig`
   and signals `hasNewConfig`, so the real config takes over.
3. **No cache and no fallback configured.** `composeMergedConfig` is called with
   a nil remote config, and because `AcceptsRemoteConfig` is on with no incoming
   config map it merges the embedded noop pipeline
   (`supervisor/templates/nooppipeline.yaml`) with whatever
   `agent::config_files` supplies:

   ```yaml
   receivers:
     nop:
   exporters:
     nop:
   service:
     pipelines:
       traces:
         receivers: [nop]
         exporters: [nop]
   ```

   **The collector starts either way.** If `agent::config_files` names a real
   local config, the collector runs that config plus a `nop` traces pipeline. If
   it names nothing, the collector runs only the `nop` pipeline: a healthy process
   that does nothing. Not "not at all", and not "last-good". For a first boot into
   an outage with no local config, that is a silent no-op rather than a loud
   failure, and it is the case to design against.

**All three outcomes are covered by upstream e2e tests**, which moves this from a
source reading to a tested property:

| Test (`cmd/opampsupervisor/e2e_test.go`) | Line | Asserts |
|---|---|---|
| `TestSupervisorStartsWithNoOpAMPServer` | 1346 | Supervisor starts at all with the server down |
| `TestSupervisorStartsCollectorWithNoOpAMPServerWithNoLastRemoteConfig` | 756 | Collector reaches a passing healthcheck with no server and no cache, then the Supervisor connects when the server later starts |
| `TestSupervisorStartsCollectorWithNoOpAMPServerUsingLastRemoteConfig` | 820 | Collector comes up on a pre-seeded `last_recv_remote_config.dat` with the server down |
| `TestSupervisorRestartsWithLastReceivedConfig` | 2419 | Restart resumes the last received config |
| `TestSupervisorRestartsWithLastWorkingRemoteConfigAfterFailedConfig` | 905 | Rollback to `last_working_remote_config.dat` after a bad config |
| `TestSupervisorPersistsInstanceID` / `TestSupervisorPersistsNewInstanceID` | 2530 / 2605 | Identity survives restart, and a fresh one is minted when it does not |
| `TestSupervisorFallbackWhenNoPersistedConfig` / `TestSupervisorFallbackDisablesAfterFirstConnect` | 3529 / 3592 | Startup fallback engages, then stands down on first connect |

There is a fourth path worth naming because it changes the answer for a *served*
estate: if the server responds with an **empty** config map, `configMapIsEmpty`
becomes true and `startAgent` refuses to start the collector at all, logging "No
config present, not starting agent" and reporting `APPLIED` plus healthy
(`supervisor.go:1936-1944`, `2063-2072`). A server bug that serves an empty map
therefore stops telemetry and reports success. That is a property of the server
Amp-Up would write, not of the Supervisor, but it belongs in the server's tests.

**Rollback is off by default.** `automatic_config_rollback` defaults to false
(README: "This feature is **disabled by default**"), and
`composeWithLastWorkingRemoteConfig` returns immediately when it is
(`supervisor.go:1605-1607`). Without it, a bad config that the collector rejects
leaves the Supervisor restarting the collector against the bad config on its
backoff timer. Ticket 09's claim that the Supervisor "reverts on failure" is
correct only with this flag set. Amp-Up's install guidance should set it.

### Identity across restart: one UUID, one file, and no guard

The mechanism, from the Supervisor's side, exactly as ticket 06 asks:

- `persistent_state.yaml` holds `instance_id`, a UUIDv7
  (`supervisor/persistence.go`, `persistentState.InstanceID`).
- `loadOrCreatePersistentState(file, instanceID, logger)` loads the file if it
  exists. **If it does not exist, `createNewPersistentState` mints a fresh
  `uuid.NewV7()`** unless `agent::instance_id` is set to a parseable UUID, in which
  case that value seeds it.
- Consequence, and this is the trap: `agent::instance_id` is consulted **only
  when the state file is absent**. It is a seed, not a pin. Setting it does not
  correct an already-diverged state file, and it cannot be used to force identity
  on a host whose state directory survived.
- The Supervisor injects its own UUID into the collector's config in two places
  (`supervisor/templates/opampextension.yaml`): as
  `extensions.opamp.instance_uid` and as
  `service.telemetry.resource.attributes[service.instance.id]`.

Upstream's documented guidance is thin but unambiguous in intent. The design spec
says: "The instance_uid is generated by the Supervisor on the first run or during
the Supervisor installation and **remains unchanged thereafter**"
(`specification/README.md:545-549`). The README documents the storage directory
and says the Supervisor "persists some data to disk in order to mantain state
between restarts" (typo upstream). **Neither document warns that an ephemeral
storage directory destroys identity.** That is the whole mechanism behind ticket
06's finding: on an `emptyDir`, every pod replacement mints a new UUIDv7 and the
server sees a new agent.

The packaged VM path gets this right without the operator thinking about it,
because systemd's `StateDirectory=opampsupervisor` is persistent. The Kubernetes
path has no packaged answer at all, which is consistent with Q1: nobody upstream
has thought about Kubernetes for this component. Interchange's own fix, at
`poc/edge-node.yaml:130-134`, is a `hostPath` volume at
`/var/lib/interchange/supervisor` with `type: DirectoryOrCreate`, which makes
identity node-lifetime rather than pod-lifetime.

### Where the evidence is weak

- **The outage semantics are read from code, not from documentation.** Upstream
  documents the startup fallback and the rollback flag. It does not document "the
  collector keeps running across an outage" anywhere found. The claim rests on the
  absence of any code path from connection state to collector state, which is a
  strong negative but is a negative.
- **The tests cover restart-during-outage, not outage-during-run.** Every test in
  the table above starts the Supervisor with the server already down. No test was
  found that establishes a healthy session, kills the server, and asserts the
  collector keeps running. That specific case is still a source reading.
- **Nothing was measured.** No memory profile, no long-running outage test, no
  restart-storm test. Every claim here is a source reading.

### Confirmed separately: there is no retry ceiling

The Supervisor sets no `BackoffPolicy` in its `types.StartSettings`
(`supervisor/supervisor.go:693-730`), so opamp-go's default applies. In
`opamp-go` `client/wsclient.go`, `ensureConnected` is documented as "Continuously
try until connected. Will return nil when successfully connected. Will return
error if it is cancelled via context", and the default policy is:

```go
b := backoff.NewExponentialBackOff()
b.MaxElapsedTime = 0
```

`MaxElapsedTime = 0` in `cenkalti/backoff/v4` means no elapsed-time limit, so the
client retries forever, capped by the library's default `MaxInterval`. **There is
no retry ceiling and no give-up state.** A Supervisor whose server has been gone
for a week is still trying, and its collector is still running the config it had.

### `opamp-go`: a good library, and an example that cannot be adopted

220 stars, Apache-2.0, 23 releases, **all marked pre-release, all v0.x**, latest
v0.23.0. Maintained by Andy Keller (Bindplane) and Tigran Najaryan (Splunk), with
approvers from Dynatrace and Elastic. Its own README says: "This repository is
work-in-progress of an OpAMP implementation in Go."

**The `server` package is wire protocol only, and the ticket's framing is
correct.** 755 non-test lines across five files, plus 1,731 lines of tests. The
`OpAMPServer` interface is `Attach`, `Start`, `Stop`, `Addr`, and `Settings` is
`{Callbacks, EnableCompression, MaxMessageSize, CustomCapabilities}`. All policy
and state sits behind `types.Callbacks`. It carries no config store, no agent
registry and no hash tracking. Whoever uses it writes those.

**The runnable server is `internal/examples/server`, 1,821 lines, and it is not
adoptable for two independent structural reasons:**

1. Its module path is `github.com/open-telemetry/opamp-go/internal/examples`. The
   `internal/` path element means Go's visibility rule blocks import from any
   module outside `github.com/open-telemetry/opamp-go/...`. You cannot depend on
   it. You can only fork it.
2. It is not durable. `data/agents.go` holds `agentsById` as an in-memory map and
   `RemoveConnection` does `delete(agents.agentsById, instanceId)`, wired to
   `OnConnectionClose`. The desired config is destroyed the moment a collector
   disconnects.

Its config source is a single HTML form field: `uisrv/ui.go:141`,
`configStr := r.PostForm.Get("config")`, stored as `agent.CustomInstanceConfig`
and rendered into a `<textarea>` at `internal/examples/html/html/agent.html:96`.
`calcRemoteConfig` then wraps that string as the whole config map. No file, no
directory, no database.

**The decisive evidence on the file-source question**: issue #456, "Ability to get
a default configuration for agents in internal/examples/server", is **still open**
(created 2025-10-06, last activity 2025-12-31). The proposal in-thread is a
`--default-config <filepath>` flag. No PR implements it. **Reading config from a
file is an unfulfilled request upstream.**

A container image now exists at `ghcr.io/open-telemetry/opamp-go/opamp-server-example`,
CI-built on every commit, tagged `latest` and `main-<sha>` only, **no semver
tags**. That is packaging for an example, not a released product.

`open-telemetry/opamp-java` is **archived** since 2023-10-23 and contained only
protos.

### Bindplane: the raw-YAML finding amends ticket 09, and the licence finding is worse than expected


Validation is YAML-parseability only, with no component schema check, and `Raw` is
mutually exclusive with `Sources` and `Destinations`. The live OpenAPI schema at
`docs.bindplane.com` still exposes `spec.raw` and `type: "raw"` today. **But it
appears in zero of the 520 current documentation pages and the Terraform provider
does not support it.** So the escape hatch works and carries no documentary
commitment. Ticket 09's decision stands; its stated reason needs qualifying to
"no raw-YAML resource in the Terraform provider".

**The licence position is the real blocker, and it is not a relicensing.**
`https://github.com/observIQ/bindplane-op` returns **HTTP 404 with no redirect**,
where renamed observIQ repos do redirect (`bindplane-agent` resolves to
`bindplane-otel-collector`). Recovered from the immutable Go module proxy:
`proxy.golang.org/github.com/observiq/bindplane-op/@latest` returns
`{"Version":"v1.35.0","Time":"2023-10-04T15:29:00Z"}`. The LICENSE in that zip is
genuine unmodified Apache-2.0, 202 lines, appendix filled with "Copyright observIQ,
Inc", and grepping it for `business source|elastic license|non-production|competing`
returns zero hits. **It was never relicensed. The open-source line stopped at
v1.35.0 on 2023-10-04 and the repository was removed.** Current terms are a
proprietary EULA effective 2026-05-28 forbidding reverse engineering and competing
use.

Self-hosting is gated: "The Bindplane license key. This option is required for
server startup", plus a PostgreSQL database documented as "a Bindplane Enterprise
feature". Self-hosting appears only on the Enterprise plan page.

The successor repo `observIQ/bindplane-op-enterprise` is **also HTTP 404**. Only
`observIQ/bindplane-otel-collector`, the agent distribution, remains public and
Apache-2.0.

**Its GitOps flow is push-from-CI, not pull-from-git**, and this is checkable at
source rather than only from documentation: **the v1.35.0 tree contains no
`go-git` import, no `git clone` invocation and no `gitops` reference anywhere.**
The `bindplane sync` command syncs agent *versions* from GitHub releases, not
config. Their own doc: "Bindplane must be reachable by the CI/CD 'runner'". The `bindplane-op-action` reads YAML from the checked-out repo and
POSTs it via `a.client.Apply(...)`. Bootstrap is export-first
(`bindplane get configuration -o yaml --export > configurations.yaml`), so
Bindplane is the system of record and git is an input channel. The optional
`enable_otel_config_write_back` commits *rendered* otelcol YAML back into the
repo, which is publication. And secrets export as the literal placeholder
`(sensitive)`, so the git copy is structurally incomplete and cannot be
authoritative even if you wanted it to be.

### GrafanaFleetManagement: it is an OpAMP server, it is Cloud-only, and it requires the Supervisor

This corrects an assumption and lands the strongest external validation of Q2 in
the whole document.

- **GrafanaAlloy does not speak OpAMP.** It uses `remotecfg`, a Grafana-defined
  ConnectRPC API from `grafana/alloy-remote-config`
  (`collector.v1.CollectorService`, three RPCs: `GetConfig`, `RegisterCollector`,
  `UnregisterCollector`), client-polled with `poll_frequency` defaulting to 1m.
  The message shapes are OpAMP renames, but it is not OpAMP.
- **OpenTelemetry Collectors connect over genuine OpAMP.**
  GrafanaFleetManagement's own architecture documentation: "OpenTelemetry
  Collector deployments connect to Fleet Management through Open Agent Management
  Protocol (OpAMP)... **you must connect with the OpAMP Supervisor if you want to
  enable remote configuration.**" Endpoint `<SERVICE_URL>/v1/opamp`. The proto
  carries `COLLECTOR_TYPE_ALLOY = 1; COLLECTOR_TYPE_OTEL = 2`. GA around July 2026.
- **Not self-hostable.** "Grafana Fleet Management is a Grafana Cloud feature, but
  you can use it with self-managed enterprise or on-premises setups **where a
  connection to Grafana Cloud is possible**", and "Fleet Management doesn't
  currently have a native solution for air-gapped environments".
- **Licence**: `grafana/alloy-remote-config` (18 stars) and
  `grafana/fleet-management-api` (5 stars) are Apache-2.0 but contain **protos and
  generated clients only**. The server is not published under any licence. An open
  wire contract over a closed service.
- `config_type = "OTEL"` does accept raw otelcol YAML. From
  `terraform-provider-grafana` `resource_pipeline.go`, resource
  `grafana_fleet_management_pipeline`, "Must be one of: ALLOY, OTEL". The validator
  is asymmetric: ALLOY contents are parsed as Alloy syntax, OTEL contents are only
  checked for well-formed YAML with no otelcol schema validation.

**So GrafanaFleetManagement is simultaneously ticket 09's delivery target and an
OpAMP server, and it mandates the same Supervisor Amp-Up would.** That is the
single strongest piece of evidence that the Supervisor is a viable thing to
require, and it comes from a vendor who took the path to GA.

### Two OpAMP servers that are read-only, which is now a pattern

- **ElasticFleetServer.** Its documentation says "Fleet Server, which acts as an
  OpAMP server", but `handleOpAMP.go` sets
  `serverCapabilities = AcceptsStatus | AcceptsEffectiveConfig`, with **no
  `OffersRemoteConfig`**. This is the third independent confirmation of the
  ADR-0003 permanence claim, after ticket 02's API reading and ticket 09's
  `fleet-server/docs/opamp.md` quote.
- **SplunkEnterprise 10.x agent management**: "available in read-only mode, so you
  can view and monitor their details without making changes". Self-hosted, but not
  a config plane.

Read alongside the OpenTelemetry Operator's bridge (ticket 17: embeds a real
OpAMP server that never populates `RemoteConfig`), **three separate projects have
now independently shipped an OpAMP server that deliberately refuses to serve
config.** That is a recurring design choice, not a coincidence, and it is worth
carrying into ticket 21: the read-only OpAMP server is an established shape and
the serving one is not.

### The adjacent shape: no pluggable config source exists anywhere

**Plainly: no.** There is no OpAMP server whose config source sits behind an
interface such that adding git would be a contribution rather than a build.

Two near-misses, both in the wrong scope:

1. **`elastic/opentelemetry-collector-components/extension/apmconfigextension`**
   has the only genuine adapter interface found:

   ```go
   // RemoteConfigClient is an adapter interface that can be used between different
   // remote configuration providers.
   type RemoteConfigClient interface {
       RemoteConfig(context.Context, IdentifyingAttributes, LastConfigHash) (*protobufs.AgentRemoteConfig, error)
   }
   ```

   Its README confirms it "starts an OpAMP server providing an OpAMP endpoint".
   But it serves **EDOT SDK central configuration, not collector pipeline
   config**, and its single implementation reads from Elasticsearch. Good
   precedent for the interface *shape*, wrong problem.
2. **SigNoz's `AgentConfigProvider`** already carries the
   `SubscribeToConfigUpdates(callback func())` hook a git watcher would need, but
   its one implementation is SQL-backed and its scope is UI-authored log
   pipelines.

Everything else divides into two groups, neither extensible:

- **Database as source of truth**: Bindplane, Graylog, HyperDX, opampcommander,
  openfleet, lawrence-oss, otel-magnify, otelfleet, opamp-elixir. Several have
  pluggable *persistence* (bbolt/Postgres/Datastore, pebble/gRPC,
  sqlite/memory), which is a different axis entirely. YAML files are an import
  format, never a source.
- **Directory on disk, read once at startup**: `mbrigl/opamp-fleet` reads a JSON
  directory into a `RwLock<BTreeMap>` at boot, `tinyolly` reads a single file via
  `loadInitialConfig()`, `confOpAmpMCP` loads a template YAML at init. **None
  watches the filesystem, none re-reads, none is pluggable.** Star counts 0, 27
  and 0.

One methodological caution worth recording for anyone repeating this: a bare
GitHub search for "opamp" is roughly 90% operational-amplifier electronics repos.
Filtering to `opamp server in:name,description` returns only 12 repos, and the
most-starred third-party one, `agardnerIT/opamp-server-py` at 14 stars,
self-describes as "Entirely vibecoded", has **no LICENSE file**, and does not set
`OffersRemoteConfig` at all.

### The build baseline, priced honestly

Interchange's `testbed/control-plane/main.go` is the existence proof the ticket
points at, and it holds up under measurement:

| Part | Lines | Would Amp-Up need it? |
|---|---|---|
| OpAMP serving loop (`server.New`, `onMessage`, hash compare, offer, status read) | **99** (`main.go:112-210`) | Yes, this is the whole serve half |
| Rendering, merge, tier stamping, shared-collector OTTL | 242 (`main.go:237-478`) | Amp-Up needs its own, different, and needs it whether or not it serves |
| Register loading, helpers, logging | ~158 | Mostly not |
| **Total** | **499** | |

Dependencies: two direct (`opamp-go v0.19.0`, `gopkg.in/yaml.v3 v3.0.1`) and two
indirect (`gorilla/websocket`, `google.golang.org/protobuf`). Nine modules in
`go.sum`, five of which are test-only. Compare ticket 09's finding on Argo CD's
repo-server, which needed **37 `k8s.io` replace directives**. The dependency
weight of serving OpAMP is approximately nothing.

**What that number does not include, stated so the baseline is not read as the
whole cost:**

- **No authentication of any kind.** `main.go:116-124`, `OnConnecting` returns
  `Accept: true` unconditionally with no check on the request. Both PoC supervisor
  configs use `tls: insecure: true`. A production server needs mTLS or bearer auth
  plus the `Server.Auth` extension wiring the Supervisor already supports.
- **No durable or shared state.** `cp.agents` and `cp.offered` are two in-memory
  maps guarded by one mutex in one process. No HA, no sharding, no restart
  survival. Ticket 11's commit stamp removes the need for `cp.offered`, which is
  the point, but agent identity mapping remains.
- **The reading model is not implemented at all.** `onMessage` never reads
  `msg.EffectiveConfig` (ticket 01), and `main.go:207` logs only
  `msg.Health.Healthy` rather than the tree (ticket 11, section 7).
- **The spec makes the hash work non-optional.** From the OpAMP specification:
  "The calculation of the hashes is performed by the Server. The Server MUST
  choose a strong hash calculation method", and "The Server SHOULD compare this
  hash with the config hash it has for the Agent and if the hashes are different
  the Server MUST include the remote_config field in the response." The 99 lines
  do this correctly, so this is a cost already paid rather than one hidden.
- `opamp-go v0.19.0` is pinned against a current v0.23.0, four minors behind.

So the honest sizing: **the git-reading, matching and offering server is a small
build on top of a maintained Apache-2.0 library, and the surrounding production
concerns (auth, TLS, HA, identity) are the larger and less glamorous half.**

### Where the evidence is weak

- **Proprietary products were assessed from documentation, not source.** Whether
  CoralogixFleetManagement or SplunkOpenTelemetryFleetManagement could be
  self-hosted under some agreement is unknown; the published position is SaaS.
- **The Bindplane `spec.raw` behaviour is read from v1.35.0 source plus the
  current OpenAPI schema.** The current server is closed, so whether `raw`
  behaves identically in the proprietary line today is not verifiable.
- **GrafanaFleetManagement's non-self-hostability rests on a scoping statement,
  not an explicit denial.** The quoted sentence says it works with self-managed
  setups "where a connection to Grafana Cloud is possible", and the docs are
  scoped throughout to a Grafana Cloud stack, and the server is not published
  under any licence. No first-party sentence saying "this cannot be self-hosted"
  was found. The conclusion is strong but is assembled.
- **Negative findings for Dash0, Observe, EdgeDelta, SolarWinds, Cribl and
  Uptrace** rest on public documentation only.
- **The GitHub search space is genuinely noisy** and the enumeration of small
  third-party servers should be read as "what surfaced", not as exhaustive.
- **No prior art means no cost data.** Nothing here establishes what a
  git-backed OpAMP server costs to *operate* at estate scale, only what it costs
  to write.

## Closing: does the serve half survive the price?

Framed as evidence for ticket 21, not as ticket 21's decision.

**The strongest evidence that it survives:**

1. **The cost lands where it can be paid.** The ticket's sharp point was that the
   Supervisor might be hardest on VMs and bare metal, which is the entire reason
   to serve. It is not. VMs and bare metal are where the Supervisor is a
   first-class artefact: signed deb and rpm with a systemd unit, an MSI that
   registers a Windows service, six platform binaries, cosign signatures and SBOMs
   on a biweekly train. **OpenTelemetry's own non-Kubernetes blueprint recommends
   OpAMP for that population and calls the Supervisor "the most capable
   integration".** Serving reaches the 51% that GitOps cannot, using the mechanism
   the project itself recommends for exactly that population.
2. **Premise 9 is true rather than aspirational.** The collector keeps running the
   last-good config across an outage with no TTL, no retry ceiling and no code
   path from connection state to collector state. On restart with the server down
   it comes up on the cached config. Upstream e2e tests cover the restart cases
   directly. Amp-Up being down loses delivery and nothing else, which is what
   premise 9 claims.
3. **Someone took this path to GA.** GrafanaFleetManagement's OpenTelemetry
   Collector path went GA around July 2026 and **requires the upstream OpAMP
   Supervisor**, documented with no stability caveat. Coralogix builds and ships
   its own Supervisor and installs it as a systemd service in a managed offering.
   The Supervisor is not a component nobody has bet on.
4. **The serve half is genuinely small.** 99 lines over a 755-line Apache-2.0
   library, four runtime modules.

**The strongest evidence that it does not:**

1. **Premise 8 is not satisfied and there is no path to satisfying it.** The
   Supervisor is alpha. Its alpha tracking issue was closed on 2025-04-04 with the
   words "not necessarily something that we intend for production usage", **no
   successor beta issue exists**, no open issue carries a milestone, the design
   spec has no graduation criteria, and #48739 means even the Supervisor-collector
   compatibility policy is undefined. Breaking configuration changes are still
   landing, one on 2026-08-04. Premise 8 says prefer CNCF Graduated or stable over
   alpha; this is the far end of that scale with no declared trajectory.
2. **The market chose the other shape.** Six vendors built or bought an embedded
   in-collector OpAMP client rather than the Supervisor, including Bindplane, who
   maintain `opamp-go` and had every incentive to standardise on it, and whose own
   documentation steers production users away from the Supervisor toward their
   agent. Two vendors ship or require it. That is a real split, not a consensus.
3. **Kubernetes has nothing at all.** Zero references in the OpenTelemetry
   Operator, zero in the Helm charts, requested since 2022-12-12 and unbuilt. Zero
   mentions of Kubernetes, sidecar, container or DaemonSet in the Supervisor's own
   design spec, and zero in its 4,115-line e2e suite. For an adopter whose
   Kubernetes estate is Operator-managed or chart-managed, adopting the served path
   means replacing their deployment mechanism with a bespoke image.
4. **There is no prior art and nothing to contribute to.** No OpAMP server reads
   from git, none has a pluggable config source, and the spec's own implementations
   list contains two proprietary products. Under premise 8 building is defensible
   because the alternatives are genuinely absent. But the absence cuts both ways:
   the reason nobody has built a stateless read-from-an-external-store OpAMP server
   may be that everybody who serves config concluded they also want to store it.
   Three separate projects have shipped an OpAMP server that deliberately refuses
   to serve config; nobody has shipped one that serves from somewhere else.

**Two things that are not evidence either way, and should not be read as such.**
There is no adoption data for the Supervisor at all, so "does anyone run it in
production" is answered by vendor behaviour and nothing better. And there is no
memory-growth, leak or long-running-stability defect in the tracker in either
direction, which is compatible with the component being clean and equally
compatible with nobody running it long enough at scale to find out. Given the
vendor picture, the second is at least as likely, and it is the single largest
unknown in this document.

**The one observation that reframes the trade rather than resolving it.** The
serve half is opt-in per collector. The population that justifies serving is the
VM and bare-metal half that GitOps cannot reach, and that is precisely the
population where the Supervisor is best packaged and best documented. The
Kubernetes gap is therefore a reason not to serve Kubernetes collectors, where
GitOps already works, rather than a reason not to serve at all. Whether that
split is a coherent product or an awkward one is a judgement about Amp-Up's shape,
not a fact this research can settle. **That judgement belongs to ticket 21.**
