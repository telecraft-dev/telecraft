# How existing graphical OTel config tools model topology

Findings for ticket `04-graphical-otel-config-tooling-landscape.md`. Evidence base for the
ticket 07 decision on Amp-Up's own modelling abstraction.

Method: primary documentation, public source repositories, and direct source reading where
docs were thin. Vendor comparison posts were excluded. Where a claim comes from a vendor
blog it is labelled as such. Claims that could not be verified from a primary source are
flagged inline as unverified.

Date of research: 2026-08-04. Several of these products shipped relevant features within the
last three months, so this snapshot decays quickly. The volatile items are named in
"What will change under us" at the end.

---

## 1. The comparison

### 1.1 Primary discriminators: unit of manipulation, and multi-tier topology

These two questions separate the field more sharply than the other four, so they lead.

| Tool | Q1. Unit the user manipulates | Q3. Multi-tier topology (edge feeding a gateway that fans out) |
|---|---|---|
| **Bindplane** | Named, versioned **`Configuration`**: a graph of `Source` / `Processor` / `Destination` / `Connector` / `Extension` nodes, edited on a canvas. One Configuration is bound to one OS platform. Has a `spec.raw` escape hatch for hand-written otelcol YAML. | **Strongest in the set, but discovered rather than authored.** Each tier is a separate Configuration. The link between them is inferred at runtime: `topologyprocessor` reads `X-Bindplane-Configuration` / `X-Bindplane-Resource-Name` headers off inbound traffic, builds a route table, and Bindplane renders gateway nodes on the overview page. You cannot draw the two-tier pipeline as one object. |
| **Cribl Stream / Edge** | The **`Route`**: an ordered filter table where each row binds exactly one Pipeline (a list of Functions) to exactly one Destination, scoped to a Worker Group or Fleet. `QuickConnect` is a genuine drag-and-drop canvas but it is a *separate, weaker authoring mode* that bypasses Routes entirely. The expressive model is the table, not the graph. | **Deployable but not modelled.** Edge to Stream tiering is a documented, first-class deployment pattern using Cribl HTTP/TCP Source and Destination pairs. But the Data Insights topology map is explicitly *"limited to a specific Worker Group"*, so an Edge fleet's egress and a Stream group's ingress are two unrelated cards on two maps you switch between. Nothing in the product knows they are the same hop. |
| **Dash0** | **No collector-config surface exists.** For fleet management Dash0 ships an integration pointing at *Bindplane*. What it does model: namespace-scoped `Dash0Monitoring` CRD carrying OTTL `filter`/`transform` (structurally identical to upstream processors), plus backend-side **Spam Filters** authored by saving a query from an explorer. | **No.** The operator deploys a DaemonSet and a Deployment, but that is a *data-source* split (OTLP/host metrics vs `k8s_cluster`/`k8s_events`), not an edge/gateway split: both export directly to the backend. No in-cluster telemetry gateway. The Service Map is a trace-derived *service* graph, not a collector graph. |
| **Grafana Alloy + UI** | A **component graph expressed in text** (Alloy syntax), wired by export references. **The UI at :12345 is read-only.** It lists components, renders the graph, and shows per-component health, debug info and evaluated arguments. No documented create/edit/delete/reorder capability anywhere. In Grafana Cloud Fleet Management the unit becomes a **pipeline**: a named config fragment plus label matchers. | **No.** The Alloy component graph is intra-process by construction. Fleet Management's data model is flat: collectors matched to pipelines by AND-ed label matchers. You can *build* edge to gateway by pointing an exporter at another Alloy's receiver, but FM has no awareness of it: no rollout ordering, no address validation, no dependency display. |
| **otelbin.io** | **One otelcol YAML file in a Monaco text editor**, with a rendered pipeline graph beside it. The graph is a strictly one-way visualisation, verified at source level: the `<ReactFlow>` element receives no `onNodesChange`, `onEdgesChange` or `onConnect` handler, nodes are re-derived from the YAML on every keystroke, and there is no graph-to-YAML serialiser in the repo. | **No.** One config, one set of pipeline swimlanes (one lane per signal). No multi-document support, so an edge collector's exporter landing on a gateway's receiver cannot be drawn. It renders `connectors` and detects cycles, but only within the single config. |
| **Dynatrace** | **Three unconnected surfaces.** (a) The `dynatrace-otel-collector` YAML file on disk, with *no* Dynatrace UI, no OpAMP, no central management. (b) The `DynaKube` CR, which declares *that* a collector should exist and which image, not what its pipelines contain. (c) **OpenPipeline**, which is confirmed **server-side ingest processing**, not collector config: it runs in Dynatrace's backend after data has crossed the wire. | **Tier is real and chainable, but never composed.** ActiveGate is a genuine gateway tier and explicitly supports ActiveGate-to-ActiveGate chaining, so Dynatrace models N-tier, not just two. Binding is declarative via **network zones** with priority fallback (same zone, then alternative, then default). You never draw it and there is no diagram of which agents feed which gateway. |
| **Splunk** | **Split across two products that must not be conflated.** (a) Splunk Distribution of the OTel Collector: a YAML file, rolled out with Ansible/Chef/Puppet/Salt, with no authoring UI. (b) **Edge Processor**: a cloud control plane over an on-prem data plane, where the unit is an SPL2 **`$pipeline`** edited as a linear step list with per-step preview. Edge Processor is *not* the OTel Collector and cannot author otelcol pipelines. | **Edge Processor is itself a tier**, and the reference architecture is `sources -> forwarders -> Edge Processor -> destinations`. But the console is per-pipeline: tier membership is expressed by *which Edge Processor you applied a pipeline to*, not by drawing an edge. No composed UF-to-EP-to-Cloud graph. |
| **OTel declarative config** (`opentelemetry-configuration`) | **A JSON Schema, not a tool.** One document configures one process. Required field is `file_format`; top level is `disabled`, `log_level`, `resource`, `attribute_limits`, `logger_provider`, `meter_provider`, `tracer_provider`, `propagator`, `instrumentation/development`, `distribution`. The repo ships exactly one binary, a validator. No UI, no server, no estate. | **None at the schema level.** Elsewhere in the project: the Operator's `spec.mode` (`daemonset\|deployment\|sidecar\|statefulset`) is a workload-shape enum on *independently reconciled* CRs with no field referencing each other, and `spec.config` is an opaque blob; connectors join pipelines *within one process*; agent-vs-gateway is prose on the website. Cross-process topology is emergent from endpoint strings that nothing validates. |

**The two structural findings.**

First, **nobody authors config by manipulating a topology graph.** Bindplane's canvas is the
only real graph editor in the set, and it edits *one collector's* pipeline. Cribl's canvas
(QuickConnect) is deliberately the less powerful of its two authoring modes. Splunk's editor
is a linear chain over a non-OTel data path. otelbin renders one-way. Alloy's UI is read-only.
Dynatrace has no collector UI at all.

Second, and more usefully for ticket 07: **the multi-tier hop is universally a string, not an
object.** Every tool in the set can *deploy* an edge-to-gateway architecture, and several
document it as a recommended pattern. In every case the connection is expressed as an
endpoint typed into one collector's exporter config and a matching port typed into another's
receiver config, with no shared object binding them and no validation that the two agree.
The closest anyone gets:

- **Bindplane** discovers the edge post-hoc from traffic headers and draws it. Closest to a
  topology model, and worth studying, but it can only show you what is already happening. It
  cannot show you an intended topology, cannot warn you that an intended edge is missing, and
  cannot be used to author.
- **Dynatrace** binds tiers declaratively through network zones with priority fallback. This
  is the best *binding* model in the set (agents resolve their gateway by policy rather than
  by hardcoded address) and it is never visualised.

Those two are complementary halves of a thing nobody has built.

### 1.2 Reuse, drift, licence

| Tool | Q2. Reuse and per-collector variation | Q4. Drift handling | Q6. Open source and licence |
|---|---|---|---|
| **Bindplane** | Strong sharing, **no parameterisation**. `selector.matchLabels` and `Fleet` objects bind one Configuration to N agents ("Fleet configurations take priority over any individual agent configuration"). Per-host variation is `${ENV_VAR}` resolved in the agent's own environment, or clone (there is a dedicated `/copy` endpoint). Blueprints are pre-built processor bundles you copy and then edit, not parameterised templates. | **Prevented, not detected.** Managed collectors are OpAMP clients: *"Once the supervisor takes over, your existing local `config.yaml` is no longer used."* Surfaces Connected / Disconnected / Error / Configuring / Pending / Incompatible / Upgrading, and auto-pauses a rollout on error. **No named drift or config-mismatch state, no drift alert, no documented UI diffing reported effective config against intent.** | Collector and all client tooling **Apache-2.0** (`bindplane-otel-collector`, `-contrib`, `-supervisor`, Terraform provider, operator, Helm chart). **Server and UI are closed.** `observIQ/bindplane-op` now 404s; last public Go module was v1.35.0, Apache-2.0, Oct 2023; a licence key became mandatory for new installs in v1.79.0 (Oct 2024). Only peripheral tooling is open: Terraform provider (MPL-2.0), Helm charts (MIT), some SDKs (Apache-2.0). No engine, no UI. |

Notable footgun: per-namespace filter conditions are *"aggregated into one single filter processor"* and the most severe `error_mode` wins cluster-wide. | **Genuine reconciliation, the strongest in the set.** The operator watches its generated ConfigMaps, DaemonSet, Deployment, Service and RBAC and *"reconciles them if they are changed or deleted externally"*. SaaS backend proprietary. |

In Fleet Management, pipelines carry Alertmanager-style label matchers (`=`, `!=`, `=~`, `!~`), **AND-only, no OR**. Mechanism worth stealing: *"The Fleet Management service wraps each pipeline in a `declare` block, and the `declare` blocks are marshalled and merged into a single file on the server side."* Per-collector variation via `argument` blocks, env vars, and remote attributes (which take precedence over local). | **Best drift visibility in the set.** Alloy reports its **effective configuration** and the UI shows it against the **server configuration**, plus a rollout banner for pending / stalled / applied / failed. | **OTel declarative config** | **Zero composition in the schema.** No include, import, merge, overlay, inherit or remote `$ref`; the only extensibility is `additionalProperties: true` with explicitly no versioning guarantee. ## 2. Question 5, handled adversarially

The project's claimed differentiator is that nobody connects config to outcomes. This section
was researched with the explicit goal of refuting that claim. To avoid the usual sloppiness
where "monitoring exists" is treated as "the gap is filled", the capability is decomposed into
a ladder. Each rung is strictly harder than the one below it.

| Rung | Capability | Question it answers |
|---|---|---|
| **L0** | Nothing | |
| **L1** | Agent liveness | Is the collector process alive and checking in? |
| **L2** | Component or pipeline health | Did the config load, and are its components erroring? |
| **L3** | Throughput metering | How much data crossed this boundary? |
| **L4** | Absence alerting | Alert me when a named object receives zero data. |
| **L5** | Content conformance | Does the telemetry that arrived match a declared expectation of its shape? |
| **L6** | **Config-derived expectation** | **Derive from the config what should arrive, then check that it did.** |

L6 is the claimed gap. Placement:

| Tool | L1 | L2 | L3 | L4 | L5 | L6 | Notes on the ceiling |
|---|:--:|:--:|:--:|:--:|:--:|:--:|---|
| **Bindplane** | yes | partial | yes | **no** | no | no | Alerting is five fixed daily notifications: Errored Rollouts, Errored Agents, Pending Rollouts, Outdated Agents, Days until Licence Expires. **Verified directly: not one is data-flow based.** Throughput exists and is good, but is sampled (`sampling_ratio` defaults to `0.5`). |
| **Cribl** | yes | partial | yes | **YES** | no | no | **The only tool in the set that reaches L4.** See below. |
| **Dash0** | yes | operator status only | yes (cost) | DIY | **no** | no | See the correction below: Dash0's semconv work is *normalisation*, not conformance checking. |
| **Alloy + FM** | yes | yes | manual only | delegated | no | no | A collector that polls for config on schedule and ships zero telemetry **reads green**. |
| **otelbin** | n/a | n/a | n/a | n/a | n/a | n/a | Pre-flight only. Boots the real distro binary. Never sees telemetry. |
| **Dynatrace** | yes | dashboards | yes | DIY | no | no | Has real sample-data preview, but only for server-side OpenPipeline processors. |
| **Splunk** | yes | effective config | yes | weak/DIY | no | no | Has real preview and a documented post-apply verification *procedure*, but only for Edge Processor, never for otelcol. |
| **OTel project** | yes | healthcheckv2 (dev) | yes | no | **YES (weaver)** | no | Two separate near-misses. See below. |

### 2.1 The three genuine refutation candidates

These are the findings that most threaten the claimed gap. All three are real. None reaches L6.

**(a) Cribl reaches L4, and it is the strongest single counter-example.** Cribl Notifications
include, verbatim from the docs and independently re-verified:

> **"No Data Received": The Source or Collector ingests zero data over your configured time window.**

Alongside **High Data Volume**, **Low Data Volume** and Source **Persistent Queue Usage**, plus
Destination-side **Backpressure Activated** and **Unhealthy Destination**. Configurable time
windows, routed to email, PagerDuty, Slack, webhook or SNS. This is a real, shipped, per-object
absence alert and any claim that "nobody alerts on missing data" is false.

Four reasons it is not L6, all verified:

1. **The trigger set covers Sources, Destinations and Licences only. There is no Route or
   Pipeline condition.** So the classic failure, a Route filter that silently stops matching
   after an upstream field rename, has *no* notification. You can see the match percentage
   drop on the Routes table. Nothing will page you.
2. **Each notification is hand-configured per object, and nothing derives it from the config.**
   Confirmed directly: *"There is no automatic trigger condition derivation from pipeline or
   route configuration."* Add a Source, forget its notification, and its silence is invisible.
   The expectation is a second artefact maintained in parallel with the config, with no check
   that the two agree.
3. **It is volume-based, not signal-based.** It fires on zero bytes at a Source. It cannot
   express "the `http.server.duration` metric from service X should be arriving". A Source can
   be healthily busy while the one signal you cared about was dropped by a Function.
4. **It cannot span the tier boundary**, because of the Worker-Group scoping in Q3. Edge egress
   and Stream ingress are two unrelated facts.

**(b) Weaver reaches L5, against the wrong declaration.** `open-telemetry/weaver` ships
`weaver registry live-check`, described as *"Check the conformance level of an OTLP stream
against a semantic convention registry"*. It starts a real OTLP listener, streams received
messages through Advisors (builtin `missing_attribute` and `type_mismatch`, plus overridable
Rego policies), emits `PolicyFinding{level, id, signal_type, signal_name, message}`, and exits
non-zero on any violation. There are shipped CI actions for it.

This is the only thing in the entire set that inspects actually-emitted telemetry and judges it
against a declared expectation. It is genuine prior art and the design should not pretend
otherwise. But the declaration is a **semantic convention registry**, not a config. Weaver has
no notion of a config document, a collector, an agent identity or a fleet, and positions itself
as *"a developer tool"* for CI. It answers "is this span well-formed", not "did config C
produce what it promised".

**(c) The collector's own metrics are L3 but are addressable to config-named components.**
This is closer to L6 than it first appears and deserves care.
`otelcol_receiver_accepted_spans`, `otelcol_receiver_refused_*`, `otelcol_processor_incoming_items`
/ `outgoing_items`, `otelcol_exporter_sent_*`, `send_failed_*`, `enqueue_failed_*`,
`otelcol_scraper_scraped_metric_points`. Per the component-universal-telemetry RFC these carry
instrumentation-scope attributes `otelcol.component.kind`, **`otelcol.component.id`**, and for
processors **`otelcol.pipeline.id`**. So the counters *are* joinable back to the exact component
IDs named in the config file. That join is the raw material for L6 and it already exists.

What is missing is the other half: nothing derives an expectation from the config to compare
those counters against. Also note two limits: `exporter_sent` counts what the exporter believes
it handed off, not what the backend accepted or indexed; and there is no cross-process view, so
an agent's `sent` and a gateway's `accepted` are two unrelated numbers.

> Correction for the ticket: **`otelcol_processor_dropped_*` no longer exists.** Per-processor
> drop counters were replaced by the generic `incoming_items` / `outgoing_items` pair. Drops are
> inferred from the delta.

### 2.2 The near-misses worth knowing about

- **healthcheckv2extension** aggregates component `StatusEvent`s into **per-pipeline** health,
  exposed over HTTP (`/status?pipeline=traces/http&verbose`) and over streaming gRPC `Watch`
  where the service field carries the pipeline name. This is the nearest thing OTel has to "is
  this configured pipeline working". Three disqualifiers, all quoted from its README: stability
  is **development**, its distributions list is **empty** (it ships in nothing), and
  *"Adoption of status reporting by collector components is still a work in progress."* Its
  predecessor's attempt at exactly this was removed: *"The `check_collector_pipeline` feature
  of this extension was not working as expected and has been removed."*
- **opampsupervisor `automatic_config_rollback`** (off by default) watches collector health
  after applying a remote config and reverts to the last known good on failure. This is the
  closest thing in the project to a closed safety loop, and it is health-based, not
  outcome-based.
- **Bindplane Snapshots** look like outcome verification and are not: a 100-record in-memory
  ring buffer, pulled on demand when a human clicks "View Recent Telemetry", sampled down if
  the payload would exceed 10 MiB. The docs explicitly decline to treat emptiness as a fault:
  *"If no metrics are available, it's possible none have been collected yet."*
- **Splunk Edge Processor** has the best human-facing loop anywhere in the set: per-step
  "Preview up to this action" against sample data before apply, then a *documented post-apply
  verification procedure* comparing inbound and outbound volume and searching the destination
  index to *"confirm that it contains the expected events"*. It is a runbook for a person, not
  an assertion the system makes, and it exists only for SPL2, never for otelcol.
- **Dynatrace OpenPipeline** has a real processor preview API returning *"The altered record
  after the processor was applied"* for sample data. Server-side ingest rules only.
- **Alloy live debugging** streams real data between components, is **disabled by default**,
  and notably does **not** support `otelcol.exporter.*` or `loki.write`. You can watch data
  enter and traverse but not the final egress hop.

### 2.3 Two corrections to assumptions that were worth testing

**Dash0 does not check telemetry quality.** This was the single most likely refutation in the
set and it fails. Dash0's semantic-convention feature is **normalisation, not validation**:
*"Dash0 provides automatic schema migration capabilities that transform your telemetry data
during ingestion to align with the OpenTelemetry semantic conventions version of your choice."*
It silently renames `http.status_code` to `http.response.status_code` and so on. There is no
wording anywhere about flagging, scoring or reporting non-conformance. Dash0 *fixes* your
telemetry rather than *telling you it is wrong*. Missing-data detection is user-authored
PromQL (`absent_over_time`), one per service, derived from nothing.

Dash0 is in fact the *strongest supporting evidence* for the gap, because of one revealing
asymmetry found in the operator: `Dash0Monitoring` carries real closed-loop status for
dashboard sync (`synchronizationStatus`, `httpStatusCode`, `validationIssues[]`) because that
traffic goes over an **API** endpoint that returns a response. Telemetry goes over an
**ingress** endpoint that returns nothing. Write a `Dash0Monitoring` requesting logs from a
namespace, have the filelog receiver fail to read the log driver, and the CR still reports
`Available=True`, *"Dash0 monitoring is active in this namespace now."*

**Dash0 also has no fleet management at all.** It ships a Bindplane integration for that. It
is in this comparison as a backend, not as a peer to Bindplane or Cribl.

## 3. Per-tool detail

Only material not already in the tables above.

### 3.1 Bindplane

The most complete object model in the set and the closest existing thing to what ticket 07 is
contemplating. Resource kinds are real, versioned, API-addressable
(`apiVersion: bindplane.observiq.com/v1`) and split cleanly into pipeline resources
(`Configuration`, `Source`, `Processor`, `Destination`, `Connector`, `Extension`), a type
catalogue that supplies parameter schemas (`SourceType`, `ProcessorType`, `AgentType`,
`AgentVersion`, `RecommendationType`), and fleet/admin objects (`Agent`, `Fleet`, `Rollout`,
`Recording`, `Project`).

Two design constraints to note. `spec.type` pins a Configuration to one platform
(`linux`, `windows`, `macos`, `kubernetes-daemonset`, `kubernetes-deployment`,
`openshift-*`), so a Configuration can never span Linux and Windows. And there is no
parameterisation at all, which means the platform split plus any per-site variation multiplies
into cloned Configurations. The `/copy` endpoint is the sanctioned answer. This is the single
clearest unmet need visible in Bindplane's own API shape.

Configuration **V2** (Bindplane 1.85.0+) added explicit routes between components, connectors
declarable in the config, and processors declarable without being attached to a source or
destination, plus a routing connector using first-match OTTL conditions. That is meaningful
graph expressiveness, still confined within one Configuration.

The gateway topology mechanism deserves specific study for ticket 07. `topologyprocessor` is
Apache-2.0 and readable. The design (edges discovered from in-band traffic metadata, aged out
of a route table) is a legitimate and cheap way to get a real topology view, and it is exactly
the inverse of the design a config-authority tool would want, which is intended topology first
and discovered topology reconciled against it. The two together would be a drift signal for
*topology*, which nobody has.

### 3.2 Cribl Stream and Edge

The important structural lesson is that **Cribl's expressive model and its visual model are
different products.** Routes give ordered evaluation, filter expressions, and a `Final` toggle
that turns a match into either a terminal dispatch or a clone-and-continue, which is how one
Source fans out to many Destinations. QuickConnect is the drag-and-drop canvas and it
*"completely bypasses Routes, which is why every QuickConnect path is independent and
parallel"*: no filtering, no cloning, no ordering. Cribl built a graph editor and then had to
tell users to use the table when they needed real dispatch semantics. Any graph-first design
for Amp-Up has to answer this.

Data Insights is the closest thing to a pipeline topology view in the commercial set: map cards
for Sources, pre-processing pipelines, Routes, post-processing pipelines and Destinations, with
volume, **freshness** and **shape** per card, and documented use for spotting *"when a Source is
not attached to the expected Route"*. Freshness and shape as first-class per-node readouts are
worth borrowing. The Worker-Group scoping is the limit.

Cribl also has the sharpest documented reuse anti-pattern: Packs are shared by **copying**
between Worker Groups. That is a fork, and it drifts.

### 3.3 Dash0

Covered above. The one further point is what its collector-config surface deliberately excludes:
an exhaustive grep of the operator for `additionalReceiver|extraReceiver|customReceiver|configOverride|rawConfig`
returns zero hits, and the docs state *"Disabling or enabling individual metrics via
configuration is not supported"* and *"Changing the frequency of metrics collection is not
supported."* Dash0 has chosen a closed, opinionated config surface (OTTL filter/transform plus
exporter endpoints plus a small allowlist of scalars) with no escape hatch. That is the opposite
of Bindplane's `spec.raw`. Both choices are defensible and ticket 07 has to pick one.

### 3.4 Grafana Alloy and Fleet Management

Two mechanisms are worth taking wholesale.

**Server-side pipeline merge.** Fleet Management wraps each assigned pipeline in a `declare`
block and marshals them into one server configuration, which is why duplicate assignment is
harmless (*"the collector runs both pipelines without conflict because each pipeline has a
unique name"*). This is a clean answer to "many policies, one collector" that avoids the
ordering and precedence problems every other tool has. The cost is shared fate at load time:
one bad pipeline discards the whole merged file and the collector silently falls back to the
previous version of *all* pipelines. That failure mode should be designed against explicitly.

**Effective vs server configuration as a first-class UI concept**, with a rollout banner for
pending / stalled / applied / failed. Alloy and Splunk arrived at this independently, which is
strong evidence it is table stakes rather than differentiation.

The attribute precedence model (local attributes set in the collector's `remotecfg` block,
remote attributes set in the UI which **take precedence**, and reserved `collector.*`
attributes auto-populated) is the cleanest identity/labelling scheme in the set.

### 3.5 otelbin.io

Small, sharply scoped, and the validation is better than it looks. Server-side validation is
not schema checking: it runs the **actual collector binary** in a per-distro Lambda image
(`otelcol validate --config=...`), and for ADOT, which lacks a `validate` subcommand, it boots
the real collector and greps stderr for *"Everything is ready. Begin running and processing
data."* Currently four distros, version-pinned: `otelcol-core` and `otelcol-contrib` (v0.157.0),
`adot` (v0.49.0), `splunk-otel-collector` (v0.157.0).

So otelbin answers "would this config load, bind its ports, and start" with real fidelity, which
is the strongest possible offline signal, and still says nothing about data. Notably, Splunk
users are sent to otelbin for otelcol config validation because Splunk ships none.

### 3.6 Dynatrace

The finding that matters for positioning: Dynatrace's centre of gravity is OneAgent, and
processing has been pulled **server-side** into OpenPipeline. That has two consequences.
Filtering and redaction in Dynatrace do not reduce egress, because they happen after ingest.
And the excellent Settings 2.0 inheritance model (environment, then host group, then host,
most specific wins) is pointed at OneAgent behaviour and never at collector YAML. Dynatrace has
solved config inheritance for a fleet and simply has not applied it to OTel.

ActiveGate chaining plus network zones is the best tier-binding model found. Worth restating
precisely because it is a design pattern Amp-Up could adopt: agents do not name their gateway,
they name a **zone**, and resolution falls through priority groups (same zone, then configured
alternatives, then default, then any). That decouples the edge config from gateway addressing
entirely, which is exactly what makes a two-tier topology maintainable at scale.

### 3.7 Splunk

The read on Splunk is competitive rather than technical. Splunk has independently concluded
that "what is actually running out there versus what you think is running" is the problem worth
building a UI for, has shipped inventory, effective config, heartbeat and drift detection, and
has publicly committed to the remote-config write half. Treat drift detection as table stakes
by the time Amp-Up ships, not as differentiation.

One operational sharp edge worth designing against, quoted from the pipeline docs: *"make sure
to always have a default destination for your Edge Processors. Otherwise, all unprocessed data
is dropped."* Silent total data loss as the default behaviour for unmatched routing. Bindplane's
routing connector has the same shape (first-match, docs recommend a catch-all last route). A
config model that can express routing should be able to *prove* exhaustiveness rather than
recommending it in prose.

### 3.8 The OpenTelemetry project

`opentelemetry-configuration` reached **1.0.0 in Feb 2026** and 1.1.0 in June 2026. The data
model is Stable. Mixed stability is encoded in property names via a `/development` suffix
(15 such properties), which is a genuinely good idea for a config schema and worth copying.

The critical structural finding: **the Collector is not converging its main config on this
schema.** Two separate efforts exist.

1. The SDK declarative schema is used by the Collector for exactly one thing, its
   `service::telemetry` section.
2. Collector *component* config is getting its own, separate JSON Schema effort, tracked in
   `docs/rfcs/component-configuration-schema-roadmap.md`: schema-first, generated from
   `metadata.yaml` via `mdatagen`, ending at *"Phase 4: Extend OCB... bind all components
   schemas to single schema that describes entire collector config file"* so that it
   *"can be used by internal and external tools for validation and autocompletion."*

Phase 4 is the thing to watch. A machine-readable schema for the whole collector config file,
generated per build from the components actually compiled in, is the missing input for any
graphical authoring tool that wants to be distro-correct rather than hardcoding a component
catalogue. Amp-Up should plan to consume it and should probably contribute to it.

> The internal-telemetry docs page still warns that the declarative schema is *"still under
> development"* and links collector issue #10808, which closed in Feb 2025. That warning is
> stale; do not cite it as current status.

## 4. Verdict on the claimed gap

**The claim is that nobody connects config to outcomes, checking whether the telemetry the
config asked for actually arrived.**

**Verdict: partly filled, and the claim as currently worded is too strong to survive contact
with Cribl. The specific gap at L6 is real and is unfilled by every tool examined.**

### What is already filled, and must be dropped from the differentiator

- **"Nobody alerts on missing data" is false.** Cribl ships No Data Received, Low Data Volume
  and High Data Volume as configurable per-Source notifications routed to real alerting
  channels. This is shipped, documented and re-verified.
- **"Nobody checks emitted telemetry against a declaration" is false.** Weaver's
  `registry live-check` does exactly that against a semantic-convention registry, with Rego
  policy extensibility and CI actions.
- **"Nobody has per-pipeline outcome counters" is false.** The collector's own
  `otelcol_receiver_accepted_*` / `otelcol_exporter_sent_*` / `send_failed_*` family is
  attributable to `otelcol.component.id` and `otelcol.pipeline.id`, which are the exact
  identifiers used in the config file.
- **"Nobody detects drift" is false and is about to become obviously false.** Alloy surfaces
  effective versus server configuration with rollout state. Splunk has built a UI around
  drift detection and named it as such in its marketing. Do not build the pitch on this.
- **"Nobody previews the effect of a config change" is false.** Bindplane Live Preview,
  Cribl Data Preview, Splunk Edge Processor per-step preview and Dynatrace OpenPipeline
  processor preview all exist. Preview against sample data is a solved, commoditised feature.

### What is genuinely unfilled

Precisely one thing, and it is worth stating as a single sentence:

> **No tool derives, from the configuration it manages, an expectation of what telemetry should
> arrive, and then checks that expectation against what did.**

Every mechanism found is on one side of that join or the other, and nothing crosses it:

| Side of the join | What exists |
|---|---|
| **Config side** | Bindplane Configurations with real resource IDs; Cribl Routes with filter expressions; Alloy pipelines with label matchers; declarative schema with `file_format` versioning; OpAMP effective-config reporting. |
| **Outcome side** | Cribl No Data Received per Source; `otelcol_*` counters keyed by component and pipeline ID; weaver conformance findings; healthcheckv2 per-pipeline status; per-destination throughput everywhere. |
| **The join** | **Nothing.** |

The consequences of the missing join, each observed directly rather than asserted:

1. **Expectations are a parallel artefact.** Cribl's own docs confirm *"no automatic trigger
   condition derivation from pipeline or route configuration"*. Every alert is hand-made per
   object and can silently fall out of step with the config it is supposed to guard. Add a
   Source and forget the notification, and its silence is undetectable.
2. **Coverage is unaskable.** Nothing answers "this Configuration asked for Windows Security
   event logs, and zero have arrived from 40 of these 200 hosts for six hours." Every tool
   meters volume at object boundaries; none reconciles per-target coverage against intent.
3. **Green means "I applied the config", never "the config worked".** Verified in three
   independent products. Dash0: `Available=True` means the operator wrote a ConfigMap. Alloy
   Fleet Management: green means the collector fetched config within 30 minutes, so a collector
   shipping zero telemetry reads healthy. Bindplane: the five notifications are agent, rollout
   and licence state only.
4. **The join cannot be made across a tier boundary by anyone**, because per section 1.1 no
   tool holds an object representing the hop. Cribl states the scoping limit explicitly. This
   is why questions 3 and 5 are the same question wearing different clothes, and it is the
   most defensible ground in the whole landscape.

### Recommendation for how to word the differentiator

Retire "connects config to outcomes", which is broad enough that Cribl refutes it. The
defensible claims, in descending order of strength:

1. **The intended topology as a first-class, multi-tier object**, against which both drift and
   delivery are reconciled. Nobody has this. Bindplane discovers topology but cannot author it;
   Dynatrace binds tiers by policy but never shows them; everyone else has no cross-process
   object at all.
2. **Expectations derived from config rather than maintained beside it.** The config already
   names the components; the outcome counters are already keyed by those names; the join is
   mechanical and nobody has made it.
3. **Per-target coverage rather than aggregate volume.** Every tool answers "how much"; none
   answers "from which of the things I asked for, and which are missing".

Claim 1 is the strongest and is directly supported by the Q1/Q3 table. Claim 2 is real but
should be stated carefully, acknowledging Cribl at L4 and weaver at L5 as prior art for the
halves.

## 5. What will change under us

Volatile items, flagged because several shipped within three months of this research.

- **Splunk's remote-config push.** All primary sources today say retrieve-only and
  limited-availability, and Splunk's own blog says push is future work. If it ships, Splunk
  becomes a direct competitor with a drift story already built.
- **Bindplane v1.101.0 (July 2026)** added *"a new OpAMP connection extension [that] ships
  agent metrics (including per-exporter and pipeline-health metrics) for cost and health
  evaluation."* No dedicated doc page found. **Unverified** what this surfaces in the UI. If it
  becomes native per-pipeline health with alerting, Bindplane moves from L3 to L4.
- **Collector component config schema, Phase 4.** Would give any graphical tool a
  machine-readable, distro-accurate component catalogue. Watch
  `open-telemetry/opentelemetry-collector` issues #14543 and #15010.
- **healthcheckv2extension** is development-stability and ships in no distribution. If it
  stabilises and gets adopted by components, per-pipeline health becomes a commodity primitive.

Other unverified items: Bindplane's undocumented `agent.verify` server metric; whether Cribl
Data Insights covers Edge Fleets as well as Stream Worker Groups; Cribl Insights licence tier;
OpenPipeline per-pipeline dropped-record counters; Splunk server-class precedence rules for
OTel-shaped config; whether Blueprints support any variable substitution (believed not).
